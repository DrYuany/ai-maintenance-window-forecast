## 一、参数：对外宣称 51 项可改，实际 19 项

### 证据

```
python backend/eval_cases/probe_param_coverage.py
```

改之前：51 项里 35 项写进 `parameters` 直接报 `未支持参数：{'xxx'}`。
改之后：19 项全部走通，32 项明确标注改不动。

### 为什么会有 51 这个数

三份手抄清单，各写各的：

| 清单 | 位置 | 条数 | 谁在用 |
|---|---|---|---|
| 设计分类 `GENERATION_LAYER` / `SELECTION_LAYER` | `registry/parameters.py` | 51 | 生成提示词目录 |
| 执行白名单 `OVERRIDES` | `scripts/product_data.py:113` | 16 | `load_project` 收参数时卡这一关 |
| 补丁说明 `_NOT_A_PARAM` | `registry/schema_prompt.py` | 4 | 事后打补丁，告诉模型"这几项别写这儿" |

提示词按第一份生成，执行按第二份卡，中间差 35 项。没有测试比对这两份表。

更糟的是当时的测试：

```python
def test_catalog_lists_every_changeable_param():
    assert len(changeable) == 51          # 51 来自同一张手抄表
```

它只证明"提示词和注册表抄得一样"，不证明改得动。全绿，功能是假的。

### 提示词怎么教模型踩坑

`_PARAM_EXAMPLES` 给 7 个参数配了可直接复制的 JSON，其中 5 个一写就报错：

| 示例 | 结果 |
|---|---|
| `{"field":"候选风机",...}` | 报错（无任何实现） |
| `{"field":"候选部件",...}` | 报错（无任何实现） |
| `{"field":"禁止新开工风机",...}` | 报错（无任何实现） |
| `{"field":"强制维修任务",...}` | 报错（正确位置是 `constraints.must`） |
| `{"field":"费用预算上限",...}` | 报错（正确位置是 `constraints.budget`） |
| `{"field":"补库延期量",...}` | 报错（无任何实现） |

示例是提示词里最强的指令形式——模型会照抄。于是"照说明书操作 → 必然报错"。

评测集也同源：70 条对抗用例里 25 条（36%）在考"能不能填出一个改不动的参数"。
这些用例无论模型多准，系统都会报错。

另外 `_parse_contract` 里的 `cardinality` 示例漏了必填的 `filter` 字段，
照抄会被校验器判为"缺少必需字段"。已补。

### 改了什么

1. `parameters.py` 新增 `APPLY_ROUTE`：每个参数登记落点
   （`parameters` / `objectives.strategy` / `constraints.budget` /
   `constraints.cardinality` / `constraints.must` / `unsupported`）。
   `is_changeable()` 唯一判据变成"有没有落点"，不再读设计分类。
2. `param_catalog()` 只列落点是 `parameters` 的 15 项；
   `redirect_block()` 给换节写的 4 项配正确示例；
   `unsupported_block()` 明说 32 项改不动，有替代出口的给出替代写法。
3. 校验器：写错节就是确定性错误，当场报"应写进 constraints.must"，
   不再放行到 `load_project` 才炸。
4. 提示词从 5163 字符降到 4584 字符（少了废话，多了边界）。
5. 评测集 25 条标 `status=not_implemented`，评测器单独统计不并入准确率。
   留在文件里当待实现清单——删掉等于把窟窿藏起来。

### 新增的防回归

`backend/tests/dsl/test_param_coverage.py`：

- `test_every_design_changeable_param_declares_a_route`：不许"归为可改但没说改到哪"
- `test_changeable_param_actually_applies`：19 项逐项走真实链路
- `test_unsupported_params_never_advertised`：改不动的不许出现在"你能改什么"
- `test_scored_cases_only_expect_writable_slots`：计分用例不许要求填改不动的参数
- `test_not_implemented_flag_is_not_a_dumping_ground`：不许拿 `not_implemented` 藏答错的用例

## 二、分阶段：阶段数没有定义，而且"高风险优先"被悄悄改了含义

### 现状（改之前）

`build_model` 里这一行决定阶段：

```python
stages.extend((s['指标'], s['方向'], metrics[s['指标']]) for s in template['分层目标']
              if partial or not s['指标'].endswith('完成数'))
```

`not xxx.endswith('完成数')` 本意是躲开 partial 模式前置那三段的重复，
实际效果是：**非部分排程时，模板里所有"完成数"阶段全被删掉**。

算出来的真实阶段（非 partial）：

| 策略 | 模板声明 | 实际执行 |
|---|---|---|
| 成本最低优先 | 4 段 | 4 段（`完成任务数` 不 endswith `完成数`，侥幸保住） |
| 高风险优先抢修 | 8 段 | **5 段，丢了"高/中/低严重完成数"** |
| 最短完成优先 | 4 段 | 4 段 |
| 检修最多器件优先 | 6 段 | 4 段，丢了高/中严重完成数 |

"高风险优先抢修"少了"先修高危数量最多"这一步，只剩"高危完工时间最早"，
是另一个目标，而模板里明明写着前者。

partial 模式更怪：前置 3 段 + 模板 3 段重复 → 高风险优先跑 11 段，其中 3 段重复。

### 阶段数到底几个

没有定义，也没有上限。它由两段拼成：

- **业务阶段** = 模板声明的顺序（去重后），当前 4~8 段；
- **决胜阶段** = 每 60 个选择变量一段，随任务数×候选数×线条数增长。

实测（基座01，11 项任务，60 秒预算）：

| 策略 | 业务阶段 | 决胜阶段 | 合计 |
|---|---|---|---|
| 成本最低优先 | 4 | — | 4 |
| 高风险优先抢修 | 8 | 39 | 47 |

决胜段是大头。它存在的理由是"同一最优值下取哪个解要可复现"，
不是业务目标，所以不该和业务阶段混在一个口径里谈"最多几段"。

### 有没有判断"两段就够"

没有。全部按模板跑完，一段不少。

能不能判断？通用的"够不够"提前判不了——第 k 段的最优值不跑不知道。
但有一类**可证明**的跳过，现在实现了：

- 同一指标前面已经优化过 → 跳（去重已经保证，兜底再挡一次）
- 该类别没有任务（比如没有"中"级任务却要优化"中严重完成数"）→ 跳

跳过会写进 `求解.阶段计划`，带原因。跑几段、跳几段、为什么，都能看到。

### 改了什么

1. 阶段去重按**指标名**做，不再按名字后缀猜。
2. `高风险优先抢修` / `检修最多器件优先` 恢复模板声明的完整阶段。
3. `partial` 前置段与模板重复的，只保留一份。
4. `求解` 里多三个字段：`阶段计划`、`计划阶段数`、`跳过阶段数`。

### 没改（已知，下一版）

- **时间预算没切分**：所有阶段共用同一个 `seconds`，前一段可以吃掉全部。
  实测成本最低优先第 3 段（最后完工时间）用了 34.23 秒 / 40 秒预算，
  后面的"完工时间和"根本没跑，整单判 `FEASIBLE`。
  改法是给每段配额，但会影响第一段（主目标）的求解质量，需要单独验证。

## 三、意图识别：大模型是第 7 顺位，不是第一顺位

### 实际链路

`app/core/dsl/llm_parser.py::_parse_core`：

```
1 批量句正则
2 parse_by_rules（规则）
3 _classify_not_change_only（关门）
4 parse_by_legacy（旧规划语言正则编译）   ← 命中即返回，置信度 1.0
5 _classify_non_change（关门）
6 向量模板命中
7 大模型
```

再往上，`agent_runtime.py:571` 还有一道 `is_planning_request`，
命中就把整句交给旧编译器，连 1~7 都不走。

所以"Agent First、大模型为主、规则兜底"是设计意图，当前实现是反的。

### 直接后果：整句被认领，后半句蒸发

```
输入：按成本最低优先排每天只能干8小时
规则层认领：是
输出：{"objectives":[{"type":"strategy","name":"成本最低优先"}], "solver":{...}}
      ↑ 工时改动不见，置信度 1.0，大模型全程没参与
```

同一句加逗号能救：

```
输入：按成本最低优先排，每天只能干8小时
拆句：["按成本最低优先排", "每天只能干8小时"]   ← parse() 拆开分别解析再合并
```

也就是说，复合句靠"按标点拆开分别解析"补救；没有标点就漏。
如果拆开的任一段抛异常，`parse()` 会静默退回整句规则解析，同样漏。

### 为什么不能只靠改提示词

提示词再准也管不到这条路——这些句子根本没送到大模型面前。

### 这一轮做了什么

只做了可见化，没动路由顺序：

- `backend/tests/dsl/test_intent_routing.py` 把链路顺序钉成测试；
- 漏词场景标 `xfail(strict=True)`，修好后测试会自己变红，提醒删标记。

不盲改的理由：改路由顺序会改变所有话术的延迟和结果，而本地没有 API key，
改完验证不了——那正是"说一套做一套"的做法。

### 建议的改法（下一版）

规则层只认领**完全消费**的句子：

1. 规则层给出结果的同时，报告"这句话里还有哪些片段没被消费"；
2. 有未消费片段 → 交出控制权给大模型，把已解析的部分作为初始 DSL 传下去合并
   （`merge_dsl` 已有）；
3. 大模型不可用时 → 退回规则层结果，并在回复里明说"这句话我只理解了前一半"。

判据可以先用一个便宜的近似：结果只有 `objectives` 一段、
而原句里还有数字+单位（小时/米/万/人/条/个），就当作没消费完。
