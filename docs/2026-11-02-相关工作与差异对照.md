# 相关工作与差异对照：重点在「用户意图 → 受控 DSL」

日期：2026-11-02
背景：README 目前没有 Related Work 一节。本文只回答一个问题——
**公开工作有没有解决「用户一句话 → 受控 DSL → 固定模型契约」这一步？**

## 0. 先纠正一个归类

上一轮把相关工作按「LLM 优化 agent」归类，偏了。本项目的核心不是 agent，
恰恰是**限制 agent**：LLM 只做翻译，不允许写模型代码，产物必须过确定性校验器。
工具循环、会话记忆、多方案对比、审批是外壳，不是这层的技术难点。

两边的判分口径也不在一个坐标系：

- 公开工作：最终数值对不对（pass@1、执行率、与最优值的误差、公式逐元素相等）。
- 本项目：状态诚实性、模型指纹重复性、证据链完整性。

## 1. 真正做「DSL 护栏」的（同类，2025–2026 才出现）

| 工作 | 机制 | 和我们差在哪 |
|---|---|---|
| **Shi et al.**, *IEEE T-ASE* 2025，[arXiv:2510.02679](https://arxiv.org/abs/2510.02679)，DOI 10.1109/TASE.2025.3596540；据 HKUST CSE 新闻获该刊年度最佳论文 | 车间调度。用 DSL 作为「符号护栏」约束 LLM 输出；双视图 DSL（工序视角 / 物料流视角）+ 下推自动机校验逻辑一致性（零件不能凭空出现）；再转成 OR-Tools 可解形式。对照两个纯 LLM 基线（MSL / TSL），Precision/Recall/F1 显著提升（配对 t 检验 p<.0001）。还做了自动适配算法：用 Dirichlet 过程混合模型 + EM，为新工厂自动「设计」DSL | **最接近的一篇**，动机和结论几乎可以照搬。但：DSL 由算法自动生成、场景是车间不是海上风电；没有参数落点注册表、没有消费点路由、没有固定模型契约与指纹，也没有审批/库存闭环。评测是在 10 个经典 JSP 上用 GPT-4o 造的自然语言描述 |
| **OptiDSL**, [arXiv:2608.07040](https://arxiv.org/abs/2608.07040)（2026-08），[代码](https://anonymous.4open.science/r/OptiDSL) | 主张「不是所有问题都该建成 MILP」。中间表示换成领域标准数据文件（VRPLIB 路径、OR-Library 调度/装箱、网络文件），LLM 两段式：先语义路由选模板，再填字段；再按问题类型分派精确/启发式/学习型求解器。44 类 COP 上宣称 formulation accuracy +51.66%、建模时间 −91.71% | 中间表示是**模板池**（有限个标准格式），不是可组合的生成器；没有确定性校验器、没有「能不能改」的注册判据。第三方评审（Pith）已指出：+51.66% 在披露 DSL→MILP 转换细节前无法解读，且基准与模板池对齐，需要独立题源复核 |
| **SDDL**, [arXiv:2608.18409](https://arxiv.org/abs/2608.18409)（2026） | 有界调度的形式化抽象 DSL，直接与 ConstraintLLM 的通用编程接口对比，主张形式化抽象能提升资源受限小模型的准确率 | 同方向，但仍是「小模型 + 受限 DSL」的准确率研究，不涉及参数落点、证据链、审批闭环 |
| **what_if_optimization**, [GitHub](https://github.com/iwasnothing/what_if_optimization) | Next.js + FastAPI + LangGraph + OR-Tools CP-SAT。LLM 把用户写的公式/约束翻成**严格结构化的 JSON 配置**，确定性引擎解析后求解，**从不执行生成的代码**；作者原话是「把 GenAI 当翻译，不是当程序员」 | 工程模式对上了，但是通用资源分配 what-if，schema 很浅；没有注册表驱动、没有落点/消费点、没有领域实体校验 |

## 2. 做「改一句话改模型」的（评测口径差得最远）

| 工作 | 机制 | 和我们差在哪 |
|---|---|---|
| **WIQOR**, ICLR 2025，[OpenReview](https://openreview.net/forum?id=no8ysO3xde) | 形式化定义了 **MPM 任务**：给「原问题自然语言描述 + 规范数学公式 + 一句 what-if 问题」，预测改后的规范公式。1946 个实例，来自 NL4Opt，部分超过 30 个决策变量。判分是**改后公式与标准答案逐元素相等**。GPT-4 在 Test-Base 76.15%，Llama-3.1-70B 最易题 69%、最难题 36% | 这就是「船租涨 20% 重排」的学术版，但只评**公式改对没改对**：没有校验器、不跑求解器、不管改了之后要重算哪一段、不产出可审计证据。它的 36% 恰好说明「让 LLM 直接改公式」在复杂题上不可靠 |
| **OR-Space**, [arXiv:2605.28158](https://arxiv.org/abs/2605.28158)（2026） | 持久工作区 + Build / Revise / Explain 三阶段；Revise 要求在新需求或求解器反馈下改模型且保留原有有效逻辑；失败归因到执行错、不可行、目标错、漏约束、解释不忠实 | 评测框架最接近「版本库 + 方案对比 + 报告」。但 Revise 改的是模型代码而非受控 DSL；缺「超时 ≠ 无解」和「同契约同结果」两个轴 |

## 3. 没解这个问题的主流（上一轮我列错重点的那批）

| 工作 | 它实际在做 | 为什么不算解了意图→DSL |
|---|---|---|
| **OptiMUS**（ICML 2024）、**Chain-of-Experts**（ICLR 2024）、**OR-LLM-Agent**（2025） | 自然语言 → LLM 写 Gurobi/Pyomo 求解器代码 → 执行 → 报错回炉 | 输出是自由代码，模型形状每次都变；正确性靠执行反馈，不靠业务规则 |
| **LLMOPT**（ICLR 2025） | 固定**五要素**表示（集合 / 参数 / 变量 / 目标 / 约束）+ 多指令微调 + 最多 12 轮自纠 | 五要素是最像「固定 schema」的学术版，但 LLM 仍输出整段求解器代码；自纠由执行报错驱动，**正确执行但语义错的模型会一直留着**；没有落点注册表、没有消费点路由 |
| **ORLM**（*Operations Research*）、**ConstraintLLM**（EMNLP 2025，[代码](https://github.com/william4s/ConstraintLLM)，IndusCP 140 题） | 合成数据微调，把建模能力压进权重；ConstraintLLM 额外做约束感知检索 CARM + Tree-of-Thoughts | 把能力压进权重，不是压进 DSL。ConstraintLLM 生成的是 PyCSP3 代码 |
| **Hasan et al.**（*Energy and AI* 2026，[代码](https://github.com/agushasan/LLM_Wind)） | Qwen3 本地 agent + 5 个工具（SCADA 查询、异常检测、物理校验、RAG、维护排程）；证明 grounding（每个数字可追到确定性过程）和 consistency（重复调用数值不变） | 机制是**函数调用**，不是受控 DSL；没有校验器、没有注册表。但它的「数字都有出处」是本项目最该引的同类主张 |
| **LLM4M**（*Engineering* 2026） | Qwen2.5-7B + LoRA，结构化槽位填风场布局/故障/班组，**直接生成维修计划**；与最优差 2% | 路线相反：让 LLM 当规划器，放弃最优性证明 |

## 4. 成熟得多的邻域：Text-to-SQL（这才是「意图 → 受控形式语言」被做透的地方）

本项目的 DSL 层本质是 **Text-to-DSL**，可以直接借它的评测口径与手段：

| 工作 | 可借的东西 |
|---|---|
| **PICARD**（EMNLP 2021，[arXiv:2109.05093](https://arxiv.org/abs/2109.05093)） | 生成过程中用增量解析挡掉不合法的词，同时查表名/列名是否存在（schema 检查）。不可用 SQL 从 12% 降到 2%，Spider 执行准确率 79.3%，单条 2.5s → 3.1s |
| **Grammar Prompting**（Wang 等） | 先让模型预测一段最小 BNF 语法，再用 Earley 解析器做约束解码。GeoQuery 程序准确率 60.7% → 69.6% |
| **GenLink**（EMNLP 2025）、**RAT-SQL** | schema linking：把用户话里的名字对到数据表里的行。对应本项目的「实体存在」校验 |
| **Track-SQL**（NAACL 2025，[代码](https://github.com/DMIRLAB-Group/Track-SQL)） | 多轮对话里跟踪 schema 与上下文变化，SParC / CoSQL 执行准确率 +7.1% / +9.55%。对应本项目的会话记忆「聊到后面还记得船租涨 20%」 |
| **Reliable Text-to-SQL**（2025） | 用保序 conformal 技术给 schema linking 正确率做概率保证，不确定时**主动拒答或找人确认**。对应本项目「没听懂就明说，不瞎猜」和「预览 → 确认 → 求解」 |
| **BIRD-Interact**（ICLR 2026 Oral，[官网](https://bird-bench.github.io)） | 交互式 text-to-SQL 评测；最强模型成功率仅 16.33%。说明「多轮改约束」本身是公认难题，不是本项目想多了 |

## 5. 我们这层有什么是公开工作里没有的

1. **落点决定「能不能改」，且提示词由注册表自动生成。**
   `dsl_core/registry/parameters.py` 的 `APPLY_ROUTE` 是唯一事实来源：
   没落点的参数 `is_changeable()` 为假；`schema_prompt.py` 据此拼 L0 目录 / L1 详述 / L2 原语，
   并把 `unsupported` 明写进提示词让模型别试，其中 8 项还登记了替代出口（`UNSUPPORTED_HINT`）。
   文献里的 schema 只描述**形状**，不决定**可改性**，更不会反向生成提示词。
   这条直接堵掉了历史上「提示词说 51 项能改、执行侧只认 16 项」那个坑。

2. **消费点路由：编译期就决定「重跑哪一段」。**
   `consumption_point()` 按 `candidates`（生成层/时间维度）还是 `build_model`（选择层/成本组合维度）分流。
   改「船租」→ 复用候选，只重建模型；改「齿轮箱工时」→ 必须重生成候选。
   WIQOR 只管公式改对没改对，不管改动的**重算代价**；这是本项目独有的编译期决策。

3. **完备性靠生成器，不靠枚举。**
   `docs/2026-10-29-milp-controlled-dsl-design.md` §5.2：可引用量 = 数学形式 × 系数 × 过滤维度，
   注册表登记的是「三个有限维度 + 编译定义」，任意合法三元组都能编译成 CP-SAT 表达式。
   OptiDSL 是有限模板池，Shi et al. 是双视图固定 DSL，都不做这种可组合完备性论证。

4. **三层解析的确定性降级 + 确定性拒。**
   规则层（高频话术正则直出，零成本零延迟）→ 向量层（已验证模板检索 few-shot）→ LLM 层（新话术兜底），
   前两层不联网；`dsl_core/validator.py` 不调 LLM，只验实体存在、原语在册、可引用量合法、线性、系数有限、界合法。
   文献要么全靠 LLM，要么全靠规则；RTS 的拒答是概率保证，这里是确定性拒。

5. **原话 ↔ DSL 对账：直接核查「意图到 DSL」这一跳本身。**
   `dsl_core/utterance.py` 不判「模型理解对不对」（那要另一个模型打分，不可证明），
   只判能用集合/算术判死的三类：数量上限、对象（排除/范围/先后）、数值（日期、工时）。
   三态：违例 → 不出方案；未核对 → 抽到断言但缺信息；通过 → 每条都有落点，
   且**一条断言都没抽到时不算通过**。违例会在预览前清空待确认变更，求解前再核一次。
   **这一条是「用户意图 → DSL」转换正确性的直接核查，公开工作里没有对应物**：
   WIQOR 只比改后公式与标准答案；OR-Space 的 Revise 改的是模型代码；
   Reliable Text-to-SQL 的拒答是 conformal 概率保证，不核对已生成的 DSL。

## 6. 两篇最该引的「弹药」，以及一个诚实的技术判断

- **When Words Change the Model: Sensitivity of LLMs for Constraint Programming Modelling**
  （Springer，[DOI 10.1007/978-3-032-41269-0_6](https://doi.org/10.1007/978-3-032-41269-0_6)）：
  把 10 个 CSPLib 问题改写措辞、加入无关干扰信息但保持结构不变，LLM 生成的模型明显退化；
  作者还怀疑标准基准被训练数据污染。这是「让 LLM 自由写模型不可靠」最直接的实验证据，
  正好支持本项目「把措辞变化消化在翻译层、模型契约不动」的设计。

- **PICARD / 约束解码** 是本项目当下最明确的升级方向：
  现在走的是「先生成、再校验、错了重来」（validation-retry），
  可以换成「解码时按 DSL 语法把不合法的词挡掉」（valid by construction）。
  但有两个不能绕开的边界：
  1. 约束解码只保证**形状**，不保证**内容**——实体存在、落点、线性这三类检查必须留着，不能用它替代；
  2. 它需要在解码时改写词表概率，只有自托管模型或开放该模式的厂商能做。
     本项目当前走 DeepSeek 的 Anthropic 兼容端点，拿不到这个控制权，
     所以现阶段保持 validation-retry 是正确的取舍，不该为了「看起来更强」硬上。

## 7. 可以写进 README 的一句话定位

> 与「LLM 直接生成求解器代码」的路线（OptiMUS、LLMOPT、ORLM、ConstraintLLM）不同，
> 本系统把 LLM 限定为自然语言到受控 DSL 的翻译器：可改字段由带落点的注册表唯一决定，
> 产物过确定性校验器，再由消费点路由决定重算范围，最后编译进形状固定的 CP-SAT 模型契约。
> 同类思路见 Shi et al.（IEEE T-ASE 2025）与 OptiDSL（2026），
> 但二者均未涉及参数落点、消费点路由、状态诚实性与审批/库存证据链。
