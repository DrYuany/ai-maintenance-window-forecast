# 受控 DSL 设计方案 v0.3：检修排程 Agent 的动态定制

日期：2026-10-29
状态：设计草案 v0.3（替代 v0.2）
范围：自然语言 → 受控 DSL → CP-SAT 模型，覆盖"任意线性约束/目标"的动态定制

---

## 0. 版本说明

**v0.2 的问题：**
1. 四张注册表是"从代码和模板里摘的"，不是从第一性推的。
2. 实体列错：严重度不是实体（是属性），漏了人员和时间。
3. "11 个可引用指标"是 build_model 的历史产物，不是第一性清单。
4. "参数"误以为只有 115 项——那只是系统参数表；部件/任务/库存/时序字段是另一回事。
5. 原语清单是随手挑的 8 个糖，不是按维度推的。

**v0.3 的核心：第一性三元骨架——"实体 × 可引用量生成器 × 原语维度"。**
注册表不再是清单，而是生成器；完备性靠生成器保证，不靠枚举。

---

## 1. 背景与目标

把当前"写死约 13 类旋钮 + 固定 4 套目标模板"升级为"有限原语的可组合空间"，
让用户**只要能用 MILP 线性形式表达的需求都能被满足**，同时保持确定性、可复现、可审计。

三条不可退让的原则：
- 大模型只做"翻译"（自然语言 → DSL 结构），不做"判断合法"。
- 确定性校验器只放行"线性 + 实体存在 + 注册表内引用"的 DSL。
- 编译产物仍然进模型指纹与证据链，同一输入同一输出。

---

## 2. 第一性框架：输入 / 时间维度 / 组合维度

```
输入数据 ──▶ 候选生成（时间维度） ──▶ 模型构建（成本 + 组合维度）
 ①部件参数表     g(时间点, 部件表, 时序)     选择 + 全局耦合
 ②基础时序数据
```

**候选生成的本质是"时间维度"**：对单个任务，唯一的独立自由度是"开工时间点"，
候选的完成、作业段、下项最早开始全部由开工时间点唯一决定；成本是时间的**派生量**。

成本经两条时序链路派生：
1. 海况 → 工时膨胀 → 人工成本（恶劣海况下同一份活干得更久）
2. 时序 → 电价 × 风速 → 发电损失（修复越晚损失越大）

---

## 3. 候选生成机制与全局最优性

### 3.1 候选生成（时间维度）

对每个任务枚举所有可行开工时间点（60 分钟粒度），每个时间点唯一确定候选的
（开始、完成、作业段、下项最早开始）。作业段模拟逐天展开：海况差则跳过当天、
工时膨胀、跨天切段。

### 3.2 全局最优性

候选生成只裁剪"单任务自身不可行"的干法（海况差、超工时、超期限、超窗口），
这些候选无论别的任务怎么选都永不入最优解，裁剪不丢最优。

全局约束（不重叠、库存、预算）全部留在 0-1 模型里，**没有**被塞进候选。
因此 0-1 模型的可行域 = 所有可行组合，CP-SAT 分支定界返回 `OPTIMAL` 即证明全局最优。

**唯一非最优来源：开工时间被离散成 60 分钟一档**（粒度取舍，非思路缺陷）。

## 5. 第一性三元骨架（v0.3 核心）

### 5.1 实体（7 个）

**实体 = 有身份、能被用户点名引用的东西：**

| 实体 | 身份 | 用户引用方式 |
|---|---|---|
| 任务 | 任务编号 | "任务018" |
| 风机 | 风机编号 | "风机001" |
| 部件 | 部件编号/名称 | "齿轮箱" |
| 窗口 | 窗口编号 | "窗口02" |
| 作业线/船 | 线编号 | "2号船" |
| 人员 | 当前仅总数（预留个体身份） | "30人" / "明天只有5人" |
| 时间（日/小时） | 日期/时刻 | "11月8日"、"明天" |

**不单独设"属性"类别。** 严重度、海况等分类标签不是实体，也不是需要单独枚举的属性清单——
它们是 §5.2 过滤维度的**取值**。过滤维度的完整来源是**候选字段本身**：
候选 dict 携带 `任务编号/风机编号/部件编号/严重等级/窗口编号/开始/完成/作业线`，
由此派生出全部 7 个可过滤维度（任务/风机/部件/严重度/窗口/日/线），
不多不少，不需要再凭空列举"属性"。

### 5.2 可引用量生成器（不是 11 个清单）

模型决策变量是 `x_{i,k,l}`（任务 i 选候选 k 上线 l），**一切可引用量都是 x 的线性函数**。
可引用量 = **数学形式 × 过滤维度**，是生成器而非枚举清单：

| 数学形式 | 表达式 | 例子 |
|---|---|---|
| 选择 Σx | Σx（可加过滤） | y_i（任务i排入）、完成数 |
| 加权和 Σc·x | c ∈ {完成, 开始, 工时, 人工成本, 备件成本, 其他费用, 发电损失} | 完工时间和、人工成本、发电损失 |
| 极值 max | max(Σc·x)，需辅助变量 | 最后完工时间 |
| 派生辅助 | 需辅助变量 | 船租、某线某天占用、某部件某时刻消耗 |

**过滤维度 = 实体的属性**（7 个）：任务 / 风机 / 部件 / 严重度 / 窗口 / 日 / 线。

**生成器规则：任意"数学形式 × 任意过滤组合"都是合法可引用量。**

原来的"11 个指标"只是这个生成器的特例：
- 总经济成本 = Σ(人工+备件+其他+发电损失+船租)·x 无过滤
- 完成任务数 = Σx 无过滤
- 高严重完成数 = Σx 过滤(严重度=高)
- 最后完工时间 = max(Σ完成·x) 无过滤
- 现金支出 = Σ(现金项)·x 无过滤
- ……

**完备性靠生成器保证，不靠枚举清单。** 校验器只需要验证"形式合法 × 过滤维度合法"，就能覆盖任意线性量。

**生成器如何实现与注册**（生成器是代码，注册的是它的参数空间）：

| 维度 | 注册内容 | 实现 |
|---|---|---|
| 数学形式（4 种） | Σx / Σc·x / max / 派生辅助 | 每个形式一个**编译函数**：形式 × 过滤 → CP-SAT 表达式 |
| 系数类型（7 种） | 完成/开始/工时/人工/备件/其他费用/发电损失 | 每个系数一个"**从候选字段提取**"的定义 |
| 过滤维度（7 个） | 任务/风机/部件/严重度/窗口/日/线 | 每个维度一个"**候选匹配**"的定义 |

注册表 = 这三个维度的**合法组合 schema**（哪些形式×哪些系数×哪些过滤是合法的）。
校验器用它验证 LLM 生成的（形式, 系数, 过滤）三元组；编译器用生成器代码把合法三元组
编译成 CP-SAT 表达式。**注册的不是"无穷多个量"，而是"三个有限维度 + 编译定义"。**

**量的引用语法（目标与约束通用，不是某个原语特有的）：**
- **具名量（糖）**：`"现金支出"` —— 具名量注册表登记"名字 → 生成器表达式"的展开，
  原 11 个指标是首批具名量，业务可注册新名字。
- **原始三元组**：`{"form":"sum","coeff":"人工成本","filter":{"severity":"高"}}` ——
  不具名的量直接写（形式, 系数, 过滤）。
- 编译器统一把具名量展开成三元组，再编译成 CP-SAT 表达式。

### 5.3 原语（按"约束触及的维度"七类）

| 维度 | 原语 | 语义 | 编译结果 |
|---|---|---|---|
| 选择 | `must(task)` / `exclude(task)` | 必修 / 排除 | y=1 / y=0 |
| 选择 | `at_most_one(tasks)` / `at_least_one(tasks)` | 分组选择 | Σy≤1 / Σy≥1 |
| 关系 | `precedence(A, B, gap=0)` | A 先于 B（可带间隔） | finish(A)+gap ≤ start(B) |
| 关系 | `co_occur(mode, tasks)` | 同/不同 窗口·天·船 | 指示变量线性式 |
| 资源 | `no_overlap(resource, tasks)` | 不重叠 | CP-SAT NoOverlap |
| 资源 | `capacity(resource, time, limit)` | 容量上限 | Σ占用 ≤ limit |
| 资源 | `fix(task, 线)` | 固定作业线/船 | Σx(line≠l)=0 |
| 计数 | `cardinality(filter, op, N)` | 计数上下限 | Σx(filter) op N |
| 时间 | `deadline(task, time)` | 最晚完工 | finish ≤ time |
| 时间 | `earliest(task, time)` | 最早开工 | start ≥ time |
| 时间 | `forbidden_dates(dates)` | 禁开工日期 | Σx(day∈dates)=0 |
| 成本 | `budget(量, op, bound)` | 预算 | 量 op bound |
| 兜底 | `linear(terms, op, bound)` | 任意线性不等式 | Σcoef·量 op bound |

### 5.4 三者串联

```
约束/目标 = 原语(可引用量) = 原语(生成器(数学形式, 过滤维度))
```

例："高严重任务的人工成本不超过 50 万"
= `budget( Σ工时·x 过滤(严重度=高) ×人工单价, ≤, 500000 )`
= 原语 `budget` + 可引用量 `加权和·过滤(严重度=高)`

目标同理：
- "先最小化现金支出，再最大化高严重完成数"
  = `lexmin([ (Σ现金·x 无过滤, min), (Σx 过滤(严重度=高), max) ])`

## 7. 路由判据与端到端机制

### 7.1 三层机制（解析 ≠ 路由）

```
自然语言 ──(a) 解析──▶ DSL JSON ──(b) 确定性校验 ──▶ 合法 DSL ──(c) 路由+编译 ──▶ 模型
```

- **(a) 解析**：LLM 为主（覆盖任意自然语言→线性约束）；**正则只做高频参数改动的快速路径**
  （"船租涨 20%"这类确定性极高的话术正则直出，省一次 LLM 调用）。
  现有 planning_intent.py 的正则是这条路的前身，从"纯正则"升级为"正则兜底 + LLM 主解析"。
- **(b) 校验**：确定性，验实体存在、可引用量形式/过滤合法、线性、系数有限、界合法。
- **(c) 路由 + 编译**：**纯注册表查表**。DSL 引用的每个输入都有"消费点"字段，
  汇总所有被改输入的消费点：含 `candidates` → 重新生成候选 + 重建模型 + 求解；
  只含 `build_model` → 复用候选，只重建模型 + 求解。**这层既不是正则也不是 LLM，是一张表 lookup。**

### 7.2 消费点拆分的依据

`candidates()` 读的输入（时间维度）：部件工时、任务期限、窗口起止、海况、每天开始/结束时间、每日工时上限、转移时间。
`build_model()` 读的输入（成本/组合维度）：船租、人工、作业线、人员、备件成本、其他费用、风速电价、约束、目标。

**关键**：时序数据不是铁板一块——海况决定"时间维度"（生成层），风速/电价决定"成本维度"（选择层）。

### 7.3 端到端示例

用户："先修风机001再修风机003，船租涨20%"

```
(a) 解析（LLM 或正则）→ DSL：
  {"constraints": [{"type":"precedence","before":"任务018","after":"任务022"}],
   "parameters": [{"field":"船舶日租金","op":"*","value":1.2}]}
(b) 校验：任务018/022 存在 ✓；precedence 原语合法 ✓；船租字段在注册表 ✓
(c) 路由：precedence → build_model；船租 → build_model
    → 均不含 candidates → 复用候选，只重建模型求解（快路径）
```

对比："齿轮箱工时涨20%" → 部件库.工时 → 消费点=candidates → 重新生成候选（慢路径，正确性要求）。

## 8. DSL 原语设计

### 8.1 目标原语

**第一性：目标 = 对可引用量做最优选择。组合自由度只有两种本质——单量、字典序；加权是糖。**

| 原语 | 本质 | 编译 |
|---|---|---|
| `minimize(q)` / `maximize(q)` | 单个量直接最优 | `model.Minimize/Maximize(q)` |
| `lexmin([(q₁,d₁),(q₂,d₂),…])` | 多个量按严格优先级 | stages 循环（解→冻结→再解） |
| `weighted([(w₁,q₁),…])` | 糖 = minimize(加权和复合量) | 各量按界标准化后线性合成，再 minimize |

**完备性论证**：模型的目标是 `x` 的线性函数，任意"目标组合"只有三种——
一个量（minimize/maximize）、多个量按优先级（lexmin）、多个量线性合成（weighted）。
没有第四种：非线性权衡会破坏线性性，本来就不允许。

**为什么目标原语比约束原语少**：约束要触及模型的各个维度（选择/关系/资源/计数/时间/成本），
所以有七维度糖；目标只做一件事——对量取最优，"对什么量"由 §5.2 生成器负责，
"怎么组合"只有两种本质。`q` 的引用语法见 §5.2（具名量或原始三元组）。

```json
{"type": "lexmin", "stages": [
  {"q": "现金支出", "dir": "minimize"},
  {"q": "高严重完成数", "dir": "maximize"}]}
{"type": "weighted", "weights": {"总经济成本": 0.7, "完成任务数": 0.3}}
```

`lexmin` 直接编译成 `stages` 列表，喂给不变的"解→冻结→再解"循环；
`weighted` 展开为"标准化加权和"一个线性量后走 `minimize`。

### 8.2 约束原语（§5.3 的七维度完整清单）

核心 `linear` + 七维度高层糖（选择/关系/资源/计数/时间/成本），每个糖都编译成 `linear`。
完备性由"七维度 × 可引用量生成器"保证，不靠堆原语数量。

### 8.3 校验器（"受控"的命门）

1. **实体存在**：引用的任务/风机/部件/窗口/线/日期都在快照里。
2. **可引用量合法**：数学形式 ∈ {Σx, Σc·x, max, 派生}；过滤维度 ∈ 实体属性。
3. **线性**：只允许"系数 × 量，求和，比常数"——出现 `x·y`、`|x|`、`1/x` 一律拒绝。
4. **系数有限、界合法**：常数且有限；界为合法数值。

## 9. 动态场景完备性清单（23 个 = 原 16 + 补 7）

**补 7 个（v0.2 列为"缺口"却未入表的）：**

## 10. 完备性判据总结

| 层 | 锚 | 完备判据 |
|---|---|---|
| 实体 | 7 实体 + 2 属性 | 约束/目标里出现的名词都能引用 |
| 可引用量 | 生成器（形式 × 过滤） | 任意线性量可表达，不靠枚举 |
| 原语 | 七维度 | 任意线性约束/目标可表达 |
| 输入数据 | 表 × 字段注册表 | 每个有业务意义、模型消费的字段都能改 |
| 动态场景 | 23 场景 × 原语对照 | 计划员会改的维度都落到注册字段或原语 |

LLM 只能在注册表内引用、校验器只放行线性表达式，从而**既完备又受控**。
