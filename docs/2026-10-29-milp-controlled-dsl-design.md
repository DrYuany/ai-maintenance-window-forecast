## 1. 背景与目标

把当前"写死约 13 类旋钮 + 固定 4 套目标模板"升级为"有限原语的可组合空间"，
让用户**只要能用 MILP 线性形式表达的需求都能被满足**，同时保持确定性、可复现、可审计。

三条不可退让的原则：
- 大模型只做"翻译"（自然语言 → DSL 结构），不做"判断合法"。
- 确定性校验器只放行"线性 + 实体存在 + 注册表内引用"的 DSL。
- 编译产物仍然进模型指纹与证据链，同一输入同一输出。

---

## 2. 第一性框架：输入 / 时间维度 / 组合维度

从业务第一性出发，整个求解分三段（不是"参数/数据/约束"）：

```
输入数据 ──▶ 候选生成（时间维度） ──▶ 模型构建（成本 + 组合维度）
 ①部件参数表     g(时间点, 部件表, 时序)     选择 + 全局耦合
 ②基础时序数据
```

**候选生成的本质是"时间维度"**：对单个任务，唯一的独立自由度是"开工时间点"，
候选的完成、作业段、下项最早开始全部由开工时间点唯一决定；成本是时间的**派生量**。

成本经两条时序链路派生：
1. 海况 → 工时膨胀 → 人工成本（恶劣海况下同一份活干得更久）
2. 时序 → 电价 × 风速 → 发电损失（修复越晚损失越大）

---

## 3. 候选生成机制与全局最优性

### 3.1 候选生成（时间维度）

对每个任务枚举所有可行开工时间点（60 分钟粒度），每个时间点唯一确定候选的
（开始、完成、作业段、下项最早开始）。作业段模拟逐天展开：海况差则跳过当天、
工时膨胀、跨天切段。

### 3.2 全局最优性

候选生成只裁剪"单任务自身不可行"的干法（海况差、超工时、超期限、超窗口），
这些候选无论别的任务怎么选都永不入最优解，裁剪不丢最优。

全局约束（不重叠、库存、预算）全部留在 0-1 模型里，**没有**被塞进候选。
因此 0-1 模型的可行域 = 所有可行组合，CP-SAT 分支定界返回 `OPTIMAL` 即证明全局最优。

**唯一非最优来源：开工时间被离散成 60 分钟一档**（粒度取舍，非思路缺陷）。

## 6. 路由判据：什么请求影响候选生成

**判据：用户请求改的输入，被 `candidates()`（时间维度）消费还是 `build_model()`（成本/组合维度）消费。**

三步机械判断：
1. 是不是"改"请求？不是 → 只读查询，不动候选也不求解。
2. 是 → 改的输入在注册表里的"消费点"是哪？
   - 含 `candidates` → **重新生成候选 + 重建模型 + 求解**
   - 只含 `build_model` → **复用候选，只重建模型 + 求解**（省掉最贵的枚举）
3. "消费点"由代码客观决定，注册表如实记录。

| 用户请求 | 消费点 | 重建候选？ |
|---|---|---|
| 船租上涨 20% / 最多两条线 / 人工单价改成 300 | build_model | 否 |
| 齿轮箱工时上涨 20% / 叶片 5 号到货 / 严重故障 8 号前修完 | candidates | **是** |
| 明天风变大（海况）/ 窗口提前 | candidates | **是** |
| 未来三天电价上涨 | build_model（发电损失） | 否 |
| 先修 001 再修 003 / 先最小化现金支出 | build_model | 否 |

**关键**：时序数据不是铁板一块——海况决定"时间维度"（生成层），风速/电价决定"成本维度"（选择层）。

## 7. DSL 原语设计

### 7.1 目标原语

```json
{"type": "lexmin", "stages": [
  {"metric": "现金支出", "direction": "minimize"},
  {"metric": "高严重完成数", "direction": "maximize"}]}
{"type": "weighted", "weights": {"总经济成本": 0.7, "完成任务数": 0.3}}
{"type": "minimize", "expr": {"terms": [{"coef": 1.0, "ref": "高严重完工时间和"}]}}
```

- `metric` / `ref` ∈ 已注册指标（11 个），或自定义线性表达式。
- `lexmin` 直接编译成 `stages` 列表，喂给不变的"解→冻结→再解"循环。

### 7.2 约束原语（核心 `linear` + 高层糖）

**核心原语（完备性保证者）：**

```json
{"type": "linear", "expr": {"terms": [{"coef": 1.0, "ref": "高严重完成数"},
                                        {"coef": 2.5, "ref": "现金支出"}]},
 "op": "<=", "value": 8000000}
```

**完备性定理（非形式化）**：选择层是 0-1 线性整数规划，其可加约束类 = `x` 上的线性不等式；
`linear` 原语能表达任意线性不等式，故完备。

**高层糖（编译到 `linear`）：**

| 原语 | 语义 | 编译结果 |
|---|---|---|
| `precedence(A, B, gap=0)` | A 先于 B（可带间隔） | `finish(A)+gap ≤ start(B)` |
| `co_occur(不同天, A, B)` | 互斥/不同天 | 指示变量线性式 |
| `co_occur(同窗口, A, B)` | 合并同窗口 | 指示变量线性式 |
| `budget(指标 ≤ 界)` | 预算 | `metric ≤ value` |
| `cardinality(完成数 ≥ N)` | 计数 | `count ≥ N` |
| `must_schedule(task)` / `exclude(task)` | 必修/排除 | `y = 1` / `y = 0` |
| `fix_line(task, 线)` | 固定作业线 | `Σx(line≠l) = 0` |
| `exclude_before(task, 时刻)` | 最早开工 | `Σx(start<时刻) = 0` |

### 7.3 校验器（"受控"的命门）

1. 每个 `ref` / `metric` 都在注册表（实体存在、指标存在）。
2. 系数有限、为常数（不能是变量的函数）。
3. 只允许"系数 × 项，求和，比常数"——出现 `x·y`、`|x|`、`1/x` 一律拒绝。
4. 界是合法数值。

完备地覆盖线性类，硬性排除非线性类。

## 8. 动态场景完备性清单（维度 × 计划员说法 × DSL 原语）

现有 16 个动态场景覆盖了 7 个主维度，但各维度内有叶子缺失。下列对照表是"动态场景是否完备"的客观依据。

### 单任务约束
| 计划员会说 | 覆盖 | 缺口 → 原语 |
|---|---|---|
| 任务018必须修 | ✅ 强制维修 | — |
| 风机001先别动 | ✅ 禁止新开工风机 | — |
| 任务018 11月8日前修完 | ✅ 指定截止 | — |
| 只用窗口02 | ✅ 固定窗口 | — |

| 计划员会说 | 覆盖 | 缺口 → 原语 |

### 资源约束（第二缺）
| 计划员会说 | 覆盖 | 缺口 → 原语 |
|---|---|---|
| 最多3条船 / 30人 | ✅ 作业线/人员上限 | — |
| 最多租20艘天 | 🚧 场景08 | 待扩展 |

| 明天只有5人出海 | ❌ | `capacity(人员, 该日)` |

### 预算/成本
| 计划员会说 | 覆盖 | 缺口 → 原语 |
|---|---|---|
| 总费用≤500万 | ✅ 预算 | — |
| 人工费单独≤50万 | ❌ | `budget(人工成本)`（需注册"人工成本"量） |
| 船租涨20% | ✅ 参数 | — |

### 时间/窗口
| 计划员会说 | 覆盖 | 缺口 → 原语 |
|---|---|---|
| 11月6号别开工 | ✅ 禁止开工日期 | — |
| 这几个任务拖到下窗口 | 🚧 延期范围 | 待扩展 |

### 天气/环境
| 计划员会说 | 覆盖 | 缺口 → 原语 |
|---|---|---|
| 安全风速阈值改11 | ✅ 安全参数（生成层） | — |
| 风速整体+20%排程怎么变 | ❌ | 场景倍率（同发电倍率做法） |
| 风速超10别排高风险 | ❌ | ⚠️ 条件约束，需 indicator |

### 风险
| 计划员会说 | 覆盖 | 缺口 |
|---|---|---|
| 故障概率/后果 | 🚧 风险构件 | 概率×损失，非线性 |

**结论**：缺失的绝大多数（互斥、最早开工、固定船、最小间隔、资源时段可用性、分项预算、天气敏感性）都能用 `linear/co_occur/precedence/budget/cardinality/exclude/fix_line` 覆盖，因为它们在数学上都是"候选选择上的线性约束"。只有三类超出线性 DSL：备件预留到任务、天气条件约束、风险概率×后果。

## 9. 完备性判据总结

| 层 | 锚 | 完备判据 |
|---|---|---|
| 输入数据（部件表+时序） | 实体/时序字段注册表 | 每个有业务意义、模型消费的字段都能改 |
| 候选生成（时间维度） | 算法正确性 | 给定任意输入，能正确算出候选时间+成本 |
| 模型构建（组合维度） | 指标注册表 + `linear` 原语 | 任意线性不等式/目标可表达 |
| 动态场景 | 维度 × 原语对照表 | 计划员会改的维度都落到注册参数或 DSL 原语 |

完备性靠"注册表 + 一个线性原语"锚定，不靠堆原语数量。LLM 只能在注册表内引用、
校验器只放行线性表达式，从而**既完备又受控**。

## 10. 实施分期

- **第一期（推荐）**：`linear` + `lexmin` + `weighted` + 高层糖 + 校验器，覆盖组合维度（选择层）。
  同时把 §8 里"互斥/最早开工/固定船/最小间隔/分项预算"这几个高频缺口补上（它们都是线性约束）。
  生成层复用现有 `overrides + data_patches`，不新增原语。
- **第二期**：把 data_patches 补全为"实体字段注册表"，补时序数据（海况/逐时/窗口）的假设修改。
- **第三期**：生成层规则参数化（时间粒度、海况判定、跨窗口），以及"待扩展"的风险/天气条件/备件预留构件。
