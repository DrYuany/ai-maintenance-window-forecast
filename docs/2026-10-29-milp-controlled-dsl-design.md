# 受控 DSL 设计方案：检修排程 Agent 的动态定制

日期：2026-10-29
状态：设计草案 v0.1
范围：自然语言 → 受控 DSL → CP-SAT 模型，覆盖"任意线性约束/目标"的动态定制

---

## 1. 目的

把当前"写死的约 13 类旋钮 + 固定 4 套目标模板"升级为"有限原语的可组合空间"，
让用户只要能用 **MILP 线性形式** 表达的需求都能被满足，同时保持确定性、可复现、可审计。

核心约束（不可退让）：
- 大模型只做"翻译"（自然语言 → DSL 结构），不做"判断合法"。
- 确定性校验器只放行"线性 + 实体存在 + 注册表内引用"的 DSL。
- 编译产物仍然进模型指纹与证据链，同一输入同一输出。

---

## 2. 第一性框架：输入 / 时间维度 / 组合维度

从业务第一性出发，整个求解分成三段，比"参数/数据/约束"的分类更贴近本质：

```
输入数据 ──▶ 候选生成（时间维度） ──▶ 模型构建（成本 + 组合维度）
 Part1 部件表    g(时间点, 部件表, 时序)     选择 + 全局耦合
 Part2 时序数据
```

**候选生成的本质是"时间维度"**：对单个任务，唯一的独立自由度是"开工时间点"，
候选的完成、作业段、下项最早开始全部由开工时间点唯一决定；成本是时间的**派生量**。

成本经两条时序链路派生：
1. 海况 → 工时膨胀 → 人工成本（恶劣海况下同一份活干得更久）
2. 时序 → 电价 × 风速 → 发电损失（修复越晚损失越大）

---

## 3. 全局最优性

候选生成只裁剪"单任务自身不可行"的干法（海况差、超工时、超期限、超窗口），
这些候选无论别的任务怎么选都永不入最优解，裁剪不丢最优。

全局约束（不重叠、库存、预算）全部留在 0-1 模型里，**没有**被塞进候选。
因此 0-1 模型的可行域 = 所有可行组合，CP-SAT 分支定界返回 `OPTIMAL` 即证明全局最优。

唯一非最优来源：**开工时间被离散成 60 分钟一档**（粒度取舍，非思路缺陷）。

---

## 4. 三层可改维度全表（含"消费点"，这是路由判据的唯一来源）

"消费点"这一列是客观事实：由 `candidates()` / `build_model()` 实际读哪些输入决定，
不是拍脑袋的分类。它直接回答"改这个要不要重新生成候选"。

### 4.1 Part 1 —— 部件参数表（实体行）

| 字段 | 现状 | 消费点 | 改后是否重新生成候选 |
|---|---|---|---|
| 6 种维修工时 | ✅ part_hours | candidates | **是** |
| 维修包成本 | ❌ | build_model | 否 |
| 其他费用 | ❌ | build_model | 否 |
| 固定维修人数（现强制=1） | ❌ | 建模假设 | 需改模型 |
| 每任务备件数量（现强制=1） | ❌ | 建模假设 | 需改模型 |
| 剩余出力系数 | ❌ | build_model | 否（偏物理，可声明不开） |

### 4.2 Part 2 —— 时序/结构数据

| 字段 | 现状 | 消费点 | 改后是否重新生成候选 |
|---|---|---|---|
| 海况（风速/波高/可用小时） | ❌ | candidates | **是**（可行性 + 工时膨胀） |
| 海事窗口（开始/结束） | ❌ | candidates | **是** |
| 逐时风速/电价 | ❌ | build_model（发电损失） | 否 |

**关键**：时序数据不是铁板一块。海况决定"时间维度"（能不能干、干多久）→ 生成层；
风速/电价决定"成本维度"（发电损失）→ 选择层。

### 4.3 Part 3 —— 模型

| 维度 | 内容 | 完备判据 |
|---|---|---|
| 时间维度（候选生成） | 开工时间点 + 单任务物理规则 | 给定任意输入，能正确算出候选时间+成本 |
| 组合维度（模型构建） | 任务选时间点 + 全局耦合 | 任意线性不等式可表达（见 §6） |

## 6. DSL 原语设计

### 6.1 目标原语

```json
{"type": "lexmin", "stages": [
  {"metric": "现金支出", "direction": "minimize"},
  {"metric": "高严重完成数", "direction": "maximize"}]}
{"type": "weighted", "weights": {"总经济成本": 0.7, "完成任务数": 0.3}}
{"type": "minimize", "expr": {"terms": [{"coef": 1.0, "ref": "高严重完工时间和"}]}}
```

- `metric` / `ref` ∈ 已注册指标（11 个：总经济成本、现金支出、完成任务数、最后完工时间、
  完工时间和、高/中/低严重完成数、高/中/低严重完工时间和），或自定义线性表达式。
- `lexmin` 直接编译成 build_model 的 `stages` 列表，喂给那个不变的"解→冻结→再解"循环。

### 6.2 约束原语（核心 `linear` + 高层糖）

**核心原语（完备性保证者）**：

```json
{"type": "linear", "expr": {"terms": [{"coef": 1.0, "ref": "高严重完成数"},
                                        {"coef": 2.5, "ref": "现金支出"}]},
 "op": "<=", "value": 8000000}
```

**完备性定理（非形式化）**：选择层是 0-1 线性整数规划，其可加约束类 = `x` 上的线性不等式；
`linear` 原语能表达任意线性不等式，故完备。

**高层糖（编译到 `linear`）**：

| 原语 | 语义 | 编译结果 |
|---|---|---|
| `precedence(A, B)` | A 先于 B | `finish(A) ≤ start(B)` |
| `co_occur(不同天, A, B)` | 不同天 | 两个指示变量的线性式 |
| `budget(指标 ≤ 界)` | 预算 | `metric ≤ value` |
| `cardinality(完成数 ≥ N)` | 计数 | `count ≥ N` |
| `must_schedule(task)` | 必修 | `y = 1` |
| `exclude(task)` | 排除 | `y = 0` |

### 6.3 校验器（"受控"的命门）

1. 每个 `ref` / `metric` 都在注册表（实体存在、指标存在）。
2. 系数有限、为常数（不能是变量的函数）。
3. 只允许"系数 × 项，求和，比常数"——出现 `x·y`、`|x|`、`1/x` 一律拒绝。
4. 界是合法数值。

完备地覆盖线性类，硬性排除非线性类。

## 7. 路由判断：什么请求影响候选生成

**三步机械判断，无歧义：**

1. 是不是"改"请求？不是 → 只读查询（read_versions/read_environment/...），既不生成候选也不求解。
2. 是"改"请求 → 它改的输入在注册表里的"消费点"是哪？
   - 消费点含 `candidates` → **重新生成候选 + 重建模型 + 求解**
   - 消费点只含 `build_model` → **复用候选，只重建模型 + 求解**（性能关键：省掉昂贵的枚举）
3. "消费点"由代码客观决定，注册表只是如实记录，不可主观改。

**判定表格（用户请求 → 影响面）：**

| 用户请求 | 改的输入 | 消费点 | 是否重新生成候选 |
|---|---|---|---|
| "船租上涨 20%" | 船租 | build_model | 否 |
| "最多两条作业线" | 最多作业线数 | build_model | 否 |
| "人工单价改成 300" | 人工单价 | build_model | 否 |
| "齿轮箱维修工时上涨 20%" | 部件工时 | candidates | **是** |
| "叶片备件 11 月 5 日到货" | 库存流水 + 到货前冻结 | candidates | **是** |
| "严重故障 11 月 8 日前修完" | 任务期限 | candidates | **是** |
| "明天风变大（海况）" | 海况 | candidates | **是** |
| "未来三天电价上涨" | 逐时电价 | build_model | 否 |
| "先修 001 再修 003" | 组合约束 | build_model | 否 |
| "先最小化现金支出" | 目标 | build_model | 否 |

**为什么多数请求不触发候选生成**：候选生成只对"时间维度"的输入敏感（工时/期限/窗口/海况/时间参数）。
改"成本维度"（船租/人工/备件/电价）或"组合维度"（约束/目标）都只是在既有的候选池上重算，
候选池不变，因此可以"热重载"模型，省掉最贵的枚举步骤。

---

## 8. 完备性判据总结

| 层 | 锚 | 完备判据 |
|---|---|---|
| Part1 部件表 | 实体字段注册表 | 每个有业务意义、模型消费的字段都能改 |
| Part2 时序 | 时序字段注册表 | 海况/风速/电价/窗口都能假设改 |
| Part3 模型 | 指标注册表 + `linear` 原语 | 任意线性不等式/目标可表达 |

完备性靠"注册表 + 一个线性原语"锚定，不靠堆原语数量。LLM 只能在注册表内引用、
校验器只放行线性表达式，从而**既完备又受控**。

---

## 9. 实施分期

- **第一期（推荐）**：`linear` + `lexmin` + `weighted` 原语 + 高层糖 + 校验器，覆盖组合维度（选择层）。
  生成层复用现有 `overrides + data_patches`，不新增原语。
- **第二期**：把 data_patches 补全为"实体字段注册表"，补上时序数据（海况/逐时/窗口）的假设修改。
- **第三期**：生成层规则参数化（时间粒度、海况可作业判定），支持"改候选展开方式"。
