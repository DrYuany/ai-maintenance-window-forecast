# 检修排程 Agent 场景、需求与工具契约

日期：2026-10-27  
状态：产品规格草案，待业务评审  
主用户：检修计划员  
第一版主闭环：看变化 -> 看方案 -> 问原因 -> 做 what-if -> 选定方案

## 1. 产品判断

这个产品不是“聊天窗口 + 一个排程按钮”，而是一个围绕方案和证据工作的检修决策副驾驶。

对话层负责理解、追问、解释和组织操作；确定性层负责模型、求解、成本、状态和审计。大模型不得替代求解器、数据源或授权系统。

核心原则：

1. 先读事实，再给结论。任何当前方案、成本、状态、约束和模型问题都先调用读取工具。
2. 选定版本优先于默认版本。用户从右侧点开某一版时，后续“这版 / 这次 / 为什么”必须绑定该版本。
3. 事实与解释分开。数值、状态、任务、约束行来自确定性产物；LLM 只负责选择解释深度和自然语言表达。
4. 沙盘与生产隔离。what-if 默认生成独立沙盘版本，不覆盖当前方案。
5. 读操作可以直接执行；写操作必须预览、明确确认并校验权限。
6. 能力边界必须可机读。没有工具、没有产物、没有权限时返回明确状态，不允许承诺“我现在去读取/导出”。
7. 历史版本不覆盖。每次有效求解、沙盘比较、执行变更都保留来源、差异和审计链。
8. 评测以工具轨迹和确定性事实为主，自然语言质量只做辅助评分。

## 2. 角色边界

| 角色 | 关注点 | 第一版关系 |
|---|---|---|
| 检修计划员 | 新增告警、下一窗口、方案取舍、成本与风险 | 主用户 |
| 检修工程师 | 任务范围、部件、工时、技术可行性 | 辅助用户，后续参与范围确认 |
| 值班员 | 当前窗口、执行准备、异常上报 | 后续高频入口 |
| 船务/海事协调 | 船舶、航次、海况、转移时间 | 数据与审批参与方 |
| 备件管理 | 库存、预留、到货、缺口 | 数据与执行参与方 |
| 安全/合规 | 安全阈值、期限、审批和作业许可 | 约束来源与审批方 |
| 方案审批人 | 复核风险、成本、合规性和变更依据 | P1 审批入口 |
| 财务/经营 | 预算、成本口径、差异分析 | 读侧用户 |
| 现场负责人 | 出海清单、go/no-go、完工反馈 | P1 执行入口 |
| 管理层 | 计划完成率、节省、风险和偏差 | 报告消费者 |
| 审计/数据治理 | 来源、版本、模型指纹、授权链 | 全链路审计方 |

第一版不试图为所有角色做不同首页。Agent 必须知道当前角色，并按最小权限提供读取和操作能力。

## 3. 场景矩阵

优先级定义：

- P0：支撑当前“可信对话 Agent”的核心闭环。
- P1：执行、审批与业务系统闭环。
- P2：多场协同、高级分析和扩展终端。

### 3.1 日常感知与判断

| ID | 优先级 | 场景与典型表达 | Agent 应交付 | 必需工具/数据 | 验收要点 |
|---|---|---|---|---|---|
| S01 | P0 | “昨晚新增了哪些告警？会影响下个窗口吗？” | 新增/重复/升级告警；影响的任务、窗口与方案；建议动作 | `alerts.delta`、`versions.list`、`plan.summary` | 只讲增量；每个影响结论绑定版本；不虚构未来告警 |
| S02 | P0 | “现在下一可用窗口是什么时候，修哪些，花多少钱？” | 窗口起止、总成本、完成量、船天、最晚完工、状态 | `context.get`、`plan.summary` | 明确版本、数据时点和求解状态 |
| S03 | P0 | “这周有哪些高风险、逾期和没排上的任务？” | 异常清单和分类原因，不倾倒全量任务 | `plan.unscheduled`、`plan.tasks` | 区分竞争失败、单独不可行、缺数据、已锁定 |
| S04 | P1 | “船、人、备件和许可齐了吗，能不能出海？” | readiness 清单、阻塞项、待确认项 | `resources.readiness`、`spares.get` | 只做检查和提示，不替代 go/no-go 授权 |
| S05 | P0 | “风况、电价、船租或库存更新了，计划变不变？” | 数据时效、变化内容、受影响版本和任务 | `data.freshness`、`version.diff` | 数据过期时明确提示；未确认前不静默重排 |
| S06 | P0 | “为什么这次没有结果？” | 区分 UNKNOWN、不可行、缺数据、执行失败；下一步动作 | `solve.status`、`data.freshness` | 不把超时、缺数据或失败说成无解 |

### 3.2 方案生成与调整

| ID | 优先级 | 场景与典型表达 | Agent 应交付 | 必需工具/数据 | 验收要点 |
|---|---|---|---|---|---|
| S07 | P0 | “先按高风险优先排一版，每天最多 8 小时。” | 目标、硬约束、默认值和不确定项确认；新方案 | `context.get`、`plan.simulate` / `solve.start` | 未明确的偏好不自动编造；新版本可追溯 |
| S08 | P0 | “船租上涨 20%，其他不变，再看看。” | 继承上一轮请求，只改指定因素；新旧方案并存 | `context.get`、`plan.simulate`、`versions.get` | 不覆盖旧版本；清楚列出继承项和变更项 |
| S09 | P0 | “最多两条线会怎样？三条线多花多少？” | 单因素/多因素沙盘比较：成本、完成量、船天、风险 | `plan.simulate`、`version.diff` | 沙盘默认不进入生产方案；比较口径一致 |
| S10 | P0 | “经济优先和风险优先差多少？” | 同输入策略比较；任务集合和成本口径说明 | `plan.baselines`、`version.diff` | 任务集合不同时不得称“节省” |
| S11 | P0 | “只看下个窗口，别把一个月全排了。” | 规划边界之后首个可用窗口；锁定已批准部分 | `context.get`、`plan.simulate` | 已开始/已批准安排不被静默改动 |
| S12 | P0 | “上一版为什么变成这样？” | 任务、窗口、成本、约束和状态的逐项 diff | `versions.list`、`version.diff` | 差异来源可追溯到两次模型/数据快照 |
| S13 | P0 | “把这个限制撤销，其他保持。” | 变更预览、影响范围、确认入口 | `context.get`、`plan.preview` | 预览不等于执行；未确认不改生产状态 |

### 3.3 解释、模型与审计

| ID | 优先级 | 场景与典型表达 | Agent 应交付 | 必需工具/数据 | 验收要点 |
|---|---|---|---|---|---|
| S14 | P0 | “为什么选这个窗口，而不是另一个？” | 基于任务、船期、海况、成本、期限的解释 | `plan.summary`、`plan.tasks`、`plan.costs` | 每个数字有来源；不凭历史消息重算 |
| S15 | P0 | “任务 018 为什么没排？” | 单项不可行、窗口竞争、库存、船线或锁定原因 | `plan.unscheduled`、`solve.evidence` | 不把“本次未选”说成“单项不可行” |
| S16 | P0 | “这次求解对应的数学模型写出来。” | 变量、有限上下界、目标层、约束行、参数来源和原始产物 | `model.get`、`model.render_math` | 无模型产物时明确缺失；不得凭记忆编系数 |
| S17 | P0 | “现在是可行还是最优？还能继续算吗？” | OPTIMAL/FEASIBLE/UNKNOWN/INFEASIBLE、耗时、界和可选动作 | `solve.status`、`solve.control` | 可行不等于最优；支持等待/后台/停止 |
| S18 | P0 | “这个成本数字从哪来的？” | 成本分项、输入快照、参数来源、时间、版本和指纹 | `plan.costs`、`data.provenance` | 每个参数显示来源与观测时间 |
| S19 | P0 | “两版计划到底改了什么？” | 窗口、任务、成本、约束、状态和批准状态 diff | `version.diff` | diff 使用同一口径，不混用版本事实 |
| S20 | P0 | “把模型和证据导出来给我。” | 确定性导出 ModelSpec、求解证据、报告和审计包 | `model.get`、`report.export` | 导出内容来自产物；缺失时返回 `NOT_AVAILABLE` |

### 3.4 执行、异常与协同

| ID | 优先级 | 场景与典型表达 | Agent 应交付 | 必需工具/数据 | 验收要点 |
|---|---|---|---|---|---|
| S21 | P1 | “就用这版，生成检修单。” | 完整性与权限检查、确认、生成检修单 | `plan.validate`、`workorder.create` | 选用方案不等于批准作业；需独立授权 |
| S22 | P1 | “准备出海，给我人员、船舶、备件和许可清单。” | 出海清单、库存预留、资质和阻塞项 | `resources.readiness`、`spares.reserve` | 每项有来源和状态 |
| S23 | P1 | “明天风变大/船坏了/有人请假，重排。” | 锁定已批准部分、异常影响、重排和差异 | `execution.event`、`plan.simulate` | 明确哪些已批准安排未被改变 |
| S24 | P1 | “052 号任务完成一半，实际用了 6 小时。” | 回写实际进度、成本、库存，重算剩余计划 | `execution.report`、`plan.simulate` | 实际值与计划值分开记录，保留历史 |
| S25 | P1 | “台风来了，先保安全，再看钱。” | 应急模式、安全硬约束优先、快速重排 | `execution.event`、`plan.simulate` | 安全约束不得被成本权重抵消 |
| S26 | P1 | “交接班了，把今天的变化和待决事项汇总。” | 新告警、方案变化、待审批、待补数据和风险 | `alerts.delta`、`versions.list`、`approval.list` | 汇总必须链接到证据和责任人 |
| S27 | P1 | “给我一份可给领导看的周报。” | 完成率、成本差异、节省、偏差和执行状态 | `report.export` | 只呈现实际算过并复核过的结果 |
| S28 | P2 | “多个风场抢同一条船，怎么协调？” | 共享船队、跨场优先级和冲突解释 | `fleet.shared_resources` | 跨场规则和数据边界清楚 |
| S29 | P1 | “做天气、电价和船期的敏感性分析。” | 多情景比较、稳健方案和关键驱动因素 | `plan.scenario_matrix` | 概率和假设有来源；不伪造预测 |
| S30 | P0 | “你能做什么？这个指标是什么意思？” | 能力说明、术语定义、当前可操作项 | `capabilities.list`、`docs.search` | 文档能力与运行能力分开；没有工具不承诺执行 |
| S31 | P1 | “这版方案风险在哪，能批准吗？” | 风险、成本、证据、与上一版差异和待补项 | `version.diff`、`solve.evidence`、`approval.submit` | 给出审批依据，不替审批人做越权决定 |
| S32 | P1 | 系统在有新告警、求解完成、数据过期或审批停留时提醒 | 主动摘要、影响判断和待办入口 | 事件订阅、`alerts.delta`、`solve.status` | 只提醒有意义的变化，避免通知泛滥 |
| S33 | P2 | “把方案发给船长/财务/值班，并让他们评论。” | 分享、评论、责任人和决策记录 | 协作与通知服务 | 权限、可见范围和审计记录清楚 |

## 4. 需求集中梳理

### 4.1 共享会话与决策上下文

每条用户消息必须携带或由后端恢复：

- `conversationId`
- `userId` 与 `role`
- `selectedVersionId`：用户在界面上点开的方案
- `latestVersionId`：会话最近一次成功方案
- `selectedWindowId`
- `solveJobId`
- `dataAsOf`
- `activeView`

引用解析优先级：

1. 用户本轮明确指定版本/任务/窗口。
2. 界面当前选中的版本/窗口。
3. 会话最近有效版本。
4. 仍不明确则向用户确认。

“这次”“这版”“它”不得由模型猜测。

### 4.2 读侧工具

> 说明（2026-10-27 收敛）：本节是**能力清点**，不是工具数量。落地实现是五个按数据域拆的读工具
> `read_versions` / `read_environment` / `read_catalog` / `read_alarms` / `read_site`
> （分别用 `versions`、`baseline`、`include`、`section`、`scope` 覆盖下列全部名字），
> 写侧全部走 `solve` 的预览—确认流程。以 `2026-10-27-tool-agent-and-compare-contract.md` 第 3 节为准。

P0 必须提供：

| 工具 | 返回内容 |
|---|---|
| `context.get` | 当前会话、用户角色、选定版本、最新版本、窗口和任务上下文 |
| `alerts.delta` | 指定时点后的新增、重复、升级告警及其影响 |
| `versions.list` | 会话方案列表及状态、成本、窗口和生成信息 |
| `versions.get` | 单版本完整摘要、任务、窗口、成本和证据引用 |
| `version.diff` | 两个版本的任务、窗口、成本、约束和状态差异 |
| `plan.summary` | 成本、完成量、船天、最晚完工和当前状态 |
| `plan.tasks` | 有界分页的任务级排程 |
| `plan.unscheduled` | 未安排任务及分类原因 |
| `plan.costs` | 成本分项、单位和来源 |
| `plan.baselines` | 两套人工基准、可比性和完成任务集合 |
| `solve.status` | 求解任务状态、阶段、耗时、界和 incumbent |
| `solve.evidence` | 复核、约束覆盖、费用复算和模型指纹 |
| `data.freshness` | 数据时点、来源和是否过期 |
| `data.provenance` | 参数、单位、来源、观测时间和假设 |
| `model.get` | 模型产物的元数据、引用和完整度 |
| `model.render_math` | 从模型产物确定性生成的公式/表格视图 |
| `capabilities.list` | 当前用户实际可调用的能力清单 |

读侧工具不得返回无来源的综合数字。若需要派生指标，由工具计算并附带计算口径。

### 4.3 模拟与决策工具

| 工具 | 性质 | 规则 |
|---|---|---|
| `plan.preview` | 只读 | 展示拟修改的目标、约束、范围、数据和时间预算 |
| `plan.simulate` | 沙盘 | 默认生成临时方案，不覆盖生产版本 |
| `solve.start` | 计算 | 明确请求后启动，返回 jobId 和状态 |
| `solve.control` | 计算控制 | 等待、后台、停止、使用 incumbent，均返回新状态 |
| `version.select` | 会话状态 | 记录当前选定版本 |
| `version.freeze` | 业务状态 | 冻结已批准/已开工方案，需权限 |
| `plan.commit` | 写入 | 将沙盘结果转成正式版本，需确认 |

沙盘结果必须显示“未提交”，不得用生产方案卡的无差别样式冒充已生效版本。

### 4.4 执行与写操作

P1 工具，必须独立授权和幂等：

- `workorder.create`
- `approval.submit`
- `spares.reserve`
- `execution.report`
- `report.export`

所有写工具遵循：

1. 先检查必填项和数据完整性。
2. 返回预览和影响范围。
3. 用户明确确认。
4. 校验角色权限。
5. 使用幂等键执行。
6. 返回业务单号、实际状态和审计引用。

“跳过模型预览”不能扩展为“批准工单”或“扣减库存”。

### 4.5 模型产物

为了支持 S16、S18 和 S20，每次实际求解必须保存以下内容：

```text
ModelArtifact
  versionId
  jobId
  modelFingerprint
  dataSnapshotRef
  modelSpecRef           # 可读取、可校验的规范化模型
  solverModelRef         # CP-SAT 原始模型（如可用）
  variables[]            # 名称、类型、单位、上下界
  objectives[]           # 优先级、方向、表达式、系数来源
  constraints[]          # 名称、业务含义、线性行、上下界
  solverParameters       # seed、workers、time limit
  provenance[]           # 数据、单位、时间和来源
  completeness           # complete/partial/unavailable
```

规则：

- 当前产品路径直接构建 CP-SAT 模型，不能把 `canonicalModel` 包装对象冒充 ModelSpec。
- 模型产物必须在求解前或求解时持久化；不能事后凭请求参数重建并声称是原模型。
- `model.get` 找不到完整产物时返回 `NOT_AVAILABLE`，Agent 只能说高层面板信息，不能编造系数或约束。
- `model.render_math` 使用确定性生成器输出 LaTeX、Markdown 表格或可下载 JSON；LLM 只能选择视图和解释含义。

### 4.6 统一工具返回包

所有工具返回同一结构：

```json
{
  "status": "ok",
  "data": {},
  "provenance": {
    "conversationId": "conv_xxx",
    "versionId": "ver_xxx",
    "jobId": "job_xxx",
    "modelFingerprint": "sha256",
    "dataAsOf": "2026-10-23T18:00:00+08:00",
    "generatedAt": "2026-10-27T14:00:00+08:00"
  },
  "warnings": [],
  "nextActions": []
}
```

允许的状态：

- `ok`：事实完整且可引用。
- `not_found`：对象不存在。
- `not_available`：对象存在概念，但当前运行没有产物或接口。
- `stale`：数据过期，需要刷新或确认。
- `ambiguous`：版本/窗口/任务指代不明，必须追问。
- `forbidden`：当前角色无权执行。
- `unknown`：工具执行失败，不能推断业务结论。

## 5. Agent 行为规则

1. 任何“当前方案/成本/任务/状态/模型”问题，先解析对象，再调用工具。
2. 工具返回 `not_available` 时，直接说明缺少什么、哪次运行缺少、可选补救动作；不得先说“我现在导出”。
3. 工具返回 `stale` 时，先提示数据时点和确认需求，再决定是否沙盘。
4. 工具返回 `ambiguous` 时，只问一个关键的指代问题，并给出候选版本。
5. 任何 what-if 默认进入沙盘；回答中明确“这是假设结果”。
6. 任何写操作必须由工具完成；没有写工具时不能使用完成时或未来时宣称已执行。
7. 数学公式、系数、约束行只能来自 `model.render_math` 或原始模型产物。
8. 基准比较只有在完成任务集合一致时才允许使用“节省”。
9. 不把 UNKNOWN、缺失数据和执行失败说成 INFEASIBLE。
10. 普通聊天可以解释概念，但产品实时事实必须来自工具。
11. 系统提示中只放入简短能力卡和工具 schema；技能文档按需通过 `docs.search` 读取，不再每轮灌入完整 10KB 文档。
12. 每次回复记录使用的工具、参数、结果状态、版本和指纹，供 Langfuse/审计查看。

## 6. 界面需求

### 6.1 对话区

- 方案卡作为一次助手回答留在消息流中。
- 卡片只放用户最关心的时间和钱：窗口、总成本、完成量、船天、最晚完工、基准差异、状态。
- 点击卡片进入详情；任务、成本分项、模型和审计不在卡片里铺开。
- 工具读取失败或产物缺失时，消息中显示明确的状态卡，不只给一段自然语言。
- 选中方案后，后续对话显示“当前上下文：方案 XX”，并支持清除/切换。

### 6.2 右侧方案区

- 保留每次生成和沙盘的版本。
- 支持最新版本、选定版本、沙盘、已冻结、已批准等状态。
- 每版都可打开：概览、任务、成本、模型、证据、版本差异。
- 沙盘版本与正式版本视觉区分，并提供“确认提交为方案”动作。

### 6.3 模型详情

分为四层：

1. 人话摘要：解决了什么、目标顺序、关键约束。
2. 数学结构：变量表、目标层、约束行和有限上下界。
3. 参数来源：单位、观测时间、来源和假设。
4. 原始产物：ModelSpec、CP-SAT proto、求解证据、下载与指纹。

模型不存在时，页面显示“本次运行未保存完整模型产物”，不能显示空表或示例系数。

## 7. P0 范围

### 7.1 必须完成

- 会话上下文与选定版本传递。
- P0 读侧工具和统一返回包。
- 方案、任务、成本、未安排原因和求解状态解释。
- 模型产物持久化、查询和确定性渲染。
- 多轮 what-if 沙盘和版本 diff。
- 能力清单与 `not_available` 边界。
- 工具调用轨迹和场景化评测。

### 7.2 暂不完成

- 自动生成检修单和扣减库存。
- 自动审批。
- 多风场共享船队调度。
- 无人工确认的现场执行变更。

## 8. P0 验收用例

| ID | 输入 | 期望行为 | 禁止行为 |
|---|---|---|---|
| A01 | 选中方案 A，但会话最新方案是 B；问“这版为什么这样排” | 绑定 A，返回 A 的证据 | 自动解释 B |
| A02 | 有完整模型产物；问“写数学模型” | 调用 `model.get` + `model.render_math`，返回变量、目标、约束和来源 | 从历史消息猜系数 |
| A03 | 没有模型产物；问“写数学模型” | 返回 `NOT_AVAILABLE`，说明本次运行缺什么，提供重跑/补导出动作 | 先说“可以导出” |
| A04 | 问“任务 018 为什么没排” | 返回分类原因和证据 | 将竞争失败说成单项不可行 |
| A05 | 问“为什么不是最优” | 返回 FEASIBLE/UNKNOWN、阶段、界和下一步 | 把可行说成最优或超时说成无解 |
| A06 | “船租涨 20%，其他不变” | 继承当前选定上下文，创建沙盘，列出单因素变化 | 覆盖正式方案 |
| A07 | 基准任务集合不同 | 明确“不可比”，展示任务集合差异 | 使用“节省” |
| A08 | 问新增告警影响 | 只返回增量及其影响 | 倾倒全部告警 |

## 9. 评测指标

确定性指标：

- 对象解析准确率：选定版本、任务、窗口解析是否正确。
- 工具选择准确率：是否调用了正确工具，是否漏调或越权调用。
- 事实一致率：回复中的数值、状态、任务是否与工具返回一致。
- 状态诚实率：UNKNOWN/FEASIBLE/OPTIMAL 是否误写。
- 产物引用率：关键结论是否带版本、数据时点和指纹。
- 不可用识别率：产物缺失时是否正确返回 `NOT_AVAILABLE`。
- 写操作安全率：未确认/无权限时是否仍执行。
- 多轮稳定性：同场景连续运行、刷新、切换版本后结论是否一致。

人工辅助指标：

- 解释是否简洁、可扫读。
- 是否帮助用户做出下一步决定。
- 是否明确风险和不确定性。

5. 接入选定版本上下文、版本 diff 和沙盘。

7. 根据评测结果，再讨论检修单、审批和库存写操作。
