# 项目全景：每个文件在哪、管什么、从哪看起

> 这份文档是一张地图，不是教程。目的只有一个：想改某个东西时，能立刻知道该打开哪个文件。
> 所有路径相对项目根 `AI窗口期预测产品/`。

---

## 一、一句话说清这条链

```
用户说一句话
   ↓  backend/app/core/planning_intent.py      把话翻译成 PlanningRequest（七个字段 + 数据补丁）
   ↓  backend/app/core/maintenance_product_executor.py   把请求交给求解器
   ↓  maintenance-milp-modeler/scripts/product_data.py   读数据、验数据、冻结成快照
   ↓  maintenance-milp-modeler/scripts/product_planner.py 生成候选 → CP-SAT 建模 → 分层求解 → 独立复核
   ↓  backend/app/core/result_normalizer.py    报告 → 前端方案卡
   ↓  maintenance-milp-modeler/scripts/product_writeback.py  方案 → 检修单/出海清单 → 完工反馈 → 销账
```

前面四步是"算"，倒数第二步是"看"，最后一步是"办"。**原来的断点就在最后一步**：算完就结束，三张台账永远是空的。

### 第 1 层｜数据：业务事实从哪来

目录：`data/phase1-demo/`

| 文件 | 内容 | 谁在用 |
| --- | --- | --- |

| `海事检修窗口.csv` | 3 个出海窗口 | 求解器 |
| `每日海况预测.csv` | 35 天风速/波高 | 求解器 |
| `每小时电价与发电预测.csv` | 840 小时逐时电价与功率 | 求解器（算发电损失） |

| `校验排程.py` / `审计可行排程.csv` / `审计未安排任务.csv` | 数据自洽性审计，不是生产代码 | 人工核对 |

### 第 2 层｜求解内核：方案怎么算出来

目录：`maintenance-milp-modeler/scripts/`（12 个文件，2475 行）

| 文件 | 行数 | 职责 | 改它会影响 |
| --- | --- | --- | --- |
| `product_data.py` | ~410 | 读数据 → 全量校验 → 冻结快照。**所有"数据不对"的人话报错都在这里** | 输入合法性、规划时点、已下发任务的锁定 |
| `product_planner.py` | ~500 | 候选生成 → CP-SAT 建模 → 分层/加权求解 → 降级 → 独立费用复核 | 方案本身。**最核心的一个文件** |
| `planning_horizon.py` | 88 | 90 天观察范围内选目标窗口（含 7 天准备期） | 排的是哪个窗口 |
| `product_writeback.py` | 新增 | 台账回写：下发 / 审批 / 完工反馈 / 状态机 | 任务状态、三张台账 |
| `product_report.py` | 58 | 写 HTML 推荐报告 | 报告长什么样 |
| `model_artifact.py` | 354 | 导出 `solver_model.pbtxt` 和模型指纹 | "数学模型"页面的公式来源 |
| `product_store.py` | 245 | **另一条路**：SQLite 事务版台账（角色权限、幂等键、哈希审计链） | 目前没接前端，是正式版参考实现 |
| `product_service.py` | 136 | 上面那条路的 FastAPI 接口（planner/approver/executor 三角色） | 同上 |
| `maintenance_product.py` | 70 | 命令行入口 | 手动调用 |
| `objective_templates.py` | 157 | 四目标模板 | **未接生产**，生产走 `build_model` 内联加权 |
| `validate_model_spec.py` / `solve_model_spec.py` / `generate_base_scenarios.py` | 197/140/170 | 模型规格工具链、造基座数据 | 离线工具 |

关键常量：`MONEY = 1e6` —— CP-SAT 只吃整数，1 元 = 100 万微元。

配套阅读：`maintenance-milp-modeler/SKILL.md`、`references/phase1-profile.md`、`references/intent-and-change-review.md`。

## 三、三套模型各配各的（容易搞混）

| 用途 | 配置文件 | 环境变量 | 实际模型 |
| --- | --- | --- | --- |
| **文字 / 对话**（主产品） | 项目根或 `backend/` 下的 `.env.local` | `MINIMAX_API_KEY`<br>`MINIMAX_MODEL`<br>`MINIMAX_BASE_URL` | 默认 `deepseek-flash`，走 DeepSeek 的 Anthropic 兼容接口 |
| **语音**（voice-bridge） | `voice-bridge/server/.env` | `LLM_MODEL` / `LLM_BASE_URL`<br>加 `VOLCENGINE_*` 一组 | 默认 `qwen-flash`（DashScope），语音识别/合成走火山 |
| **数学模型**（排程） | 无环境变量 | 参数在 `data/模型参数/` | OR-Tools CP-SAT，模型文件导到 `product-output/*/solver_model.pbtxt` |

变量名里写 `MINIMAX_` 是历史遗留，实际调的是 DeepSeek。**看到 `MINIMAX_API_KEY` 不要以为是 MiniMax。**

## 五、这次闭环改了什么（2026-10-28）

**新增**

- `maintenance-milp-modeler/scripts/product_writeback.py`：台账回写模块
- `backend/eval_cases/verify_closed_loop.py`：17 项端到端验收

**修改**

| 文件 | 改了什么 |
| --- | --- |
| `product_data.py` | 读检修单，把待审批/已批准的任务登记为 `locked`；`Snapshot` 新增 `locked` 字段 |
| `product_planner.py` | `recommend` 把 locked 任务解析成固定候选，不重排但占资源；已开工的直接剔除 |
| `site_data.py` | `_counts` 拆出 `pending` / `scheduled`，`open` 语义收窄为"还没排进检修单" |
| `agent_tools.py` | 新增 `ledger` 工具（board / dispatch / approve / feedback） |

**状态机**

```
待安排 / 待补充窗口  --下发-->  已排程  --完工反馈-->  已完成
      ↑                          |
      +------ 拒绝 / 作废 --------+
```

**为什么必须回写**

不回写的话，"待安排 N 项"永远等于"收到过且没标完成/取消的全部告警"，同一批任务每一轮都会被重新排进去，检修单和出海清单永远是空的。
