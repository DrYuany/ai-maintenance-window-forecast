# 错误分类学：从「填表」的自由度推导，不从经验列举

日期：2026-10-30
对应代码：`backend/eval_cases/error_taxonomy.py`

---

## 0. 一句话

> **穷举用户的语言形式是无穷的；穷举模型填表的错法是有限的——因为表的结构是有限的。**
>
> 但这个「有限」不是感觉，得能推导出来。本文给出推导：7 个决策点、20 类错法、
> 其中 3 类原理上抓不到（全是"少了"），必须靠原文侧先列清单补。

---

## 1. 为什么这个转向成立：两个集合的势不一样

我们做的事，本质是**把一句自然语言，填进一张行数不固定的动态表**。

| | 空间有多大 | 能不能列完 |
|---|---|---|
| 用户的说法 | 开放集。同一件事有无限种说法，还带口音、省略、错别字、情绪 | **不能** |
| 表能填的内容 | 有限。19 个可写进 parameters 的栏目 + 4 个换节写的栏目 + 16 个约束原语 + 5 个目标原语 | 能，就这些 |
| **模型可能犯的错** | **有限。因为它只能错在表的自由度上** | **能** |

第三行是本文的全部立论。它成立的前提是一个结构判断：

> 填表的产物 = (表集合, 每张表的行集合, 每行的栏目, 每行的值)。
> 产物要被执行，还要满足两条：形状合法、依据可查。
>
> 这 6 个自由度穷尽了产物的全部可能。**所以错误也只能在这 6 个地方发生。**

如果这条成立，错误的集合就是封闭的。下面把它展开。

## 3. 三条必须修正的地方（都是实测撞出来的，不是理论洁癖）

### 3.1 「121 项」这个例子在我们系统里有更狠的版本：不是多一项，是表本身错了

你说「本来 120 项可改，它说 121 项，查一下在不在 120 以内就抓到了」。
这个抓法成立——**前提是那 120 项是对的。**

我们系统里真实发生过的事：

| 表 | 条目 | 谁在用 |
|---|---|---|
| 参数注册表（宣称可改） | **51** | 生成提示词 |
| `load_project.OVERRIDES`（执行白名单） | **16** | 真正生效 |
| 补丁说明（事后打的） | 4 | 文档 |

模型完全按提示词办事，填了第 17 项——**审查以「在 51 项以内」为准，通过；执行时炸「未支持参数」。**

这个错误模型一点没错，是表错了。所以：

> **审查所依据的表，必须是执行侧的表（落点表），不能是宣称表。**
> 而且只能有一份，由执行侧生成，不许手抄。

现在 `error_taxonomy.py` 里 E4.1 用的就是 `param_reg.route_of()`，它的定义是「有没有执行落点」，
不是「在不在清单里」。这个区别看起来小，但它正是 51/16/4 那个坑的解药。

### 3.2 3 类「少了」原理上抓不到，因为漏 = 空集

E1.1（该填没填）、E2.1（少拆）、E3.1（行少了），这三类有一个共同点：**它们不产生任何输出。**

没有输出就没有 token，没有 token 就没有东西可查。这不是工程没做好，是审查这件事的数学性质。

推论很硬：

> **审查能抓「错」和「编」，抓不住「漏」。**
> 「漏」必须靠外部基准——原文侧先列出「这句话一共提出了几件事」，
> 再核对每一件事有没有归属。

这个基准不需要理解语义，只需要**数句子**：按标点切段，每段必须挂一个栏目或标 `unassigned`。
它是确定性的、可判定的、有限的。这就是上一轮说的「锚点清单」，
但它不是我拍脑袋提的方案——**它是「审查有盲区」这个事实的唯一补法。**

所以完整的链路是两件事，不是一件：

```
原文侧：数诉求单元（确定性，不需要理解）  →  得到「应该有 N 行」
产物侧：审查 20 类错法                  →  检查「这 N 行填得对不对」
```

少任何一半都不成立：只有产物侧审查，漏掉的永远发现不了；只有原文侧清单，填错的值没人管。

### 3.3 审查有顺序，不是一张并列的检查清单

实测：DSL 写成 `{"parameters": {"每日有效维修上限": 8}}`（字典不是数组）时，
下游的句式审计报告「每日工时上限落空」——**这是假警报**，因为形状错导致读不出来。

一条形状错误，能连带污染 5 条下游判定。所以审查必须是流水线：

```
D0 形状 → 不合法就停下，修形状（归一化，0 次调用），重判
       → 合法才继续 D1~D6
```

代码里这条已经实现（`audit()` 里形状命中后把下游标成「待归一化」）。
这不是优化，是不这么做审查结果就没法看——**一堆连带误报，人就不看了，等于没有审查。**

## 4. 实测：18 条案例，漏判 0、误报 0

`error_taxonomy.py` 内建 18 条案例：6 条正确输出（防误报）+ 12 条真实观测到的错误形态。

```
按成本最低优先排每天只能干8小时          期望[]                    实得[]
钱不超过300万                    期望[]                    实得[]
船租翻倍了，重新排一下               期望[]                    实得[]
先修任务001再修任务002，钱别超300万     期望[]                    实得[]
每天只能干8小时…别排任务005           期望[]                    实得[]
任务001和任务002不要同一天做           期望[]                    实得[]
明天风大，先别出海                 期望[E5.1]                实得[E5.1]
成本压到最低，但高风险的必须全修          期望[E4.3]                实得[E4.3]
只看风机003和风机004              期望[E4.3]                实得[E4.3]
每天只能干8小时（参数写成字典）          期望[E0.2]                实得[E0.2]
每天只能干8小时（值写成"八小时"）         期望[E5.1]                实得[E5.1]
风速上限放宽到14米每秒（写成1400）       期望[E5.3,E6.1]           实得[E5.3,E6.1]
钱不超过300万（op 写成 >=）          期望[E5.5]                实得[E5.5]
只排部件01和部件02（栏目不可改）         期望[E4.1]                实得[E4.1]
把工期限制在某个范围（编造原语）          期望[E4.1,E6.1]           实得[E4.1,E6.1]
船租涨两成，人工单价也涨两成（同字段两值）     期望[E2.2]                实得[E2.2]
经济优先和风险优先差多少（问句当指令）       期望[E1.2]                实得[E1.2]
```

13 条真实模型输出上：**11 条零命中、零疑似，2 条命中真错**——
`明天风大，先别出海` → E5.1（day 写成中文）、`成本压到最低，但高风险的必须全修` → E4.3（用 cardinality>=1 顶替「全部」）。

补一条口径：`dsl=null` 且 route 属于 clarify/reject/chitchat/explain/compare 时，20 类全部判「不适用」。
不这么判，每条 clarify 都会被报成「顶层不是对象」——假警报一多，审计器就被人关掉了。

### 两个已知盲区，都在代码注释里写死了

1. **E6.1 抓不到字符串里的编号。** `exclude` 里的 `任务001` 是字符串，数值抽取收不到。
   编号型编造要靠「查表：这个任务在任务清单里吗」——那是另一类检查，不在 20 格里。
2. **E4.2 只能给「疑似」。** 它靠句式表，句式表的关键词会串门：实测
   「风速上限放宽到14米每秒」被「天气/海况」句式抢走，因为「风速」同时属于两个句式。
   **误报比漏报更伤**——一条假警报会让人关掉整个审计器。所以 E4.2 降一级，只当线索。

## 5. 值域覆盖率：2/15，这才是真短板

E5.4（取值域越界）看起来最容易，实测最难：

```
值域可机器解析率：2/15
  每日有效维修上限   可解析   (0, 24)      原始：大于0且不超过24
  最大作业线       可解析   (1, 3)       原始：1至3
  常态风速上限     散文      —            原始：非负数且不超过安全上限
  安全风速上限     散文      —            原始：非负数且不低于常态上限
  每天开始维修     散文      —            原始：当地时刻
  允许夜间转移     散文      —            原始：是或否
  …其余 9 项全是散文
```

两个不同的原因：

- 「非负数」「非负整数」「是或否」——**语义清楚，但没有数字**，正则抓不到，只能手写值域表。
- 「不超过安全上限」「不低于常态上限」——**界不是常量，是另一个字段**。这不是区间，是关系。

第二类恰好是你说的「约束的组合方式」。它比区间更强：`常态风速 ≤ 安全风速` 这一条，
比给两个字段各写一个 `[0, 50]` 有用得多。所以值域表要分两层：

```
第一层 单字段域：从「取值约束」这一列手写过来（15 项，一次性成本很低）
第二层 字段间关系：常态风速≤安全风速、开始时刻<结束时刻、预算≥最小现金支出
```

第二层每一条都是一个真实的业务约束，写一条赚一条。

## 6. 人、模型、审查：三栏对照

你说得对，人做的事和模型做的是同一件事。区别只在于**验收方式**。

| 步骤 | 人怎么做 | 模型怎么做 | 怎么验收 |
|---|---|---|---|
| 知道有哪些栏目可填 | 心里有一张表 | 系统提示词里给了同一张表 | 不用验收——**模型记不记得，靠结果反推** |
| 理解这句话在说什么 | 不知道，说不清机制 | 一次前向 | **不可判定**，不验收 |
| 判断要不要填表 | 直觉 | route 分类 | E1.2（问句当指令） |
| 判断填哪几个栏目 | 对照表 | 输出 field | E4.1 查表 / E4.2 疑似 |
| 判断值填多少 | 报价、查手册 | 输出 value | E5.1~E5.5 |
| 判断值合不合法 | 查手册 | **也交给代码** | 值域表 + 关系表 |
| 检查有没有漏 | 回头再读一遍 | **不做，也做不到** | 原文侧数句子 |

**「它记不记得那 122 项」这条，你判断得对：不保障，也没法保障。**
理由和「员工认不认真」一样——那是过程，你观察不到，只能看结果。
但有一个差别要注意：员工的输出你可以抽检，模型的输出可以**每一句都全检**，因为检查是代码跑的，边际成本为零。

所以结论是：**过程不保障，结果全检。** 这句话成立的前提是「全检的成本足够低」，
而 20 类错法里 8 类只看 DSL 就能判（不需要原文、不需要模型），这部分成本确实是零。

## 7. 这个思路的边界（说清楚，不藏）

1. **「穷举错误」降低了难度，但没有消灭「规则本身会错」。**
   20 类的判定函数是我写的代码，它自己也会误报（E4.2 就是活例子）。
   区别在于**错的代价变了**：生产规则漏一条 = 丢一句用户的话；审计规则误报一条 = 多一条假警报，可以关掉、可以修、可以降级成「疑似」。前者不可回滚，后者可回滚。

2. **20 类是完备的，但每一类的判定函数是有成本的。** 5 类免费（已有），12 类要写，
   其中 E5.4 的成本取决于值域表写得多细——这块是人工活，不是算法活。

3. **「漏」这个盲区永远存在，只能靠原文侧基准压缩，不能消除。**
   基准本身也有粒度问题：一句「风有点大」算一个诉求还是不算？这需要产品定义，不是代码能定的。

4. **分类学管的是「填得对不对」，管不了「该不该填这张表」。**
   如果用户的需求根本不在表的能力范围内（只排风机003），20 类里只有 E4.3（近似顶替）
   能隐约察觉。真正的解是补 `scope` 原语，或者明确告诉用户做不到。这是模型能力缺口，不是链路问题。

## 8. 建议的落地顺序

| 步 | 内容 | 成本 | 收益 |
|---|---|---|---|
| 1 | E0.2 归一化（dict→list） | 一行代码 | 形状错不再污染下游 |
| 2 | E5.1 + E5.4 + E5.5（类型/域/方向） | 半天 + 值域表 | 最常见的"值填错"当场拦 |
| 3 | E6.1 出处校验（只记日志不拦截） | 半天 | 拿到"无出处编造率"这个数 |
| 4 | 原文侧数句子（诉求单元基准） | 一天 | 补上 3 类盲区，才敢说"不漏" |
| 5 | E2.2/E3.2/E4.1 已有，接进主链 | 半天 | 免费的三类 |
| 6 | E4.2/E4.3 降级为"疑似"，交人工 | 半天 | 能力缺口的可见化 |

第 1~3 步不需要动路由顺序，不需要改提示词，可以独立上线、独立回滚。

**先说清一件不做的事**：E6.2（出处错）现在做不了，因为契约里模型给的是文本片段不是字符区间。
要做得改契约。我把它留在清单里标「缺」，不假装有。
