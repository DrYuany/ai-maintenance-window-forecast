# 最近完整窗口滚动排程设计

## 目标

检修排程 Agent 每次只优化一个目标窗口：从当前规划时点向后预留完整七天准备期，再选择准备期结束后开始的第一个可用窗口。基础数据覆盖未来 90 天，用于持续寻找目标窗口和支持每日滚动重算，但后续窗口不进入本次求解。

## 产品口径

- `规划边界 = 规划时点 + 7 × 24 小时`，使用带时区的精确时间计算。
- `观察终点 = 规划时点 + 90 × 24 小时`，观察区间为 `[规划时点, 观察终点)`。
- 合格窗口必须满足 `窗口开始时间 >= 规划边界`。
- 合格窗口必须完整落入观察范围，即 `窗口结束时间 <= 观察终点`。
- 若规划边界落在窗口的半开区间 `[开始时间, 结束时间)` 内，该窗口整体跳过。
- 将合格窗口按开始时间、窗口编号稳定排序，选择第一项作为唯一目标窗口。
- 只有满足 `首次接收时间 <= 规划时点` 且经过版本化规则去重的告警进入本次任务池；未来告警不能提前进入模型。读取使用同一事务快照或已记录的 ingestion watermark。
- 无法在目标窗口内安排的任务保留在待修池，记录原因，不自动转排第二个窗口。
- 每日数据刷新后创建新输入快照，重新计算规划边界、目标窗口和推荐排程。

示例：规划时点为 `2026-10-23T18:00:00+08:00`，规划边界为 `2026-10-30T18:00:00+08:00`。一个覆盖 10 月 30 日的窗口因开始时间早于规划边界而被跳过；若下一个窗口从 11 月 2 日开始，则 11 月 2 日窗口是本次唯一目标窗口。

## 方案选择

采用“数据加载后、建模前筛选唯一窗口”。90 天原始窗口保留在输入快照中，窗口选择器输出目标窗口及跳过记录，随后候选生成、基准方案、正式求解和独立复核只接收目标窗口。

不采用以下方案：

- 把全部窗口送入模型后禁止非目标窗口：模型更大，审计信息更复杂，容易让报告误展示后续窗口。
- 求解多个窗口但只发布第一个窗口：未来月份尚未收到的告警无法参与当前决策，多窗口全局方案会给用户造成稳定计划的错觉。

## 组件与职责

### 90 天数据层

窗口目录必须完整覆盖 `[规划时点, 观察终点)`，这是窗口选择的前置条件。数据层负责校验窗口时间连续性、来源、发布时间、审批状态和预测范围，不负责选择求解窗口。选择器不得读取观察终点之外的窗口。海况、电价、风速、资源日历、库存和人员数据在目标窗口选定后，仅对目标窗口及其成本计算所需区间进行完整性校验；缺少任何必需输入时返回 `MISSING_FORECAST_DATA`。

当前合成演示数据扩展至 90 天时继续明确标记为合成数据。`eligible(window, run_mode)` 同时校验时间有效、完整落入观察范围、满足七天边界以及授权和审批状态。正式运行只允许正式可用窗口；假设测算模式可以使用预测窗口，但输入、状态和页面必须显著标记，且两种模式不得共享缓存。

### 目标窗口选择器

输入为规划时点、准备期天数和按时间排序的窗口列表。输出结构包括：

- 规划时点；
- 准备期天数，默认固定为 7；
- 规划边界；
- 唯一目标窗口；
- 被跳过窗口及原因；
- 数据观察范围的起止时间。

入口先按唯一窗口编号校验并拒绝缺失编号、重复编号和冲突记录。排序键固定为 `(start_utc, window_id)`，不依赖输入文件顺序。

只有在 90 天数据完整性校验通过后，不存在合格窗口才返回 `NO_ELIGIBLE_WINDOW`。窗口列表或观察范围不完整时返回 `MISSING_WINDOW_DATA`，时间或编号冲突时返回 `INVALID_INPUT`。这些状态均不调用求解器，也不称为排程不可行。

### 单窗口求解上下文

业务截止期在目标窗口筛选前，基于同一 90 天窗口快照计算并固化为任务标量，同时记录来源窗口编号。进入求解上下文后只传入固化的截止时间及审计元数据，不把后续窗口作为决策对象。若计算第 N 个窗口截止期所需的窗口不在完整观察范围内，返回 `MISSING_DEADLINE_DATA`，不得推断或改写截止期。

窗口选择完成后构造新的求解上下文。`windows` 只包含目标窗口，求解终点为目标窗口结束时间。任务候选、船天、作业线、海况、库存、人员、固化截止期、人工基准和独立复核全部基于同一上下文，避免编译器与复核器使用不同窗口集合。

正式业务截止期保留原始含义。窗口选择不能修改告警发生时间、首次接收时间、严重度或用户明确约束。由于本次只安排一个窗口，未入选任务默认显示为 `NOT_SELECTED` 或 `PENDING`。只有在同一模型中强制该任务入选并得到正式不可行证明后，才能把单个任务标为 `INDIVIDUALLY_INFEASIBLE`，并记录证明模型的指纹和求解状态。

### Agent 与页面呈现

Agent 首先展示本次目标窗口，而不是多窗口月度计划。结果需要包含：

- “基于截至某时点已收到的告警”；
- 七天准备边界；
- 被跳过的最近窗口及原因；
- 目标窗口起止时间；
- 推荐检修任务、总成本和基准差异；
- 未安排任务数量及原因；
- 下一次数据刷新后会重新计算的提示。

详情面板中的窗口列表改为单一“本次目标窗口”。后续窗口可以在数据依据中作为观察信息展示，但不得显示为本次已排程窗口。

### 对话可视化与交互

对话采用轻盈、亲和的卡片式 UI，风格参考现代即时通信产品的清晰层级和顺滑反馈，但业务状态必须严谨。回答不只输出大段文字，而是由可交互的消息块组成：

- 计算中消息将细粒度进度合并为四个视觉步骤；超过三分钟在同一消息中出现“继续等待”和“停止求解”。只有存在已复核通过的 incumbent 时，按钮才改为“停止并查看当前可行方案”。停止后先完成复核，再按状态矩阵渲染。
- 结果顶部是目标窗口卡，突出日期、开始结束时间、可作业时长、天气摘要和“提前七天规划”标签。
- 第二层用指标卡显示推荐任务数、未安排任务数、总成本、两套人工基准的可比状态或差异，以及求解状态。只有 `COMPARABLE` 基准渲染数值差异；其他状态展示原因。
- 第三层用时间轴或紧凑甘特条展示作业线和任务顺序；高、中、低严重度使用可辨识颜色并同时显示文字，不能只靠颜色传意。
- 未安排任务使用独立折叠卡，逐项显示 `PENDING`、`NOT_SELECTED` 或 `INDIVIDUALLY_INFEASIBLE` 及证据。
- “为什么推荐”用三条以内自然语言解释主要驱动因素；模型指纹、参数、数据来源、基准详情和复核记录收纳在“查看计算依据”抽屉中。
- 使用圆角、柔和状态色、简洁图标和轻量进入动画营造亲和感；禁止用动画遮挡错误、延迟状态或真实求解状态。
- 手机和窄屏按单列展示，指标卡可横向滑动，时间轴保持可读；键盘导航、焦点态、ARIA 标签和状态文本满足基本无障碍要求。
- 结果头部同时展示 `solution_status` 和非 `COMPLETED` 的 `termination_reason`；`run_mode=HYPOTHETICAL` 时显示不可隐藏的“假设测算”标识。

所有可视化都由结构化结果字段驱动，不从自然语言回答中二次猜测。纯文本回退必须表达当前状态下所有非装饰性语义，包括运行模式、解状态、终止原因、目标窗口或无窗口原因、任务与费用、基准状态、未安排原因、数据截止点和审计引用；动画、颜色和布局无需等价。

### 对话结果 Schema

对话消息使用版本化 `ui_schema_version`。核心字段如下：

| 字段 | 类型 | 说明 |
|---|---|---|
| `ui_schema_version` | string | UI 结果契约版本 |
| `run_mode` | `PRODUCTION\|HYPOTHETICAL` | 正式运行或假设测算 |
| `solution_status` | enum | 本设计定义的解或前置状态 |
| `termination_reason` | enum | `COMPLETED\|TIME_LIMIT\|USER_CANCELLED\|SYSTEM_INTERRUPTED` |
| `progress` | object | 当前阶段、完成比例、开始时间、最近更新时间和错误码 |
| `target_window` | object 或 null | 唯一目标窗口及七天边界 |
| `executable_schedule` | array 或 null | 仅供已复核通过方案使用 |
| `candidate_schedule` | array 或 null | 仅供审计未通过候选使用，不可执行 |
| `cost` | object 或 null | 总成本、现金成本和分项，单位与精度明确 |
| `baselines` | array | 两套版本化人工基准及可比状态 |
| `unscheduled_tasks` | array | 未安排任务及结构化原因 |
| `reason_codes` | array | 页面文案所依据的稳定原因码 |
| `data_cutoff` | string | 告警与预测快照截止时间 |
| `audit_ref` | string 或 null | 输入、模型、求解和复核记录引用 |

数组按照业务唯一键稳定排序。`baselines[]` 每项包含 `baseline_id`、`version`、`status=COMPARABLE|NOT_COMPARABLE|BASELINE_INFEASIBLE`、`cost|null`、`difference|null` 和 `reason_code|null`。

状态不变量如下：

- `NO_ELIGIBLE_WINDOW`、`MISSING_WINDOW_DATA`、`MISSING_DEADLINE_DATA` 和 `INVALID_INPUT` 的 `target_window=null`、`executable_schedule=null`。
- `MISSING_FORECAST_DATA` 可以包含 `target_window`，但 `executable_schedule=null`。
- `UNKNOWN` 和 `INFEASIBLE` 的 `executable_schedule=null`。
- `VALIDATION_FAILED` 只能把未通过复核的结果放入 `candidate_schedule`，`executable_schedule=null`。
- 只有 `FEASIBLE` 和 `OPTIMAL` 可以提供 `executable_schedule`。

合法 `null` 渲染对应的状态卡，不显示为字段缺失错误。只有违反 schema 或状态不变量时才显示数据契约错误。

### 结构化进度

后端阶段固定为 `SNAPSHOT`、`DEADLINE_CALCULATION`、`WINDOW_SELECTION`、`INPUT_VALIDATION`、`MODEL_BUILD`、`SOLVING` 和 `REVIEW`。UI 可以将其合并为四个视觉步骤，但消息必须保留原始阶段、错误码和时间戳，确保 `MISSING_DEADLINE_DATA`、`MISSING_WINDOW_DATA` 和 `MISSING_FORECAST_DATA` 定位到实际失败阶段。进度状态通过 ARIA live region 宣告。

## 数据流

1. 按规划时点读取并冻结 90 天窗口、逐日预测、资源数据和已接收告警快照。
2. 基于完整窗口快照计算并固化任务截止期；缺少所需第 N 个窗口时返回 `MISSING_DEADLINE_DATA`。
3. 计算精确的七天规划边界。
4. 过滤开始时间早于边界的窗口，包括覆盖边界的窗口。
5. 选取第一个合格窗口，生成窗口选择审计记录。
6. 校验目标窗口所需的海况、电价、风速和资源数据；缺失时返回 `MISSING_FORECAST_DATA`。
7. 将唯一目标窗口、当前告警快照和固化截止期交给候选生成器。
8. 在相同单窗口上下文中运行版本化的“严重性优先”和“低风速优先”人工基准、CP-SAT 求解和独立复核。
9. 保存输入快照、窗口选择记录、规范化模型指纹、求解器参数与结果。
10. 页面和对话框使用结构化结果展示本次单窗口建议。

两套人工基准必须遵循版本化算法契约、稳定排序和并列决胜规则，使用相同告警快照、目标窗口、资源和截止期。成本统一计算到人民币分并采用四舍五入。基准无可行结果时输出 `BASELINE_INFEASIBLE`；任务集合不同时将差异标为 `NOT_COMPARABLE` 并显示原因，不展示节省金额。

## 确定性与模型指纹

同一规范化输入必须选择同一目标窗口。指纹采用版本化 canonical schema 和 SHA-256，时间规范化为 UTC epoch 并另存展示时区，集合按唯一业务键排序，数值使用契约规定精度，空值保留显式 `null`。模型指纹至少包含：

- 规划时点及其时区；
- `run_mode=PRODUCTION|HYPOTHETICAL`，并使用独立缓存命名空间；
- 准备期天数；
- 规划边界；
- 90 天窗口、海况、电价、风速、资源日历、库存和人员数据哈希；
- 目标窗口编号、开始时间和结束时间；
- 告警快照、去重规则、ingestion watermark、候选任务和固化截止期哈希；
- 参数、约束、目标层级、基准算法与版本；
- 候选生成器、约束实现、独立复核器和应用构建版本；
- 求解器名称与版本、随机种子、线程数和全部求解参数。

求解器记录随机种子、线程数和全部搜索参数。分层目标完成后追加覆盖全部决策变量的规范化最终决胜序，消除多个等价最优排程之间的不确定性。相同指纹复用已完成结果；若原始数据、代码版本或规划时点变化，则生成新版本。缓存复用和冷启动重算分别验收。只有 `OPTIMAL + COMPLETED` 的冷启动运行要求逐字段排程一致；`FEASIBLE` 只要求模型指纹、可行性、已完成目标层值和终止原因一致，不要求墙钟时限下的 incumbent 明细完全相同。

> 2026-10-30 修订：线程数默认由 1 改为 `min(8, CPU)`。原"固定单线程"是为了消除并行搜索的随机性，但真正的确定性来自上面那条"覆盖全部决策变量的决胜序"——它让最优解唯一，与线程数无关。实测同一算例 1 线程 90 秒未收敛、8 线程 1.1 秒最优，目标值一致；同配置重复两次排程逐条相同。需要严格复现时用 `MWA_SOLVER_WORKERS=1`。

## 异常与状态语义

- `NO_ELIGIBLE_WINDOW`：90 天内没有合格窗口，属于数据/业务状态，不是数学不可行。
- `MISSING_WINDOW_DATA` / `MISSING_DEADLINE_DATA`：窗口范围或期限计算所需数据不完整，不调用求解器。
- `MISSING_FORECAST_DATA`：目标窗口所需的海况、电价或资源数据不完整，阻止求解并指出缺口。
- `INFEASIBLE`：仅在求解器正式证明基础硬约束模型无可行解时使用。
- `UNKNOWN`：没有可行 incumbent，且求解器没有证明不可行。
- `FEASIBLE`：存在独立复核通过的可行 incumbent，但未证明全部目标层最优。
- `OPTIMAL`：全部目标层由求解器证明最优，且结果通过独立复核。
- `VALIDATION_FAILED`：求解结果未通过独立复核，不得展示为可执行方案。
- `ERROR`：求解器或运行系统异常，保留错误来源，不映射为无解。

解状态与终止原因分别记录。`termination_reason` 可为 `COMPLETED`、`TIME_LIMIT`、`USER_CANCELLED` 或 `SYSTEM_INTERRUPTED`。达到三分钟时界面只发出一次 `CONTINUE_WAITING` 事件，提供“继续等待”和“停止求解”；仅在已有复核通过 incumbent 时显示“停止并查看当前可行方案”。求解在等待用户操作期间继续运行。交互与非交互运行都必须配置硬时限。用户未响应时继续求解至完成或硬时限；求解先完成则关闭提示。达到硬时限或用户停止时，有复核通过的 incumbent 返回 `FEASIBLE`，没有 incumbent 返回 `UNKNOWN`，incumbent 复核失败返回 `VALIDATION_FAILED`。

## 验收标准

- 规划边界处于窗口内部时，该窗口必定被跳过。
- 给定唯一最早候选窗口的 `start == planning_boundary`，选择器必须选中该窗口。
- 目标窗口之后的窗口不产生任何决策变量或排程记录。
- 同一输入通过缓存复用必须得到逐字段一致的完整结果；`OPTIMAL + COMPLETED` 的冷启动连续运行必须得到相同目标窗口、模型指纹、解状态、分层目标值和逐字段一致的排程明细；`FEASIBLE` 冷启动按正文的有限确定性口径验收。
- 新增次日告警后生成新快照并重算，不污染前一日版本。
- 90 天内无合格窗口、窗口数据缺失、期限数据缺失、预测数据缺失、正式不可行和复核失败分别返回对应状态与文案。超时和取消通过 `termination_reason` 区分，并按状态矩阵验收：`TIME_LIMIT|USER_CANCELLED + 已复核 incumbent => FEASIBLE`；无 incumbent => `UNKNOWN`；incumbent 复核失败 => `VALIDATION_FAILED`。
- 达到三分钟时只触发一次继续等待事件；选择停止后不把 `UNKNOWN` 表述为无解。
- 前端工作台和 Agent 只把一个窗口标记为本次排程目标。
- 对话结果必须渲染目标窗口卡、指标卡、排程时间轴、未安排任务和可展开审计信息；结构化字段缺失时显示明确占位或错误状态，不生成猜测数据。
- 每个运行状态均提供结构化 fixture 和组件测试，验证合法 `null`、状态不变量、基准可比性、运行模式和非正常终止原因。
- 窄屏断点设为 768px；320px 宽度下页面不得产生整体横向溢出，时间轴和指标组在组件内部滚动。
- 所有交互可仅用键盘完成并显示可见焦点；异步状态由 ARIA live region 宣告；正文、控件、状态色和非颜色提示按 WCAG 2.2 AA 对比度与可感知要求验收。

## 迁移影响

现有五周多窗口演示数据和测试需要升级为 90 天数据口径。原有按“未来第 1/2/3 个窗口”计算严重度截止期的规则需要保留为任务业务期限，但不能驱动本次选择第二或第三个排程窗口。历史运行结果保持只读；新版本通过模型指纹和运行版本号与历史多窗口结果区分。
