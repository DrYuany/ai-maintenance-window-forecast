# 大模型优先的意图识别：设计稿

日期：2026-10-30
状态：**设计，产线代码未改**（只有探针脚本）
实测环境：DeepSeek `deepseek-chat`，温度 0，单次 0.55~1.47 秒

---

## 0. 一句话

把「规则先认领」换成「模型先判读、校验器判对错、规则只在模型失手时兜底」。

判读不是让模型自由发挥：它必须同时交一份**原文逐段对账表**，校验器拿它对账。对不上就不许出结果。这是把「不许假装成功」从一句口号变成一道可执行的关。

---

## 1. 为什么现在的顺序必然吞话

规则层每个节点同时干两件事：

1. **判断这句话归不归我管**（认领）
2. **把这句话变成结构**（解析）

第 1 件的判据宽松——命中一个词就算；第 2 件的判据严格——整句必须被正则吃干净。两者之间的差额，就是静默丢掉的部分。

这不是哪条正则写漏了。只要「认领」比「读懂」宽松，就一定有东西掉在地上，而且**不报错**——它返回的是一份看起来正常的方案，置信度 1.0。

今天实测，这条还在（前几轮修完仍然存在）：

```
输入：先修任务001再修任务002，钱别超300万
门 is_planning_request → 认领
规则层 parse_by_rules → 命中
产出：{"constraints":[{"type":"precedence","before":"任务001","after":"任务002"}]}
      ↑ 预算 300 万，没了。confidence=1.0
```

同一批 13 条难例，旧链路里 **4 条被规则层抢先、其中 2 条丢内容**：一条丢预算，一条丢工时（前几轮已修）。

## 2. 新链路

```
                        ┌─ 大模型判读（1 次调用，~1s）
用户一句话 ──────────────┤   route + 槽位 + 对账表
                        └─ 上下文：快照 + 时间基准 + 当前方案
                                  │
                    ┌─────────────┴─────────────┐
                    │  确定性校验（0 调用）        │
                    │  ① 结构关  ② 值域关 ③ 对账关 │
                    └─────────────┬─────────────┘
                        全过 ─────┤───── 不过
                          │               │
                    出 DSL → 预览      确定性归一化（改形状）
                                          │ 仍不过
                                     repair 一次（只改错处，~0.7s）
                                          │ 仍不过
                                     规则层兜底（须「完全消费」）
                                          │ 仍不过
                                       clarify（带已识别 + 缺什么）
```

三段职责切干净：

| 段 | 谁做 | 做什么 | 不做 |
|---|---|---|---|
| 判读 | 大模型 | 定 route、填槽、交对账表 | 不判自己对不对 |
| 校验 | 代码 | 判结构/值域/覆盖 | 不猜语义 |
| 兜底 | 规则 + 澄清 | 模型失手时接管 | 不许直出半截结果 |

**关键点：判读和校验是两个不同主体。** 现在的问题是同一个主体既当运动员又当裁判（正则既认领又解析），所以错了没人知道。

## 3. 判读契约

在现有契约上新增三个字段，其余不动：

```json
{
  "route": "modify_plan | modify_data | query_plan | compare | explain | chitchat | reject | clarify",
  "dsl": {"parameters": [...], "constraints": [...], "objectives": [...], "data": [...]} | null,
  "spans": [{"text": "按成本最低优先", "into": "objectives[0].name"}],
  "unresolved": ["原文中没有任何槽位能吃的片段（逐字复制）"],
  "ask": "需要用户补充的一句话" | null,
  "confidence": 0.0~1.0
}
```

三条硬要求写进提示词：

1. 先按标点、连词切句，**每一段都要在 spans 里有归属**，逐字复制，不改写不合并；
2. 有一段说不清它变成哪个字段 → 进 `unresolved`，**不许硬编**；
3. `unresolved` 非空时：能确定主体就 `clarify` 并给 `ask`；完全越界才 `reject`。

### 3.1 route 从 4 个扩到 8 个的理由

现在只有 `dsl / not_change / reject / clarify`。`not_change` 把「问方案」「比方案」「问原理」「闲聊」四件事压成一个，下游只能靠 `_looks_like_modification` 猜，猜错就走到不该去的分支。

实测证据：

```
输入：经济优先和风险优先差多少
新契约 → route=compare，0.58s
旧链路 → 门 is_planning_request 判真 → 进旧规划器 → 产出 strategy=高风险优先抢修
```

用户问的是「差多少」，系统给了个「改成高风险优先」。给了 `compare` 这个 route，问题在判读阶段就消失了，不需要补一打问句正则。

### 3.2 契约必须给完整骨架（实测踩到的坑）

第一版契约只写了文字说明（"parameters 每项必须写 op"），模型输出：

```json
{"parameters": {"每日有效维修上限": 8}}     ← 字典，不是数组
```

校验器报 `parameters[0]: 参数必须是 JSON 对象`。加上一个可复制的骨架后，同一批话全部正确：

```json
{"parameters": [{"field": "每日有效维修上限", "op": "=", "value": 8}]}
```

**这条的教训比它本身重要**：上一轮「36 项填了就报错」里，有一部分不是能力缺失，是提示词没给可复制的结构样例。以后凡是结构化输出，契约里必须有一个能直接抄的完整对象。

## 4. 三道校验关

### 4.1 结构关（已有，够用）

`validate_dsl`：字段白名单、原语在册、required 齐全、参数写对节、op 合法、引用实体存在。

### 4.2 值域关（新增，现在几乎是空的）

现状：参数只查 `>= 0`。字符串值**直接放行**。

实测漏洞：

```
{"parameters":[{"field":"每日有效维修上限","op":"=","value":"八小时"}]}
→ validate_dsl 返回 []   ← 零错误
```

这条一路走到 `load_project` 才会炸，那时已经离用户的话很远了。

要做的是把参数总表里那句中文「取值约束」变成机器可读的域。19 项，手写一张表，成本极低：

| 参数 | 类型 | 合法域 |
|---|---|---|
| 每日有效维修上限 | 数值 | `(0, 24]` |
| 最大作业线 | 整数 | `[1, 3]`（超过 3 属资源能力变更，需确认） |
| 可调动人员总数 | 整数 | `>= 0` 且 `<= 人员池上限` |
| 船舶日租金 / 维修人工单价 | 数值 | `>= 0`，且 `< 1e7`（量级保护，防「翻倍」被写成 240000000） |
| 风机间转移 | 数值 | `[0, 24)` |
| 常态风速上限 | 数值 | `>= 0` 且 `<= 安全风速上限` |
| 安全风速上限 | 数值 | `>= 常态风速上限` |
| 常态/安全浪高上限 | 数值 | 同上，互为上下界 |
| 每天开始/结束维修 | 时刻 | `HH:MM`，且 开始 < 结束 |
| 允许夜间转移 / 跨天暂停 | 布尔 | `"是"` / `"否"` |
| 候选开工粒度 | 整数 | `>= 1` 且整除 60 的常见档位 |
| 费用预算上限 | 数值 | `>= 0`，且 `>= 最小现金支出下界`（否则必然无解，直接拦） |

其中「跨字段约束」是重点：安全 ≥ 常态、开始 < 结束、预算 ≥ 下界。这些现在一条都没有，而它们正好是最容易出错的地方（用户说「风速上限放宽到 14」，但没说常态上限是不是也要跟着动）。

分级：**error**（绝不能过）/ **warn**（可疑，界面提示但仍放行）。判不准的一律 warn，不要假装确定。

### 4.3 对账关（新增，核心）

三条确定性检查，全部不依赖模型自评：

**① unresolved 必须为空。** 非空 → 不出 DSL，直接进澄清（`ask` 原样转给用户）。

**② spans 不能编造。** 每个 `spans[i].text` 必须是原文的真实子串（`in message`）。防模型为了凑覆盖率自己造句。

**③ 数字对账（最硬的一条）。** 从原文抽出「数字 + 单位」，换算后必须能在 DSL 的所有数值里找到对应：

| 原文 | 换算 | DSL 里必须出现 |
|---|---|---|
| 300万 | 3,000,000 | 3,000,000 |
| 8小时 | 8 | 8 |
| 两成 / 20% | 1.2 | 1.2 或 等价绝对值 |
| 翻倍 | 2 | 2 或 等价绝对值 |
| 任务001 | 001 | "任务001" |

找不到 → 判定「这句话的数字没落地」→ 不出结果。**这条就是「静默丢话率」的实现**，能把「先修…钱别超300万」丢预算那类问题当场揪出来。

### 4.4 这三关能拦住什么（今天实测的真错）

| 输入 | 模型产出 | 哪一关拦 |
|---|---|---|
| 按成本最低优先排每天只能干8小时 | `parameters` 写成字典 | 结构关 |
| 每天只能干8小时 | `value: "八小时"` | 值域关 |
| 只排风机003的任务（第一版契约） | 手工枚举 19 条 exclude 冒充范围限定 | 对账关（原文无 19 个任务号）+ 值域关 |
| 先修任务001再修任务002，钱别超300万（旧链路） | 只有 precedence | 对账关（300万 未落地） |
| 明天风大，先别出海 | `day: "明天"` | 值域关（日期非 ISO，且超出视界） |

## 5. 降级路径：每一层留证据

```
判读 → 结构关不过？ → 确定性归一化（dict→list 这类形状问题，不烧调用）
              ↓ 仍不过
          repair 一次（把错误原文回灌，只改错处）
              ↓ 仍不过
          规则层（仅当「完全消费」）
              ↓ 仍不行
          clarify（带已识别片段 + 缺什么）
```

### 5.1 repair 的实测边界

| 错误类型 | repair 效果 |
|---|---|
| `budget` 缺 `quantity` | ✅ 补上，0.66s |
| `value: "八小时"` | ✅ 改成 8，0.91s |
| `parameters` 写成字典 | ❌ 只改成嵌套字典 `{"每日有效维修上限":{"op":..,"value":..}}`，仍不是数组，1.45s |
| `day: "明天"`（validator 无 data 时不报错） | ✅ 主动问「明天是哪一天」，1.17s |

结论：**结构形状错误不要指望 repair**——模型倾向最小改动，不会跳出原形状。形状问题在解析层做确定性归一化，值/缺字段问题才 repair。

### 5.2 规则层「完全消费」的判据

规则层保留的唯一资格：能证明「原文每个实词段都有主人」。

做法：每次正则命中记 `span [start, end)`；未覆盖的原文片段（去虚词后）非空 → 没资格直出。

这条不依赖大模型，可以单独先上。它比现在的「命中恰好一条才直出」严得多——现在的问题是「一条命中」不等于「整句吃完」。

## 6. 两个必须补的上下文

### 6.1 时间基准（今天实测白跑一轮）

```
输入：明天风大，先别出海
产出：{"data":[{"kind":"weather","day":"明天","state":"不可作业"}]}
```

`data_block` 里 weather 的示例明确写的是 `"day":"2026-11-03"`，模型还是写了「明天」——因为**提示词里没有今天是几号**。

要补的是一行：

```
## 时间基准
今天 2026-10-23（周五）。规划视界 2026-10-23 ~ 2026-11-22。
「明天」= 2026-10-24；「下周」= 2026-10-26 起；「月底」= 2026-10-31。
所有日期一律写 ISO，不要写「明天」「后天」。
```

`context_block` 现在只有「当前选中方案：方案02」，没有时点。修法很小，收益是「相对时间」这一类话术全部不再产生一轮交互。

### 6.2 快照已有实体映射

`snapshot_block` 给的是任务/风机/部件/窗口清单。所以模型能自己推出「风机003 → 任务003、任务018」——第一版契约下它就是这么干的（枚举了 19 条 exclude，唯独漏了它认为属于风机003的两个）。

这说明**范围限定缺的不是数据，是原语**（见第 10 节）。

## 7. 性能与成本

| 项 | 实测 |
|---|---|
| 判读单次 | 0.55 ~ 1.47s，13 条均值约 1.0s |
| repair 单次 | 0.66 ~ 1.45s |
| 端到端（判读 + 校验 + 预览） | 约 1.1 ~ 1.6s |
| 旧链路（走 LLM 那 9 条） | 同量级，且多绕 6 层判断 |
| 旧链路（被规则层抢先那 4 条） | ~1ms，但其中 2 条内容错 |

结论：**慢的那部分本来就在慢，快的那部分是错的。** 用户能感知的差别是 1 秒 vs 1 毫秒——只有在高频重复同一句话时才有意义，而那种情况有缓存。

两个必须处理的隐患：

1. **缓存键现在只有 `message`**（`_PARSE_CACHE[message.strip()]`）。同一句「按成本最低优先排」在不同方案上下文下可能该得到不同结果（比如已经有 pending 变更）。键要加上下文摘要哈希。
2. **向量 0.95 命中跳过 LLM 要加数字对账**。0.95 相似度容忍「任务003 → 任务005」这种改动，直接复用模板 DSL 会把任务号带错。命中模板后先比对数字序列，一致才用。

## 8. 评测口径（切默认值前必须有数字）

加环境开关 `MWA_INTENT_MODE=llm_first|rules_first`，两条路并存。

四个指标：

| 指标 | 定义 | 为什么要有 |
|---|---|---|
| route 准确率 | 与期望 route 一致 | 现有评测已在算 |
| 槽位召回 | 期望约束类型 ⊆ 实际类型 | 现有评测已在算 |
| **静默丢话率** | 原文有数字/实体但 DSL 里找不到对应，且系统返回了 dsl 的比例 | **新指标，专抓「不报错的错」** |
| 端到端时延 | 判读到预览 | 防为了准确率牺牲体验 |

静默丢话率是这一轮的重点。现有 221 条提问库只能测「route 对不对」，测不出「话有没有被吃掉」——「先修任务001再修任务002，钱别超300万」在现有口径下是**通过**的（route=dsl，类型 precedence 覆盖期望），可它丢了一半。

三套集：

- `dsl_questions.jsonl` 221 条 —— route 与槽位
- `adversarial_slots.jsonl` 70 条 —— 对抗槽位（其中 25 条已标 `not_implemented`）
- 今天的 13 条难例 —— 静默丢话率

## 10. 这轮设计解决不了的三件事（是模型能力缺口，不是链路问题）

| 诉求 | 现状 | 建议 |
|---|---|---|
| 「只排风机003的任务」 | 没有范围原语，模型只能枚举 exclude 硬凑 | 补 `scope` 约束（filter 风机/部件/严重度）。快照已有映射，成本低 |
| 「高风险的必须全修」 | 只有 `cardinality >= N`，表达不了「全部」 | 补 `must_all(filter)`，或在提示词明说做不到 |
| 「三天干完」 | 缺「全局完工期限」这类表达 | 补 `deadline_global` 约束，或明确定为不支持 |

这三条不管链路怎么改都得补模型。**区别在于：改链路之后，模型会老实说「做不到」，而不是自己编一个看起来对的 DSL。**

## 11. 实施顺序（每步可单独回滚）

| 步 | 内容 | 风险 | 回滚 |
|---|---|---|---|
| 1 | 契约升级：加 spans/unresolved、完整骨架、时间基准 | 低，只影响 LLM 输出解读 | 删字段即回 |
| 2 | 三道校验关 + 数字对账埋点（先只记录不拦截） | 低 | 关开关 |
| 3 | 确定性归一化（dict→list）+ repair | 低 | 同上 |
| 4 | 规则层加「完全消费」判据 | 中，可能让一批话改走 LLM | 判据阈值可调 |
| 5 | 顺序反转，`MWA_INTENT_MODE` 双路并存 | 高 | 切回 rules_first |
| 6 | 跑 A/B（221 + 70 + 13），有数字再切默认 | — | — |

1~3 步不改变路由顺序，纯增强，可以立刻上。第 5 步才动顺序，必须有第 6 步的数字。

## 12. 「凭什么相信它给出的槽位」——可执行的三类错误、三种抓法

这一节回答一个绕不过去的质疑：**校验器只能校验已经产出的槽位，模型压根没想到的那个槽位，
校验器抓不住。那「能力 A 整句读」凭什么成立？**

答案分两步。第一步承认：**凭什么都不成立**。没有任何提示词、任何模型版本、任何 temperature，
能保证它读对。所以系统的正确目标不是「让它读对」，而是——
**让「读错」变成一个必须被拦下的、可判定的、可计数的事件。**

### 12.1 先分清三类错误，它们的抓法完全不同

| 错误类型 | 例子 | 现在能不能抓 | 抓到靠什么 |
|---|---|---|---|
| **漏**（该给的没给） | 「先修001再修002，钱别超300万」只出 precedence | 旧链路：抓不到（返回 1.0 置信度的半截结果） | 覆盖率审计（句式表 × DSL 落点） |
| **错**（给了但值不对/形态不对） | `每日有效维修上限 = "八小时"`；budget 缺 quantity | validator 只抓后者 | 值域表 + 交叉一致性 |
| **编**（给了原文没有的） | 「船租涨了不少」→ `船舶日租金 = 15000` | **完全抓不到**，而且置信度正常 | 出处校验（DSL 每个值必须能在原文找到） |

第三类是最危险的，因为**它长得最像正常输出**。下面有实测。

### 12.2 实测：模型自报的覆盖率没有信息量

契约里要求模型自己交 `spans` / `unresolved`（原文逐段对账表）。13 条难例的实际结果：

- 自报 `unresolved` 非空的：**2 条**，且这两条都是它自己主动判 `clarify` 的
- 其余 11 条全部自报「已全部消化、无未识别片段」

也就是说：**让它评价自己的工作，等于没有评价。** 自报只能当线索，不能当证据。

拿噪声长句做对照实验，差异非常清楚：

```
原文：我在现场看了一圈，风有点大，海况也不太好，船租最近涨了不少，
      你先把方案重排一下，另外钱还是不能超过300万

模型输出：
  parameters: 常态风速上限=12, 常态浪高上限=1.2, 船舶日租金=15000
  constraints: budget <= 3000000
  自报 unresolved: ["我在现场看了一圈"]        ← 只承认了寒暄那句
  自报 confidence: 正常

代码审计（audit_slot_coverage.py）：
  越界编造 = [12.0, 15000.0]                  ← 原文根本没这两个数
  落空槽位 = ["天气/海况"]                     ← 它把"今天风大"写成了全期"常态上限"
  结论 = 有落空
```

三个编造参数，模型一个都没承认。这不是模型「不老实」，是它**真的不觉得自己在编**——
它的任务是「把话翻译成 DSL」，遇到"涨了不少"这种模糊表述，它倾向于补一个看起来合理的具体值，
而不是举手说"这里缺数字"。**这是生成式模型的本能，改提示词只能降低频率，不能归零。**

顺带一个更细的证据：`15000` 既不等于默认值 12000，也不是 12000×倍数。
它不是抄示例，是**自己猜了一个量级合理的数**。

### 12.3 三种抓法，全部由代码判定，不看模型态度

**抓法一：出处校验（最硬，优先级最高）**

> 规则：DSL 里出现的每一个数值，必须能在原文里找到出处；找不到 → 拒绝出方案，转澄清。

- 允许的派生：默认值 × 倍率（「船租翻倍」→ 24000，基准 12000 来自参数表，可查证）
- 不允许的派生：凭空出现的具体值（15000）
- 判定完全可执行：抽原文数字集合 + 抽 DSL 数字集合 + 做包含/派生检查

这条规则的价值在于**它不要求模型诚实**。只要它编了，一定会被抓。
代价是要维护一张「哪些字段允许从默认值派生」的白名单（初始只有 4 项：船租、人工单价、电价倍率、工时倍率）。

**抓法二：覆盖率审计（近似可判定）**

> 规则：原文按标点/连词切段，每段必须命中「句式表」里的一条，且该条对应的 DSL 节点存在。

句式表的形态（`audit_slot_coverage.py` 里 11 条起步）：

| 句式 | 必须存在的节点 |
|---|---|
| 每天…只能/最多…X 小时 | `parameters[每日有效维修上限]` |
| 不超过/别超/预算…X万 | `constraints[budget]` |
| 先…再… / A 在 B 之前 | `constraints[precedence]` |
| 不要同一天 | `constraints[co_occur]` |
| 最多 X 条作业线 | `parameters[最多作业线]` |
| 别排/禁止 + 任务 | `constraints[exclude]` |
| 风大/海况/台风 | `data[weather/sea_state]` |

**这张表是人写的，它是这个方案的真正短板**：覆盖不到「我没预想到的说法」。
所以它的定位不是「证明全对」，是「把静默丢话从不可见变成可数」，并且这个数会随句式表增长而下降。

实测：13 条难例里审计判「有落空」0 条。**这个 0 不能当结论**——那 13 条是挑过的，
契约也是照着它们写的，属于过拟合。真正有意义的数字要在 221 条 + 70 条的盲测上取。

**抓法三：两次采样一致性（抓不稳定样本）**

> 规则：同一句话调用两次（temperature=0），两份 DSL 不等价 → 不出方案，转澄清。

实测同一句话重复 6 次，输出**字节级完全一致**（6/6，同一签名）。但在盲测集里必然存在
处在决策边界上的句子（比如「试试看能不能三天干完」，实测置信度 0.3），这类句子两次采样就会分叉。
分叉本身就是信号：**系统对自己没底的句子，本来就不该直接出方案。**

成本是翻倍的调用次数，所以建议**只对置信度 < 0.7 的样本触发**，其余只跑一次。

### 12.4 结构层：拿不到 grammar 约束，只能靠代码兜

原计划想靠「结构化输出」把结构错误这个维度直接消灭。实测这个模型（DeepSeek）三种模式的表现：

| 请求方式 | 结果 |
|---|---|
| 无约束 | 返回带 ```json 围栏的文本，需要剥 |
| `response_format: json_object` | 可用，但只保证「是合法 JSON」，字段名、嵌套形状一概不管 |
| `response_format: json_schema` + `strict: true` | **400 拒绝：`This response_format type is unavailable now`** |

结论：**这个 provider 没有 grammar-constrained decoding，结构正确性无法由 API 保证。**
所以结构层只能三步走，全部在代码侧：

1. **归一化**：dict → list（`{"每日有效维修上限": 8}` → `[{"field":...,"op":"=","value":8}]`），
   纯形状修复，0 次调用。实测模型在只给文字说明时确实会写成 dict，给完整骨架样例后不再犯。
2. **校验**：`validate_dsl` + 新增值域表。
3. **repair**：把校验错误原文回灌给模型重出一次。实测能修「缺 quantity」「值写成中文」，
   **修不了形状**（它会把 dict 改成嵌套 dict，还是不合法）——所以形状必须走第 1 步，别浪费调用。

### 12.5 一句话回答

> 我不能保证模型读对，我能保证三件事，而且这三件事都由代码判定、可复算、可计数：
> **结构不合法就修，修不好就拒；值在原文找不到出处就拒；覆盖率算下来有段落落空就问。**
> 至于「它有没有理解到位」，那个问题不交给模型自评，交给评测集的数字。

这也解释了为什么不能靠「换个更强的模型」解决：这类系统的失败模式是**静默失败**——
它给出的东西看起来完全正常，置信度 0.95，校验零错误，用户不会怀疑。
准确率再高也只是把频率压低；**静默失败必须靠可检测性来兜，不能靠准确率来兜。**

### 12.6 新增的两个可复算指标

| 指标 | 定义 | 现状 |
|---|---|---|
| **静默丢话率** | 审计判「有落空」但模型 route 仍是 `modify_plan` 的比例 | 旧链路实测 8 条复合句里 4 条（50%）；新契约 13 条里 0 条（过拟合，待盲测） |
| **无出处编造率** | DSL 数值中无法在原文找到出处的比例 | 旧链路无此项检查；新契约噪声句 3/4 个参数编造，事后审计可抓 |

这两个指标必须在盲测集（221 条提问库 + 70 条对抗）上跑，才能作为切默认值的依据。

### 12.7 落地顺序（在原 1~6 步里插两条）

把原来的第 2 步拆细：

| 步 | 内容 | 新增文件 |
|---|---|---|
| 2a | 出处校验 + 覆盖率审计**先只记录日志、不拦截** | `audit_slot_coverage.py` |
| 2b | 跑盲测，拿到「静默丢话率 / 无出处编造率」两个基线 | — |
| 2c | 打开拦截（拒绝出方案 → 转澄清），再跑一遍看澄清率能不能接受 | — |

**2a 和 2b 不改任何行为**，只是把现在的静默失败变成日志里的一行。这一步的投入产出比最高：
它不需要动路由，也不需要相信模型，就能立刻知道现在到底丢了多少话。
