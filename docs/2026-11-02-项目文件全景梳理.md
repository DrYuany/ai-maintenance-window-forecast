> 2026-11-02 写。这是一份"每个文件干嘛的"地图，比 10-28 那份《项目全景与学习路线》新——
> 补上了它没覆盖的：dsl_core 抽包、llm-first 实验版、引擎切换、SSE 流式、异步求解、演示额度体系。
> 每条描述都核对过代码落点，不是凭印象写的。

## 先给一张总图：三层分工

整个项目就干一件事：**你说话，它排检修计划，并且每个数字都查得到出处。**

```
你的一句话
   │
   ▼
【懂中文的那层】backend/ + llm-first/     —— LLM 只翻译，把话变成受控 DSL
   │        （产物必须过确定性校验器，编造字段直接拒）
   ▼
【会算数的那层】maintenance-milp-modeler/ —— CP-SAT 真求解，分层目标 + 决胜段
   │        （独立复核器重算一遍费用，对不上就报错）
   ▼
【说人话的那层】报告 + 前端 src/          —— 只搬运前两层的数字，不产生新数字
```

`dsl_core/` 是三层的地基：DSL 长什么样、哪些参数能改、怎么编译成约束，
只写这一份，backend 和 llm-first 共用，谁也不许另抄一份。

## 二、backend/ — 对话与调度（懂中文的那层）

一个用户消息进来之后的完整路径：
`api/agent.py` 收请求 → `agent_runtime.py` 总调度 → `conversation_agent.py` 跑 LLM 工具循环 →
`agent_tools.py` 执行工具 → 要改模型时走 `change_planning.py` → `llm_parser.py` 三层解析出 DSL →
`dsl_core` 校验桥接 → 回一份"待确认预览" → 你说"确认" → `maintenance_product_executor.py`
派真求解 → `solve_jobs.py` 后台任务 → 结果落库，前端能看到。

## 三、dsl_core/ — 中立共享内核（地基，全项目最重要的一层）

定位：backend（规则主导）和 llm-first（LLM 主导）都只用这一份执行侧，互不 import 对方。
历史上"哪些参数可改"被手抄三处且互相矛盾（文档说 51 项、代码认 16 项），这个包的存在就是为了
让"不登记就跑不通"替代"靠纪律保持一致"。

| 文件 | 干嘛的 |
| --- | --- |
| `__init__.py` / `README.md` | 包定位声明 / 设计与评测成绩总账 |
| `registry/parameters.py` | **参数注册表（122 项）**：每登记一个参数必须同时登记"落点"（这句话怎么落到模型里）。没有落点 = 不可改 = 提示词不列。`consumption_point()` 还决定改了它要不要重算候选 |
| `registry/primitives.py` | 16 个约束原语 + 5 个目标原语的登记表，含"为什么不做 no_overlap"这类边界理由 |
| `registry/quantities.py` | 可引用量登记表：计数/加权和/最大值……什么量在模型里合法可引用 |
| `registry/entities.py` | 7 类实体（任务/风机/部件/窗口/作业线/人员/时间）+ 别名解析（"任务18"和"T18"是同一个） |
| `registry/data_fields.py` | 六张输入表逐字段登记：类型、单位、能不能改 |
| `registry/schema_prompt.py` | **提示词不是手写的**：从注册表反向生成"你能改什么"的系统提示词，改注册表提示词自动跟着变 |
| `validator.py` | 确定性校验器，纯 Python 不调 LLM。LLM 编造的字段、非法结构在这里被拒——"受控"两个字靠它 |
| `compiler.py` | 把校验过的 DSL 变成 CP-SAT 约束/目标，统一量纲（时间→分钟、钱→微元），判断要不要切部分排程模式 |
| `generator.py` | 生成"可引用量"的符号项，编译器的上游 |
| `planning_bridge.py` | 新旧语言桥：DSL 和 PlanningRequest（七个字段+数据补丁）互相转换 |
| `planning_request.py` | 共享数据模型：求解器的标准输入长什么样 |
| `runner.py` | 端到端入口：取数→求解→报告一条龙，失败时带诊断和"撞在哪道门"的归因 |
| `utterance.py` | **原话对账（前半段）**：你说"只修 8 个"，DSL 里就必须恰好 8 条必做。只判机器能判死的三类：数量、对象、数值 |
| `reconcile.py` | **意图对账（后半段）**：DSL 每条诉求逐条对产物核证据，三态：通过/违例/未核对。背景是"复核通过但模型根本没含排除约束"的事故 |
| `diagnose.py` | 无解时的失败诊断：只用算得出来的事实回答为什么，分"已证明/上界证明/未能定位"三档 |
| `gate_metrics.py` | 失败归因计数：六道门各挡了多少 |
| `objective_catalog.py` | 四种目标模板的唯一事实源（读 maintenance-milp-modeler 的 json） |
| `part_catalog.py` | 部件别名映射：LLM 只见"叶片"，不见"部件01"；查不到就报错不许猜 |
