# Shi et al. 双视图 DSL 与本项目三元骨架：逐条机制对照 + 可借鉴清单

日期：2026-11-02
对象：Yu-Zhe Shi et al., *Automated Constraint Specification for Job Scheduling by Regulating Generative Model with Domain-Specific Representation*，IEEE T-ASE 2025，[arXiv:2510.02679](https://arxiv.org/abs/2510.02679)，DOI 10.1109/TASE.2025.3596540

> **读之前先对齐口径。** 本文的轴仍是「用户意图 → 受控 DSL → 固定模型契约」，不是「LLM 优化 agent」。
> 这篇论文值得对照，恰恰因为它和本项目一样**把 LLM 关进笼子**：DSL 当护栏，确定性装置管正确性，
> LLM 只做解析、实体抽取和"盯梢"。工具循环、会话记忆、方案对比是外壳，不在本文对照范围。
> 两边判分也不在一个坐标系：它看字段级 Precision/Recall/F1、编译/运行错误率；
> 本项目的发布闸门看状态诚实性、模型指纹重复性、证据链完整性。

---

## 0. 一句话结论

**动机几乎可以照搬，机制各走一半。** 它把「DSL 护栏 + 确定性验证」这条路走通并做了统计对照实验，
但停在「约束规约」这一跳；本项目在「意图这一跳」和「产物这一跳」两头都多做了它没做的东西。
真正能搬的只有三件：**守恒不变量上移到编译期**、**把"未核对"量化成召回率**、**失败归因分层计数**。
其余要么是你已经更强（目标、模型契约、唯一实现），要么现阶段不该硬上（约束解码、DPMM 自动设计 DSL）。

## 1. 两条管道摆平

```
Shi et al.：原始制造资料 ──LLM 抽取(伪标签)──▶ 双视图 DSL 程序
                                      │
                          PDA 按工序顺序遍历、验"内存为空"
                                      │  验证的同时导出 资源约束 R / 优先约束 P
                                      ▼
                          OR-Tools JSP 求解（约束规划）
                                      │
                          排程落回生产计划（grounding）

本项目：    用户原话 ──规则/向量/LLM 三层解析──▶ 四段 DSL JSON
                                      │
              validator.py 确定性放行（实体/原语/量/线性/界）
                                      │  utterance.py 前段对账：原话 ↔ DSL
                                      ▼
              consumption_point() 决定重算候选 还是 只重建模型
                                      │
              compiler.py 注入闭包 → CP-SAT（形状固定的模型契约）
                                      │  reconcile.py 后段对账：DSL ↔ 产物
                                      ▼
                          方案 + 证据包 → 审批 / 库存
```

## 2. 逐机制对照（M1–M12）

术语先翻译：**PDA（下推自动机）**＝一个带记事本、按工序顺序往下走的检查员，边走边记"手头有哪些在制品"；
**DPMM（Dirichlet 过程混合模型）**＝不事先定死分几类、让数据自己长类别的聚类；
**EM**＝两步交替：先从数据里猜结构，再从规则里修结构，直到不改为止；
**EMKVP**＝不比整句话、只比"字段-值"对逐个对不对。

### M1 · DSL 从哪来

| | Shi et al. | 本项目 |
|---|---|---|
| 做法 | 场景语料 → DPMM 长出「操作中心视图」的语义特征（离散用 DP、连续/混合用 DP×GP、unification 合并等价接口）+ EM 长出「产品流视图」的管道句法 ψ。10 个场景各自收敛出自己的 DSL | 人工设计第一性三元骨架（设计文档 §5）；`registry/schema_prompt.py` **由注册表反向生成提示词**，`build_system_prompt()` 自动拼 L0/L1/L2 |
| 差在哪 | 它解决的是「跨 10 个工厂、DSL 从哪来」这个泛化问题；本项目单场景，DSL 是一次设计 | 它自己承认两难：通用语言太复杂、DSL 又难跨场景；还承认「手工造 DSL 只是把人力从一处搬到另一处，可能更贵」。本项目的「注册表反向生成提示词」恰好绕开：改注册表，提示词自动跟着变，不需要为每个场景造 DSL |
| 判断 | **各有适用场景，别互相取代** | 本项目更适合单场景；轻量版思路见 C2 |

### M2 · 结构组织轴

| | Shi et al. | 本项目 |

### M3 · 双视图 vs 双维度（最容易误读成同一件事的一条）

| | Shi et al. | 本项目 |
|---|---|---|
| 做法 | 操作中心视图 Lo = (前条件/后条件/执行) 三要素；产品流中心视图 Lp = 前驱/后继/属性 + 管道结构 ψ〈pred,succ〉（可表达 linear / Y 形 / N 前驱对 M 后继）。**动机：工序与物料互相纠缠，盯一个就丢了另一个，所以两个视图并行追踪** | 设计文档 §2：候选生成＝**时间维度**（唯一自由度是开工时间点，完成/作业段/成本都是派生量），模型构建＝**成本 + 组合维度**；`parameters.py:193 consumption_point()` 把这个拆法变成**编译期路由**：改船租复用候选只重建模型，改齿轮箱工时必须重生成候选 |
| 差在哪 | 同样的"两个纠缠视角"问题，它用双视图**同时追踪**，本项目用双维度**决定重算范围**，进了一层 | 它缺一个「两视图之间的不变量在编译期被机械检查」的对应物吗？不缺——它的 PDA 正是干这个（M5）。本项目缺的恰恰是**两个维度之间的同源性检查**：候选的时间派生与模型的成本派生是否读了同一份快照，目前靠流程保证，没有机械遍历 |
| 判断 | **别为了对齐论文去造第二个视图**（C3）。同构问题你已经解得更远 |

### M4 · 确定性验证放在哪

| | Shi et al. | 本项目 |
|---|---|---|
| 做法 | **编译期**：PDA 遍历 DSL 程序，记录"可达产品流单元"，defining/killing 单元，转移时删/加；接受条件 = 执行完内存为空。LLM 只被 in-context learning 用来**监控** PDA 的 kill/define 两个动作，决定权不在 LLM | **编译期** `validator.py` 只放行"实体存在、原语在册、量合法、线性、系数有限、界合法"，不调 LLM；再叠**两段事后对账**：`utterance.py`（原话↔DSL，前段）、`reconcile.py`（DSL↔产物，后段） |
| 差在哪 | 它的确定性装置是**生成式**的：验证的同时**顺带导出**资源约束 R 和优先约束 P。本项目的 validator 只做**放行/拒绝**，不产出新约束；正确性靠前后两段对账兜 | 它明确说"determinism of symbolic representations"来自 PDA，LLM 只盯梢——和本项目"LLM 只翻译"是同一条纪律，写法可引 |
| 判断 | **这是全篇最值得搬的一条**，见 A1 |

### M5 · 守恒不变量（本项目有素材、但没上移，最实的一条）

| | Shi et al. | 本项目 |
|---|---|---|
| 做法 | 产品流的**时空连续性**："物料不能凭空出现"。PDA 的可判定形式＝执行结束内存为空（所有 define 的都被 kill）；这个不变量在验证时**自动**把 kill 的一对操作写成优先约束、把操作点+机器写成资源约束 | 库存守恒其实**已经写了两遍**：`data/场景评测/运行场景.py:108` 把「现有量 + 到货 − 计划消耗 ≤ 容量 − 安全库存」写成 CP-SAT 前缀约束；`:165-173` 再按事件排序累加余额、独立重算断言 `balance ≥ 安全库存`。字段也注册了：`registry/data_fields.py:36-41` 的「库存.到货/出库」movement 类型，`参数总表.csv:67` 的「安全库存下限」 |
| 差在哪 | 它把守恒做成**一条声明，在 DSL 编译期就判，且判的同时生成约束**；本项目这两处都在**场景评测脚本里逐场景手写**，不在 DSL 编译链上。直接后果：`diagnose.py` 的六类不可行归因（`_conflicts` / `_time_window_facts` / `_starved` / `_capacity_bound` / `_budget_bound` / `_cardinality_bound`，见 `:384-391`）**没有库存这一项**——用户改了到货日期导致备件不够，系统会走到"未能定位"，而这件事本可以在编译期就"已证明"地指出 | 不是"从零做"，是**把已有的两段逻辑上移、去重、让它自动生成** |
| 判断 | **A1 头号借鉴**。别照搬"内存为空"（那是产品流语义），要的是它「验证即导出」这个模式；库存是带时点的前缀和，比产品流简单 |

## 3. 可借鉴清单（分档，每条落到文件）

### A. 马上能搬（代价小、素材现成）

**A1 · 守恒不变量上移到编译期** —— 对应 M4/M5，最高优先
- 新增 `dsl_core/invariants.py`（或并入 `validator.py` / `compiler.py`）：一条声明「每个部件、每个时点：现有量 + 到货 − 出库 − 已排消耗 ≥ 安全库存下限」。
- 学 Shi 的「验证即导出」：由这一条**同时**产出 ① 编译期可判的检查（数据本身不够 → 直接"已证明"拒，不必等求解不可行）、② 模型里的前缀约束、③ `reconcile.py` 的复核项。把 `data/场景评测/运行场景.py:108` 和 `:165-173` 两份手写逻辑收编成这一份的产出。
- 顺手补 `diagnose.py`：在 `:384-391` 的 checks 里加库存一类，让"到货改晚导致备件不够"能被定位，而不是落进"未能定位"。
- 边界：别照搬 PDA 的"内存为空"语义；库存是带时点的前缀和，比产品流简单。素材已齐（`data_fields.py:36-41`、`参数总表.csv:67`）。

**A2 · 把「未核对」量化成召回率** —— 对应 M11，几乎零代价 · **已落地 2026-11-02**
- 落点 `dsl_core/utterance.py`：`audit_utterance()` 返回新增 `断言覆盖率` / `对账召回` / `评测口径`（分子分母全列出，可复算），另加 `format_metrics()` 供复盘报告用；用户预览文案 `format_audit()` 保持不变。
- 口径：`断言覆盖率 = 已覆盖片段 / 值得列出片段`（`_WORTH_LISTING` 圈分母、`leftovers` 圈未覆盖）；`对账召回 = 对上断言 / 检查项`（抽出来的诉求，DSL 真正落实了的比例）。两者配一对：**覆盖率管「该抽没抽」，召回管「抽到的做没做到」**。
- 分母为 0 留 `None` 不报 100%；读不到在册清单时两个都不算、在口径里写明原因。两个数**只披露、不参与判定**——`通过` 仍由 `违例/未核对` 决定，闸门口径不变（有回归护栏测试）。
- 命名提醒：字段名沿用当初叫法，但按标准术语 `断言覆盖率` 实为**抽取召回**、`对账召回` 实为**精确率**。对外按公式讲，别望文生义。
- 验证：`backend/tests/dsl/test_utterance.py` 新增 8 条（覆盖率掉档、召回掉档、分母 0、world 缺失、闸门口径不变、格式化不虚报满分）。

**A3 · 失败归因分层计数** —— 对应 M8 · **已落地 2026-11-02**
- 新增 `dsl_core/gate_metrics.py`：只读现有返回结构做归因与计数，**不重复执行任何检查、不新增判定机制**。`classify()` 按「先撞到的那道门」归一类；`from_dsl_error()` 从 `runner.run()` 抛的 `DslError` 反推；`tally()` 出按类计数/占比 + 分桶计数/占比；`format_tally()` 出可读表；`classify_records()` + `main()` 提供命令行。
- `dsl_core/runner.py` 的 `DslError` 新增只读 `gate_class` 属性（延迟导入），闸门每次拦截自带归因标签。

## 4. 一个诚实判断

这篇论文最有用的不是机制，是它**替你把"为什么要有中间这一层"做成了统计实验**（M12/B1），

除此之外，本项目在两头都比它远：前段有 `utterance.py` 直接核"意图→DSL"这一跳（WIQOR / OR-Space / 这篇都没有对应物），
后段有 `reconcile.py` 逐条核产物、有目标与审批库存闭环。
**别拿它的框架来裁自己的系统**——它研究的是"约束怎么自动写出来"，你做的是"这一次决策能不能被审计"。
