# 工具循环落地记录：把「背表」换成「查表」，顺手挖出六个静默失败

上一份施工记录（`2026-10-30-落地记录.md`）建的是"一次成型"的链路：模型看提示词背表，
写完就交卷，错了靠修复轮退回来。这一份记的是把**工具循环**接进去之后发生的事——
以及它像探针一样照出来的那些"看着成功、其实没照做"的缺陷。

---

## 一、起点：为什么必须有工具循环

原架构里有两个"循环"，性质完全不同：

| | 是什么 | 修得好的上限 |
|---|---|---|
| 修复轮次（`for attempt in 1..2`） | 写完 → 验收判 → 退回重写 | 事后审判，只能改表面 |
| 工具循环（`for round in 1..4`） | 不知道 → 查 → 再写 | 事前查证，能改根本 |

缺工具循环时，模型只能**背**：`船租` → `船舶日租金` 这种映射得靠提示词里列全。
列不全就猜，猜错就靠修复轮纠——两条路都在烧模型调用。

接上之后，`人手砍一半`（backend Q114，改前恒为 clarify）现在查 3 次能把
`可调动人员总数=15` 落进 DSL。

---

## 二、先说结论（数字）

| 指标 | 改前 | 改后 | 备注 |
|---|---|---|---|
| core 评测 | 66/67 | **67/68** | 加了 G05 同义改写，防背题 |
| 需重试条数 | 2 | **3**（一度 33） | 「33」是我自己的解析器写错造成的 |
| 平均耗时 | 1095 ms | **3673 ms** | 工具轮的钱，单独算 |
| backend 测试 | 343 | **355** | |
| llm-first 测试 | 152 | **163** | |
| 首轮合格率（10 条抽样） | 6/10 | **10/10** | 只看第一遍，`diag_first_pass.py` |

耗时翻三倍是**明账**：一次提问现在可能查 1~3 次表，每次都是一次完整模型调用。
省下来的是一轮修复（同为一次调用，但带着完整提示词 + 全量产物重来）。
两条路的账要分开记，不能只报通过率。

## 三、照出来的六个静默失败

工具循环本身只是一次改造；真正的收获是它把"判据之间不一致"全照出来了。
六个的共同点：**看上去成功**。

### 1. 同一段 JSON，两个解析器两个结论

`pipeline._looks_like_json` 用 `rsplit("```")` 切尾部，`contract.load` 用
`strip_fence` 只剥两端。模型交 `JSON + 「说明：…」` 时，前者判「合法」、后者报
`Extra data`，于是白烧一整轮修复换回一份一模一样的内容。

修法：只留一份 `contract.parse_object`。放行范围故意窄——只放行"去掉空白和围栏后
不以 `{` 或 `[` 开头"的尾巴；第二份 JSON 是数据，丢掉的后果是判据在残缺产物上判通过。

### 2. 交卷轮靠模型自己停

原来只有第 4 轮撤工具 + 强制 JSON。两种状态漏了：说完但没开 json_mode（补一段话）、
4 轮都在调工具（交回空 content）。现在探索轮只认"交出能解析的 JSON"，用完必补收口轮。

### 3. validator 与 executor 对同一份 DSL 两个答案

`{"type":"linear","terms":[[1,"最后完工时间"]]}`：validator 说已实现，verify 判通过，
执行侧抛 `原型不支持的形式 'metrics'`。metrics 由内核 metrics dict 提供，**只有目标**
物化得出来。现在 linear 里引用它直接拦。

### 4. 兜底方案被当成解（最严重）

`product_planner.solve` 先把启发式基座当 fallback，那份方案是在**没有 DSL 约束**的
模型上排的。约束一逼到不可行就原样返回，`解状态` 写 `FEASIBLE`，只有
`方案来源=HEURISTIC_FALLBACK` 藏着真相。

实测：同时要求「禁止任务001」和「必须任务001」，返回的方案里任务001 排得好好的。

### 5. 期限把任务挤成零候选，它就悄悄消失

候选按截止时间截断生成（`hi=min(窗口结束, 截止分钟)`）。干不完 = 零候选 =
从"必须排进去"的名单里消失 → 求解照常 `FEASIBLE`，那几条躺在"未安排"里。
用户说的是"必须修完"。现在拿基座对照，基座排得进、加期限排不进 → 直接报。

### 6. 降级是静默的

三处 `except ConversationAgentError` 都是裸 `pass`，兜底答复和正常答复**形状完全一样**。
现在 `AgentResponse.degraded` + `AgentTrace.degraded` + 界面横幅。
标记挂 thread-local，`_begin_trace` 里清空——不清会粘住，下一轮明明走了模型
还挂着"规则兜底"，那是指向错的地方，比不提示更糟。

## 四、判据与被测物：谁该改

这一轮有三条用例的 `note` 被证明是**当年的能力假设**，不是被测物的错：

| 用例 | 原判断 | 实测 |
|---|---|---|
| I05 加权 | 表 D 没有加权，只能明说做不到 | 有 `weighted`，求解器按量级归一（`ranges`：成本按现金/船租上界、完成数按任务数），0.6/0.4 能跑 |
| G04 完工期限 | 量目录里没有能做日期上界的量 | `task_deadline` 不给 task/severity = 全部任务，**等价于整体期限**；<=11-15 直接 INFEASIBLE，<=11-20 可行 |
| J11 按级别批量期限 | 没有这块积木 | `_apply_task_patches` 本来就按严重等级收紧；真正的坑在下一层（第 5 条） |

**改用例的纪律**：每一条都把实测证据写进 `note`，并加一条同义改写（G05）——
只留一条，下一个人很容易把它调成"认得这一句"而不是"认得这件事"。

没改的那条：I03「算两个场景…对比一下」route 判对（clarify），但判据 A8 要求
clarify 的草稿也双向对齐（每个 DSL 项都要有 fill 指着）。这属于判据设计问题
（clarify 的草稿根本不会提交），**留着不修**，等想清楚再说。

## 五之二、三个工具补上了三处盲区

三个都做了，但**落点不一样**。这一点比工具本身重要：硬凑成两条路径各来一份，
等于复制出两套迟早分叉的实现。

| 工具 | 落在哪 | 为什么在那儿 |
|---|---|---|
| `prepare_change` | 只做 llm-first | backend 的模型不手写 DSL（它说一句话，`solve` 内部再调一次模型去编译），没有"自己写的东西要试跑"这回事 |
| `read_jobs` | 只做 backend | 只有 backend 有求解作业表；llm-first 是同步 `execute.solve`，跑完就返回 |
| `submit_change` | 只做 backend | 同上 |

### prepare_change：实测推翻了我的判断

我原来判断它"收益最小，可以一直不做"。实测不是：

```
高严重任务11月9日前修完
  read_capabilities  -> ok
  read_capabilities  -> ok
  prepare_change     -> invalid  ['constraints']   ← 先写成 deadline 约束塞 severity
  prepare_change     -> ok       ['data']          ← 自己改成 task_deadline 补丁，重试通过
```

它自己踩坑、自己发现、自己改对，全在同一轮里。以前这件事要靠外层退回一次才发生，
而且只有一次机会（`rounds=2`）。

**刻意只做 validate_dsl，不加自己的判据。** 上一轮刚吃过「同一段 JSON 两个解析器
两个结论」的亏。第一条测试就是逐字比对：工具报的错必须和 `pipeline._compile_check`
完全相等。

绿灯时返回一句「这不等于可以交卷」。不说的话模型会把 ok 当验收通过，交上去被
A1~A14 退回来——比不试还冤。

### submit_change：门槛卡在状态上，不在参数上

必须先有 `pending_change`（这一轮调过 `solve`、给过预览），否则直接拒绝。

允许模型凭一句"直接算"凭空发起求解，等于绕开"先看预览再确认"这条线。真排程
一次三分钟、占算力、生成新方案并改掉当前选中版本——这种动作不能是模型想起来就做的。

派活走的是和用户点确认**同一套分派**（`_start_dsl_solve` / `_start_planning_solve`），
没在 toolbox 里另写一条。上一轮 DSL 双路径已经证明，同一件事两份实现迟早给出两个答案。

工具说明里写死两种可调情形，并写了"写不出授权原话，就说明没被授权"。**说明本身
是安全边界的一部分**——光靠代码拦，模型会反复试、反复被拒，白烧轮次。

### read_jobs：把已经存在但够不着的能力递过去

`solve_jobs.py` 有 246 行，一整套给服务端和前端的接口，模型一个都碰不到。
于是最常见的多轮对话断在这儿：

```
用户「算完了吗」
模型「请到方案页面查看」      ← 它手里没有钥匙，不是偷懒
```

这个工具本身没写什么逻辑，就是包了一层。价值全在"接线"上。

### 顺手挖出第七个静默失败：A6 误判槽位

加完三个工具跑评测，62/68（改前 67/68），三条挂在 A6。

D01/D03 是采样波动（单跑就过），**C02 稳定挂 3/3**：

```
DSL：precedence{before:"任务001", after:"任务002", gap:2}   ← 完全正确
fills：row C03 ← "任务001" / "任务002" / 2                  ← 三条，忠实
A6：1 个行号出现互相矛盾的值，却仍按 dsl 提交                ← 判死
```

fills 里同一个 row 只记行号、不记槽位。三条 claim 各认领原文一段，A6 却读成
"三个互相矛盾的值"。整句降级成 clarify，用户收到"请说清楚"——它其实已经说清楚了。

改法按行分两类：约束/数据行放过**标量**（证明不了冲突），但 dict 照旧合并检查
（`{quantity:2}` 和 `{quantity:5}` 是同键两个数，真矛盾）；参数行仍然严格。

**教训：判据只能在自己看得懂的信息上下结论。** fills 里没有槽位名，A6 就不该
假装能判槽位冲突。

第一次改时图省事，把非参数行整行跳过，旧测试立刻红——它把"quantity 一个 2
一个 5"也放过了。**放宽必须精确到"哪一类值"，不能到"哪一类行"。**

### 最后的数

两轮连跑都是 68/68（改前 67/68）。需重试 4 条，平均 4494 ms（改前 3673）。

功劳要分开看：

| 改动 | 效果 |
|---|---|
| A6 修多槽位误判 | C02 从稳定挂 3/3 变回 dsl ← 主要来源 |
| 两条用例能力假设更新 | F03/F04 过 ← 次因 |
| `prepare_change` | 这条曲线上一分没涨 |

`prepare_change` 防的是"第一次改不对、第二次还改不对"，而 68 条里本来就没有
这种情况（110 条真实提问里也没有）。代价是 +22% 耗时。

**留着，但别拿这个 68 当它的功劳。** 它的收益要等积木变多才显出来。

D01/D03 在不同轮次里时过时不过，各单跑 4 次确认是采样波动，不是回归——
这也是为什么最后连跑两轮：单次 68 说明不了稳定性。

## 六、这一轮的教训

- **一个功能能不能用，不看它跑通了，看它出错时能不能被看见。** 六个缺陷里五个都是
  "返回了结果"，其中四个连 `FEASIBLE` 都写着。
- **判据之间不一致比判据太松更坏**：太松只是漏，不一致会让人反复怀疑被测物。
  这一轮三处不一致（解析器、validator/executor、兜底/解状态），每处都花了半天。
- **改测试之前先证明能力变了。** 三处 `note` 都是靠"紧日期 → INFEASIBLE，松日期 → 可行"
  这种对照才敢改；改完把证据抄进 `note`。
- **降级要留痕，但只留第一条。** 把五个后果都摆给用户看，反而看不出最初坏在哪。
