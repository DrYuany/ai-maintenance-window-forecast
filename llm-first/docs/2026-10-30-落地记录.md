# 落地记录：从提示词到可跑的产品

这一份记的是"施工日志"：建了什么、施工中撞出什么问题、最后跑出来什么数。
判断与方案见 `2026-10-30-五段方案复查.md`，用法见 `../README.md`。

## 一、建了什么

九个小模块，每个只管一件事，加起来是一条链：

```
护栏 guardrail ──否决──┐
                        ↓
缓存 ─→ 模型 client ─→ 归一化 contract ─→ 验收 verify ─→ 退回重试 ─→ 澄清
                                                ↑
                        行号目录 rows ── 系统切段 segment ── 提示词 prompt
```

| 模块 | 一句话 | 行数 |
|---|---|---|
| `prompt.py` | 系统提示词，表 A~F 全部由注册表生成 | 572 |
| `rows.py` | P/X/C/O/D 五组行号的唯一来源，提示词与验收器共用 | 116 |
| `segment.py` | 系统切段（A1 的分母），连接词表 | 66 |
| `contract.py` | 产物形状、枚举、键名归一化 | 163 |
| `verify.py` | A1~A10 + 数字对账 | 850 |
| `guardrail.py` | 结构性护栏，只否决不认领 | 59 |
| `client.py` | DeepSeek JSON 模式，标准库 urllib | 121 |
| `pipeline.py` | 编排 + 退回重试 | 239 |
| `rulebench.py` | 规则侧理解层复刻（只读 backend，走到调模型前停） | 259 |

外加 51 条测试、两个跑批脚本（`bench_compare.py` 一次快照、`bench_stability.py` 跑多遍看抖动）。

加一个 `server.py`（FastAPI :8011）和一个 `web/index.html`（双栏对照台）。

**`backend/` 一个字节没动**——`git status` 里只有 `llm-first/` 是新增。

## 二、施工中撞出的十个问题

### 1. `enum` 是万能出口

`只排风机003的任务` 被模型写成 `from=enum, value=1`。
A4 对 enum 的判定是"语义映射，机器核不了"，于是**任何值塞进去都能过**。

改：enum 的 `value` 必须是固定词。是数字就判错，数字只能走 `literal` 或 `convert`。
再进一步，enum 的 value 要去查该行的允许取值（策略四选一、量目录、是/否）。

### 2. 切段没认"但"

`成本压到最低，但高风险的必须全修` 被切成 `["成本压到最低", "但高风险的必须全修"]`。
模型抄 claim 时会去掉那个"但"，于是 A1 因为一个字判它漏话——**假警报**。

改法两处：连接词表加上 `但是/不过/而且/然后/于是/但`（长词在前），
切完再剥一层段首虚词。同时加了一条测试，断言**提示词里教的那串连接词
必须就是切段器认的那串**——两边不同源，A1 就成了随机判据。

### 3. A4 对 `convert` 只认算式

模型写 `calc="明天=2026-11-05"`，A4 报"算不出来"。可真正的问题是：
**原文只说"明天"，没有基准日期，任何具体日期都是猜的。**

改：`convert` 分两支。纯算式走数值核对；文字推导走"引用一致"核对。
另外单独加一条：span 里有相对时间词（明天/后天/下周/月底…）而 value 落了具体日期 → 判死，
理由写清楚"缺基准，应走 clarify"。

这条的反面也修了一次：一开始写成"span 里没日期就是猜的"，
结果冤枉了 `11月5日风大，别出海` 里的"别出海"（它的日期来自同句上一段）。
现在条件收窄到"span 里**有相对时间词**"。

### 4. 编译器报错模型看不见

退回消息只带 A1~A10 的失败项。于是一种情况会死循环：
A 全过，编译器一句"非法运算符 '='，允许 ('<=','>=','==')"就给退了，
模型永远不知道自己错在哪。

两处改：退回消息带上编译错误；提示词补一节「写法」，
把 `op` 两套取值、`linear` 的 `terms` 形状（`[[系数, 量], …]`）、
量的三种写法、filter 与 coeff 的允许值全部写清。
这些全是 validator 的确定报错，不写就是让模型去猜。

### 5. fill 没写 value 也能过（判据这一侧；根因在提示词，见第 8 条）

`人工单价涨到200，任务003最晚11月9日修完` 里，第二条 fill 的 `value` 是 null，
A4 因为"没东西可查"而空过——**这比判错更糟**。

改：`from≠default` 时 value 为空直接判错。加完这条，那句在重试后自己补上了
`2026-11-09T08:00:00+08:00`，两轮通过。

### 6. 提示词自己的三处矛盾（本轮之前修的）

`kind` 两套枚举、A2 把 `not_change` 锁死、`not_change` 能吞掉改动。
详见 `2026-10-30-五段方案复查.md`，都有测试盯着。

### 7. 对照脚本测错了对象（这一条比任何数字都重要）

第一版 `rulebench.py` 直接拿整句喂 `_parse_core`，得出"规则侧只覆盖一半改动"。
但产品的真实入口是：

```
批量场景 → parse() 先按逗号拆段 → 逐段解析 → 每段都命中才合并 → 才轮到模型
```

跳过拆段，等于拿一个产品不会走的输入去论证它不行。
更打脸的是：页面上打开规则主导版，同一句话它两个改动都做了——
那句"两个改动都做了"是大模型做的，规则层根本没插手。

**对照脚本测错对象，比没有对照更糟。** 现在 `rulebench.py` 按真实顺序走，
并且用 `test_rulebench.py` 五条断言把边界钉住（哪一句该是纯规则、哪一句该退模型）。

证据留在 `screenshot-rule-product.png`：规则主导版界面里同一句话，
"维修人工单价 150→200" 和 "任务003 最晚完工 → 2026-11-09 08:00 硬约束" 两条都在。
而规则层自己连第二段都读不出来——**这两条是大模型做出来的**。

### 8. 提示词说"每个 fill 交四样"，漏了 `value`

这是本轮最贵的一个错。模型照着"四样：claim 编号、row、span、from"写，
`value` 就不写；A4 逮住（"这条 fill 没有 value，出处无从核对"），
退回重试，模型自己补上——于是每次都能过，只是每次都多花一轮。

补成"五样"并说明"dsl 是结论，value 是出处账本"之后，
10 条句子的重试率从 4/10 掉到 1/10，那 1 条是"明天风大"，它本来就该澄清。

**判据没错，提示词错了，表现出来却像"验收器很有效"。**
如果不看尝试次数只看最终 route，这个错一辈子发现不了。

### 9. 不编日期，改成把"明天"夹带进去

A4 判死"编一个具体日期"之后，模型换了第三种绕法：

```json
{"claim": 1, "row": "D04", "span": "明天风大", "from": "default",
 "why": "原文未给具体日期，按不可作业处理",
 "value": {"day": "明天", "state": "不可作业"}}
```

`from=default` 只要求写 `why`，于是 A4 放行；`{"day": "明天"}` 一路进编译器。
**"没编造"不等于"能用"。** 两头都堵：value 里不许留相对时间词（A4），
日期字段必须是日期（A9）。加完之后同一句 5 次全部 clarify，不再忽好忽坏。

### 10. 退回重试会诱导模型"硬凑"

`只排风机003的任务` 第一版硬凑成 `linear: count(filter=风机003) == 1`
——"正好完工一个003的任务"，跟"只排003"是两回事，但 A1~A10 全过。

两处改：能力边界里加第四条（限定排程范围没有对应积木，不许拿 `count==1` 顶替）；
退回消息里加一句"能过验收不等于表达对了"。
改完它自己改成 `reject` + `row_not_wired`，一次就过。

这也划出了验收器的上限：**判据能拦"值编不出来"，拦不住"表达式能编译但意思变了"。**

十条话，两边各读一遍（`scripts/bench_compare.py --save`）。
**先说清楚性质**：右边是模型，同一句重跑会抖，所以这一张只是快照；
稳不稳看后面那张跑 5 遍的分布表。左边是规则层，确定性，重跑不变。

**最扎眼的一列是第二列：10 条里规则层能独立交出 DSL 的只有 2 条**
（`任务001和任务002…` 的复合句、`钱不超过300万`），另有 1 条被非改类守卫直接判死。
其余 7 条它读不出来——包括 `把船租降到8万` 这种招牌改写。
换句话说，**规则主导版在真实说法上本来就是大模型在干活**，正则只是省了几次调用。
这一点以前没被说清，因为评测集里的句子是按正则的形状写的。

### 稳定性：每条跑 5 遍（`scripts/bench_stability.py -n 5 --save`）

| 结论 | 数 |
|---|---|
| 最终 action 在不同轮次抖动的 | 0/10（补完提示词之后） |
| 需要退回重试才过的 | 1/10（只有"明天风大"，而且两轮之后仍然澄清） |
| 重试之后仍判死的 | 0/10 |
| 平均耗时 | 0.8~2.5 秒（"明天风大"最慢：它要多跑一轮） |

**这张表推翻了我之前的一个说法。** 补提示词之前，10 条里有 4 条靠"退回重试"才过，
当时我把它记成"验收器在干活"。真正的原因是提示词里 `fills` 那一节写着
"每个 fill 交四样：claim 编号、row、span、from"——**漏了 `value`**。
模型照着写，A4 判死，重试时它自己补上，于是看起来"重试很有效"。
补成"五样"之后，同一批句子的重试率从 4/10 掉到 1/10。
教训不在判据，在提示词：**一句话漏写一个字段，代价是全表的稳定性。**

### 三个值得单独说的

**1. 规则侧在复合句上不是"错"，是"根本不走这条分支"。**
`parse()` 先按逗号拆段，逐段解析，**每段都命中才合并**。
`人工单价涨到200，任务003最晚11月9日修完` 里第二段规则层一层都认不出，
于是整句退回大模型。所以在这句话上，"规则侧 vs LLM 侧"其实是
"旧提示词的模型 vs 新提示词的模型"——真正被比的不是有没有用模型，是**交出来的东西有没有人验收**。

**2. `钱不超过300万` 规则侧交了三项，用户只说了半句。**
除了 budget，还塞了 `strategy=成本最低优先`、`mode=分层`、`solver.seconds=300`。
"多填"和"少填"是同一种病：都不是用户说的话。
LLM 侧只交用户说的那一条。

**3. `只排风机003的任务`：把边界写清楚之后，它自己认账了。**
第一版模型硬凑成 `linear: count(filter=风机003) == 1`
——"正好完工一个003的任务"，和"只排003"是两回事，但 A1~A10 全过。
把"限定排程范围没有对应积木、不许拿 count==1 顶替"写进能力边界之后，
它改成 `route=reject` + `row_not_wired`，一次就过。
**这一条同时暴露了验收器的上限**：判据能拦"值编不出来"，拦不住"表达式能编译但意思变了"。

## 四、还欠什么

1. **执行侧没接**：本版只到"产物 + 验收"，没有真的跑求解。
   接的话复用 `backend` 的 `dsl_to_request` + `product_planner`，但那要几十秒，
   会让对照台变成"等结果"。先不做。
2. **`about` 三个读请求没执行器**（fact / reason / diff），目前只统计。
3. **相对时间要基准**：需要在会话里注入"今天几号"。现在是两轮之后澄清，
   用户得多说一句话——这一步本来就该是系统做的。
4. **"能编译"不等于"意思对"**：`count==1` 那一次就是例子。A1~A10 管的是
   "值有没有出处、结构合不合法"，管不了"这个表达式是不是用户那句话的意思"。
   要管，得把 claim 文本和 DSL 语义对齐——那是另一套东西（也是下一步真正值钱的）。
5. **18 条错误分类学的案例**还没全量接进来做回归；现在是 51 条手工构造的测试。
6. **规则侧复刻要跟着 backend 改**：`rulebench.py` 是按 `agent_runtime` 的入口顺序抄的。
   backend 那边一变，这个复刻就会静默失真——它没有自动校验，只有 `test_rulebench.py` 里
   五条盯边界的断言（拆段合并、部分命中就退模型、口语改写认不出、兜底要标丢数）。

## 五、补漆：跑压力集之后又踩到的七个坑

上面第四节的"还欠什么"基本都在这一天之内补掉了，但补完之后去跑 backend 那 221 条，
又崩出一批新东西。**这一节的共同点：七条里有六条是判据自己错了，不是模型错了。**

### 1. A1 因为连接词冤枉人（57f1d1f）

`T01和T02不能同时修` 的 DSL 完全正确，但 A1 判它"1/1 段没有被覆盖"。

原因是切段器把"同时"当连接词换成了逗号，段里就没有这两个字了；而 claim 是**照抄原文**
的，里面还在。两边形态不同，逐字比对必然对不上。

修法是两边都去掉连接词再比。**教训**：判据要求产物之间"对得上"，那它自己得先把
不承载内容的差异抹平，否则要修的不是模型，是判据自己。

### 2. A6 把 lexmin 的两个阶段当成"同一行两个值"（57f1d1f，6c995a9）

`lexmin` 的必填是 `stages`（一串），"先最小化 A 再最小化 B"天然在同一行填两条。
同一类还有一个：`叶片11月5日到2套，到货前不能开工` 被切成两条 claim，
一条填 `{part, at, quantity:2}`，另一条填 `{part, at, blockBefore:true}`——那是同一条
补丁的两半，判成"互相矛盾"就等于不让模型分句表达。

现在的口径：**没有同一个键取值不同，就能并成一条。** 同一个键填两个不同的数照旧判死。
"本来就要装一串"的原语名单从注册表算（`required` 含 `stages`/`weights`），不手抄。

### 3. A4 不认中文数字（dfd19fe）

`船坏了，只剩两条作业线` 被判"span 里没有任何数字"——用户原话里明明白白写了"两条"。

但这里有个必须掰开的界限：

- **span 认中文数字**（用户说了就算），带量词一起算：`三百万` = 3000000
- **填进 dsl 的值不认**（"八小时"不是求解器能用的数）
- **整句数字对账也不认**（见第 4 条）

### 4. 对账侧认了中文数字，当天冒出三条假警报（f5dcb4c）

同一笔改动里 `audit_numbers` 跟着读中文数字，结果 `同一天`、`一天`、`一小时`
全被读成数 → Q302/Q309/Q340 报"丢数 1"。一次真丢话都没多抓到。

**判据的适用范围决定它的口径。** A4 比的是一条 fill 的 span 和它填的值，范围窄，
中文数字读对了收益很大；对账拿整句话比整套 DSL，范围宽到连虚词都像数。
收益撑不住误报就收回。

同一轮还给对账加了第三类"本来就该不同的数"：增减量。`船少一条` 现值 3 减 1 得 2，
DSL 里该出现的是 2；要求那个 1 出现等于让用户把算式写两遍。

### 5. A7 的退回消息没法用（6c995a9）

`严重故障11月8日前必须修完` 被写成 `deadline{severity:"高"}`——`deadline` 必填是 `task`。
退回消息只写"1 项缺必填字段"，模型下一轮还是不知道改哪儿。**有重试机制，但反馈给不出
能改的信息，重试就等于没用。** 现在写明"deadline 缺 task（必填是 task/time）"。

### 6. 现值表里少了窗口（6c995a9）

`窗口02提前两天开始` 原来只能反问用户。和"船少一条"是同一件事：
这两个值系统自己知道，让用户重说一遍是产品的问题。加了 `window_values()` 之后，
现在能直接换算到 `2026-10-31`。

### 7. 为了改 Q101 把 Q101 自己改坏了

新规则写"相对增减要自己算成绝对值"，把倍率也算成绝对值了——`船租上涨20%` 变成
`= 14400`，原话里的 20 被判"丢数"。

改成一张两行的表：加减类算绝对值（`=`），比例类保持比例（`*`）。
**自己当天引入的回归当天就被压力集抓到，比明天被别人抓到便宜得多**
——压力集每改一次都重跑一遍，就是为这件事付的钱。
