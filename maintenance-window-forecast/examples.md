# Few-Shot 对话示例

下面的示例不是给执行器用的，而是给负责理解用户自然语言的大模型用的。目标是示范如何把业务话术稳定地映射成结构化 `updates`，以及什么时候必须拒绝。

## 示例 1：经济性调高点

用户：

> 经济性调高点

模型应理解为：

- 这是“改权重”
- 目标是提高 `weights.loss`
- “调高点”按默认规则解释为约 `10%`

结构化更新：

```json
{
  "weights": {
    "loss": 1.1
  }
}
```

执行后应说明：

- 已提高经济性权重
- 其余参数保持不变
- 方案会更偏向降低停机损失

## 示例 2：风险优先

用户：

> 风险优先

模型应理解为：

- 这是预置策略切换，不是细粒度手调
- 应优先调用预置策略 `risk_priority`

结构化动作：

```json
["risk_priority"]
```

如果用户要求“对比经济优先和风险优先”，则应调用策略对比，而不是只跑单一方案。

## 示例 3：去掉某部件

用户：

> 这次先别考虑变频器

模型应理解为：

- 这是“改对象”
- 应从默认部件集合里排除 `变频器`

结构化更新：

```json
{
  "objects": {
    "exclude_components": ["变频器"]
  }
}
```

## 示例 4：只看部分风机

用户：

> 只看1号和2号风机

模型应理解为：

- 这是“改对象”
- 应缩小风机范围

结构化更新：

```json
{
  "objects": {
    "turbine_ids": [1, 2]
  }
}
```

## 示例 5：修改部件严重性

用户：

> 齿轮箱严重性提高到12

模型应理解为：

- 这是“改部件参数”
- 不是全局风险权重，而是具体部件的 `severity`

结构化更新：

```json
{
  "component_params": {
    "齿轮箱": {
      "severity": 12.0
    }
  }
}
```

## 示例 6：做方案对比

用户：

> 对比经济优先和风险优先两种方案

模型应理解为：

- 这是“做方案对比”
- 应直接调用预置策略对比

结构化动作：

```json
["economic_priority", "risk_priority"]
```

输出应突出：

- 两种策略修了哪些部件
- 总损失差异
- 风险惩罚差异
- 各自更适合什么场景

## 示例 7：不支持的新约束请求

用户：

> 齿轮箱和主轴不能同时修

模型应理解为：

- 这不是参数调整
- 这是新增约束逻辑
- 当前脚本不支持直接实现

正确回复方式：

- 明确说明这是“新约束”，当前 skill 不能直接通过参数调整实现
- 不要硬把它翻译成 `updates`
- 如果合适，可以补一句：当前能做的是调整并行上限、对象范围、权重和部件参数

## 示例 8：容易混淆的“严重性调高点”

用户：

> 严重性调高点

这里有歧义：

- 可能是全局 `weights.severity`
- 也可能是某个部件的 `severity`

正确做法：

- 先追问一句，尽量短：
  - “你是想提高整体风险权重，还是提高某个具体部件的严重性？”

## 示例 9：多轮场景

第一轮用户：

> 时间窗改48小时

第二轮用户：

> 经济性再调高一点

模型应尽量理解为：

- 第二轮是在上一轮已生效配置基础上继续调整
- 如果当前系统拿不到会话状态，必须明确说明：
  - “这次按默认场景重新解释”

## 示例 10：不应臆造结果

用户：

> 经济性调高点，告诉我结果

错误做法：

- 不调用执行器，直接凭经验猜“会优先修发电机和齿轮箱”

正确做法：

- 先生成更新
- 调用执行器
- 再基于真实结果解释
