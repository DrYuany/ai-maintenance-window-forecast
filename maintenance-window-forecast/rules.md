# 检修窗口期预测能力规则

本文档面向负责理解用户自然语言的大模型，而不是面向求解器实现本身。目标是让模型稳定地把用户话术转换成结构化 `updates`，再交给执行器计算。

## 1. 系统边界

当前脚本支持的是：

- 调整目标权重
- 调整已注册的约束参数
- 调整优化对象范围
- 调整已注册的部件参数
- 对比预置策略

当前脚本不支持的是：

- 动态新增一种全新的数学约束
- 临时改变模型结构
- 引入脚本中不存在的新目标函数
- 让模型自动编写 MILP 代码
- 没有参数承载的泛泛要求，例如“尽量合理一点”

遇到不支持的请求时，模型必须明确说：

- 当前脚本无法直接实现该要求
- 这是“需要扩展模型能力”的需求，而不是“调参数”需求
- 如果可能，提供最接近的可执行替代方案

## 2. 结构化输出规范

模型给执行器的结构必须是：

```json
{
  "weights": {},
  "constraints": {},
  "objects": {},
  "component_params": {}
}
```

四个顶层字段都不是必填；只提交要修改的字段。

### 2.1 `weights`

可改字段：

- `loss`
- `duration`
- `severity`

含义：

- `loss`：停机损失权重，越高越偏经济性
- `duration`：总维修时长权重，越高越偏尽快完成
- `severity`：风险/严重性权重，越高越偏优先修高风险件

### 2.2 `constraints`

当前仅支持改以下约束参数：

- `time_horizon`
- `max_parallel_tasks`
- `rated_power_mw`
- `cut_in_wind_speed`
- `rated_wind_speed`
- `unrepaired_severity_factor`

注意：

- 这是“改约束参数”，不是“新增约束”
- 用户如果说的是“加一个新规则”，不能硬翻成这里的字段

### 2.3 `objects`

可改字段：

- `turbine_ids`
- `include_components`
- `exclude_components`

### 2.4 `component_params`

格式：

```json
{
  "component_params": {
    "发电机": {
      "duration_hours": 10,
      "severity": 12.0
    }
  }
}
```

每个部件当前允许修改：

- `duration_hours`
- `severity`
- `wind_speed_limit`
- `wave_height_limit`
- `can_night_work`

## 3. 意图分类规则

### 3.1 改权重

典型话术：

- “经济性调高点”
- “风险优先”
- “尽量快修”
- “别太在意维修时长”
- “把严重性看重一点”

映射原则：

- 成本/收益/损失/经济性 -> `weights.loss`
- 工期/速度/尽快完成 -> `weights.duration`
- 风险/严重程度/高危部件 -> `weights.severity`

### 3.2 改约束参数

典型话术：

- “时间窗改成48小时”
- “最多同时修2个部件”
- “把不修惩罚再调高”

### 3.3 改对象

典型话术：

- “只看1号和2号风机”
- “先别考虑变频器”
- “只算齿轮箱和发电机”

### 3.4 改部件参数

典型话术：

- “发电机维修时长改成10小时”
- “齿轮箱严重性提高到12”
- “叶片允许施工的最大风速改成13”

### 3.5 做方案对比

典型话术：

- “对比经济优先和风险优先”
- “比较快修优先和经济优先”

优先使用预置策略：

- `economic_priority`
- `risk_priority`
- `fast_repair_priority`

## 4. 模糊词解释规则

默认基于当前配置里的现值调整。

- “一点” / “一点点” / “稍微”：约 `10%`
- “多一点” / “再高一点” / “再低一点”：约 `20%`
- “明显提高” / “大幅提高” / “大幅降低”：约 `30%`

### 4.1 优先级型表达

- “经济性优先” -> `economic_priority`
- “风险优先” -> `risk_priority`
- “尽量快修” / “快速修复优先” -> `fast_repair_priority`

## 5. 歧义处理规则

直接执行，不必追问：

- “经济性调高点”
- “时间窗改48小时”
- “只看1号和2号风机”
- “去掉变频器”
- “发电机维修时长改成10小时”

应先澄清：

- “严重性调高点”
- 同时表达多个冲突方向
- 用户想表达的不是已注册参数

## 6. 多轮会话记忆规则

若系统能拿到上次的已应用配置，则基于上次配置继续调。
若拿不到，则按默认配置为基准，并明确说明。

## 7. 常见业务场景

### 场景 A：更省钱

- “经济性调高点”
- “成本更重要”
- “尽量少损失发电收益”

### 场景 B：更保守

- “高风险部件优先”
- “风险优先”
- “严重的先修”

### 场景 C：缩短窗口期

- “窗口期改48小时”
- “这次只给两天”

### 场景 D：缩小对象范围

- “只看1号和2号风机”
- “先不算变频器”
- “只考虑齿轮箱和发电机”

### 场景 E：方案对比

- “对比经济优先和风险优先”
- “比较尽快修和经济优先”

## 8. 不支持场景清单

必须明确回复当前脚本不支持直接实现：

- “增加一个规则，让齿轮箱和主轴不能同时修”
- “每天18点以后必须收工”
- “让第一台风机先修发电机再修齿轮箱”
- “给我自动生成一个新的数学模型”

## 9. 结构化调用示例

### 示例 1：经济性调高点

```json
{
  "weights": {
    "loss": 1.1
  }
}
```

### 示例 2：时间窗改48小时，最多同时修2个部件

```json
{
  "constraints": {
    "time_horizon": 48,
    "max_parallel_tasks": 2
  }
}
```

### 示例 3：只看1号和2号风机，去掉变频器

```json
{
  "objects": {
    "turbine_ids": [1, 2],
    "exclude_components": ["变频器"]
  }
}
```

### 示例 4：发电机维修时长改成10小时

```json
{
  "component_params": {
    "发电机": {
      "duration_hours": 10
    }
  }
}
```

## 10. 执行器调用规则

不要自己模拟优化结果，不要自己编排维修方案。

执行器入口：

- 参数调整：
  `maintenance_update_executor.execute_parameter_updates(updates, solver_name="ortools")`
- 预置策略对比：
  `maintenance_update_executor.execute_named_strategy_comparison(strategy_names, solver_name="ortools")`

## 11. 最终原则

大模型负责：

- 理解
- 归类
- 生成结构化更新
- 解释结果

执行器负责：

- 校验
- 计算
- 返回真实结果

当用户需求超出参数化能力时，不要硬映射，不要臆造数学含义，必须明确说当前脚本做不到。
