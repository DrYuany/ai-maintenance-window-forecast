# 意图识别、澄清与建模变更预览

## 目的与边界

自然语言解析负责还原用户的目标、目标间关系、约束强度、范围、数据口径及拟议变更；它不负责替用户裁定业务偏好。大模型可识别语义、上下文和未覆盖的新表达，确定性模板/规则负责检查字段完整性、映射已登记指标、线性边界、状态门和生成 ModelSpec。大模型无法确认的内容必须保留为未知并提问，不能以默认权重代替回答。

本模块的分类采用**正交字段**而不是互斥的单标签：一次请求可以同时包含目标、约束、范围和数据变化。每个字段内部应有互斥取值；完整解析结果可以是多个字段的组合。100 个压力场景按其主要判定点分成十组，每组十例，不代表十类请求彼此排斥。处理顺序是：先识别请求操作与对象，再提取目标及关系、约束强度、范围、数据/时效/来源，最后检查语义歧义和可建模性。

## 解析槽位

对每项用户要求，尽量填充以下槽位；没有提及的值记为 `unspecified`，不得自动补成零、软约束或默认权重。

| 槽位 | 互斥值（每个对象各选一个；未提供值记 `unspecified`） |
|---|---|
| 请求操作 | 只读解释、沿用现有、修改模型、比较方案、运行假设情景、生成业务单据/执行动作 |
| 变更类型 | 无变更、新增、删除、替换、参数调整、数据刷新；一条请求可以对不同对象分别记录多种变更 |
| 对象类型 | 目标、约束、决策/变量、数据、范围/集合、报告、业务动作 |
| 目标方向 | 最小化、最大化、满足阈值/区间、仅判断可行性、仅报告 |
| 目标关系 | 单目标、严格先后（分层）、可交换折中（加权）、无偏好声明的多目标、关系未定 |
| 约束属性 | 强制硬约束、可违反的软目标（违反代价待定义）、情景条件、只读说明、属性未定 |
| 作用范围 | 全部、明确子集、排除子集、固定已批准部分、范围未定；具体键含风场/风机/部件/告警/窗口/时间段 |
| 数据状态 | 已给定且有来源、用户指定假设、预测/草案、缺失、冲突、过期/待刷新 |
| 指标定义状态 | 已登记、已定义且可构造、定义不完整、数学结构待验证、已知不支持 |
| 交互授权 | 只讨论、用户明确请求继续、预览后等确认、用户跳过预览、确认业务动作；一个授权不能推及其他对象/动作 |
| 建模状态 | 可进入候选 ModelSpec、需澄清、需扩展提案、拒绝该数学结构；整个请求的状态取所有必要对象中最受限者 |

这些维度彼此正交，因此一次表达可以同时是“修改模型 + 新增目标 + 加权 + 有一项缺数据”。MECE 指每个槽位内部的值互斥且覆盖已知/未知情况，跨槽位组合不互斥；不要强迫整句只落入一个意图类别。十组各十个场景是主压力点索引，不是十个互斥的用户类型。

目标关系按以下规则裁定：

1. 明确“先 A 再 B”“A 优先于 B”“只有 A 达到目标后才优化 B”映射为分层；保留原话并确认其确为不可交换优先级，若语境已明确则不重复追问。
2. 明确“按权重/比例/愿意用多少成本换多少改善/允许互相牺牲”映射为加权；使用用户提供的权重或逐项询问可接受偏好。权重必须绑定明确指标及归一化口径，不能从“重视”“优先考虑”猜数值。
3. “都重要”“兼顾”“同时考虑”“成本优先也要考虑严重故障”“尽量兼顾”等，若没有明确顺序或折中意愿，关系标记为 `unresolved`，询问“严格先后还是允许折中”；不得直接路由到某个预设策略。
4. “必须、不得、不能、至少、至多、截至、只有……才……”优先按硬约束候选解析；若可能是愿望表达或与别处冲突，澄清硬/软及冲突处置。对法律、安全、许可条件，不得降为软目标。
5. 标准策略词只在其登记定义与当前语境一致时映射。若用户为熟悉名称提供了不同解释，先说明版本定义并询问是沿用标准定义还是提出新版本。

## 澄清规则

仅针对会改变目标顺序、可行域、解读口径或是否可求解的缺口提问。把可独立回答的问题合并成一轮，优先给出少量明确选项，并保留自由回答。提供用户可选的解释，不诱导某一答案。

典型多目标问题：“成本优先，同时照顾高严重故障”应追问：

- A：严格先最小化成本，再在同成本优解中尽量完成高严重任务；
- B：严格先完成高严重任务，再最小化成本；
- C：允许两者折中，指定/讨论相对权重；
- D：其他关系，请描述。

如果选 C 而未给偏好强度，继续询问权重或提供有业务含义的对比方案；未经用户选择，不以模板默认权重代表用户偏好。当前注册指标不能表达用户提出的新目标时，不要求用户把新目标硬塞进旧模板：若新目标可用已知数据和声明变量构成有单位、方向明确的线性表达式，可以生成待审扩展提案；必要时向用户确认定义后再纳入候选 ModelSpec。若涉及非线性、决策依赖系数、未审线性化或未知数据，返回 `extension_proposal` 或 `clarification_required`，阻止求解。

区分“意图不明确”和“模型不可表达”：前者先澄清语义；后者解释模型边界并提出可验证的替代定义。区分“数据缺失”和“用户没有指定”：询问真实数据源/口径，或由用户明确选择假设情景；不得把未知库存、天气、价格、窗口或成本当零。

## 建模变更预览

对新增、删除、替换或实质修改目标/约束/数据口径，先生成紧凑的**建模变更预览**：

- 原模型与拟议模型的目标、约束、范围、数据口径差异（新增/移除/修改分别列出）；
- 采用的优先顺序/权重、硬软属性及用户未明确的假设；
- 对可行域、目标取舍、数据需求的预期影响；
- 状态：可继续、需澄清、需扩展提案，不能把预览称为已求解结果。

交互选项为“确认继续 / 修改 / 跳过预览”。用户明确跳过时，可按其原始明确指令继续确定性建模与求解准备；跳过不构成对未说出的偏好、假设、缺失数据或非法模型的授权。若字段含糊仍需澄清；若只是解释、读取现状或未改变模型，不强制展示变更预览。输出检修单、更新库存、提交审批等外部/业务动作沿用其自身授权流程，不因跳过模型预览而获准。

## 100 个压力场景

完整请求及期望路由见 `tests/intent-scenarios.json`。十组各覆盖一个主要判定维度：目标顺序、权衡、关系歧义、硬软约束、目标变更操作、指标扩展、范围、数据与来源、时间/情景、组合请求及预览控制。评测看的是解析状态和下一步，不要求固定措辞；同一请求可触发多个槽位，主标签仅指主要压力点。

## 解析输出建议

```json
{
  "operation": "modify_model",
  "objectives": [{"metric": "总经济成本", "direction": "minimize"}],
  "objective_relation": "unresolved",
  "constraints": [{"meaning": "库存不超可用量", "strength": "hard"}],
  "scope": {"turbines": "all", "horizon": "unspecified"},
  "data_status": "needs_confirmation",
  "proposed_changes": [],
  "clarification_questions": ["成本与高严重任务是严格先后还是允许折中？"],
  "model_status": "clarification_required",
  "solver_dispatch_allowed": false
}
```

解析 JSON 不是 ModelSpec。只有业务语义、数据来源、线性表达式和所有影响决策的澄清完成后，才能编译并运行结构校验器。
