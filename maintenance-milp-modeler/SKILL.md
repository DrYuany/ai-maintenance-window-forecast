# Maintenance MILP Modeler

Turn operational language into an auditable ModelSpec; never let an LLM invent solver-ready mathematics silently.

## Runnable first-stage product

For an ordinary recommendation, execute the bundled product runtime instead of stopping at a ModelSpec. The product data project is the parent of this skill directory in the source checkout; an installed skill needs an explicit `--project` pointing to the project containing `data/phase1-demo` and `data/场景评测`. Default to `基座01`, cost-first, layered goals, and the as-of time defined in the synthetic base. Run `python <skill>/scripts/maintenance_product.py --project <project> plan --output <fresh-output-dir> --seconds 60`. Read the returned run ID and `推荐摘要.md` / `结果.json` before answering. Do not report an optimal claim unless the corresponding stage says `OPTIMAL`; a verified feasible incumbent is still a useful recommendation. The report compares severity-first and low-wind-first heuristics under the same inputs and hard constraints; savings are stated only when completed task sets match.

The runner takes `--base 基座01..05`, `--as-of`, `--strategy` (four registered strategies), `--mode 分层|加权`, and JSON `--weights`, `--limits`, `--overrides`. For a real input, pass `--input` with a versioned four-field envelope (`schema_version`, `业务数据`, `基座`, `元数据`) and source/provenance; synthetic forecasts must never be silently mixed with it. The planner excludes alerts received after as-of, recalculates deadlines, enforces line and stock constraints, computes weather-dependent work, and independently rechecks feasibility and economic cost. Formal infeasibility produces a separately labelled partial diagnostic; timeout/unknown does not prove infeasibility.

After the user selects a recommended window and asks for a work order, run `draft <RUN-ID> --windows <窗口编号>`; this creates a pending order. Human approval is explicit through `approve <WO-ID> --actor <reviewer>`, with a reviewer distinct from the creator. Approval checks the input hash and revision, reserves planned stock, then generates `出海清单` and `库存变化单`, readable with `documents <WO-ID>`. Planned reservations do not deduct physical stock. Actual stock changes only on `post-external`, `issue`, and later reconciliation. `orders`, `audit`, `complete`, and `cancel` support the remaining workflow. Use a unique `--key` for every write and reuse it for retries. No user approval is inferred from merely requesting a recommendation.

The product runner is a local reference implementation. It requires Python and OR-Tools, and the provided data are synthetic. Before operating against a real site, connect authenticated source systems, persistent access control, service monitoring and real execution feedback; do not claim those are present merely because the local solve passes. When a request introduces an unsupported construct, use the extension workflow below, show the exact proposed modeling changes, and validate before use.

## Workflow

1. **Route by actual capability.** Use `maintenance-window-forecast` only when its registered executor supports every requested field. Parameter changes in a different model (vessel day rates, work lines, inventory, budgets) must not be forced into its legacy weights or parallel-task fields. Stay with this skill for those requests and for added decisions, objectives, or constraints. For the first-stage wind-maintenance project, read [the project profile](references/phase1-profile.md) when its data and parameter package are present.
2. **Resolve intent and goal mode.** Parse goal relationships before selecting a preset. Load [the versioned goal contract](references/objective-templates.md) and [intent and change-review protocol](references/intent-and-change-review.md). Do not infer priority or weights from “also consider”, “balance”, “as much as possible”, or “both matter”; clarify when the relationship changes the chosen solution. Preserve registered metric meanings; in weighted mode use the default or explicit weights, normalize with finite declared-variable bounds, and record weights/ranges. Unregistered goals enter the extension path; never silently map them to a different preset or use an unapproved large penalty as a hard requirement.
3. **Ground and match the model.** Identify decisions, known data, units, source/time, and missing inputs. Match requested objectives, constraints, and data fields against [the objective metric catalog](references/目标指标库.json), [constraint catalog](references/约束构件库.json), [data dictionary](references/数据字典.json), and [objective composition rules](references/目标组合规则.json). These are the current supported vocabulary, not a closed list. An unmatched request becomes a candidate construct: define semantics, direction/strength, units, data dependencies, and a linear expression; validate it before use. Read [the learning protocol](references/自学习流程.md) for promotion after successful runs. For the first-stage 10 MW reference turbine, read [the project profile](references/phase1-profile.md); configurable synthetic base sets are in `data/场景评测/五组基座配置.json` and are generated by `scripts/generate_base_scenarios.py`. Never present those synthetic scenarios as real forecasts. Never fabricate inventory, weather, energy price, task duration, or authorization windows. Distinguish infeasibility from missing data or solver failure.
4. **Preview and compose.** For material objective/constraint/data/scope changes, show a concise add/remove/modify preview and offer confirm, edit, or skip-preview. Skipping only skips this review interaction; it does not resolve ambiguity, supply missing data, waive validation, or authorize separate operational actions. Build a ModelSpec using declared bounded variables, linear objective expressions, and custom linear rows over declared variables. New reusable primitives are proposals until validated. Read [the ModelSpec contract](references/model-spec.md), [the component catalog](references/milp-components.md), and [the linearity boundary](references/linear-milp-boundary.md) as relevant.
5. **Validate.** Run `python scripts/validate_model_spec.py <model.json>` (or pipe JSON to stdin). A nonzero result blocks solver dispatch. The validator checks structure, references, finite bounds, and canonical linear form; it does not prove units, business correctness, feasibility, or optimality. Those need separate checks.
6. **Choose tools.** The bundled `scripts/solve_model_spec.py` maps validated canonical ModelSpec rows to OR-Tools CBC, if installed. Run `python <skill-directory>/scripts/solve_model_spec.py <model.json> --seconds 60 --output <result.json>`. Resolve script paths from this skill's actual directory, not the current shell directory. Check returned status, constraint verification, objective-stage verification, and whether all lexicographic layers were proven. It is a generic adapter, not an automatic maintenance model compiler. Discover which data connectors and solvers are actually available. If no solver is available, return a validated specification and state that it is not solved. Dispatch only a `ready` spec with no unresolved data.
7. **Report.** Return the interpreted request, objective order, new/changed constraints, assumptions, unresolved risks, tool and solver status, result provenance, and sensitivity/alternatives where available. Never label a heuristic result as optimal or infeasible unless the solver reported that status.
   For ordinary user-facing recommendations, use [the default cost and reporting contract](references/默认成本与结果展示.md). Unless the user specifies another objective, optimize total economic cost and compare the result with the severity-first and low-wind-window-first human-rule baselines. Lead with windows, tasks, total cost, and the two savings figures; put detailed schedules, parameters, inventory and audit data in expandable detail.

When formal deadlines cannot all be satisfied, preserve the formal result and present any partial diagnostic model separately. Never silently authorize lateness, delete blocked tasks, or treat an unknown future window as proven infeasibility. Distinguish per-task impossibility, competition in one selected solution, missing inputs, and solver timeout. Unconfirmed arrivals may be used only in an explicitly isolated hypothetical scenario; they are not available stock in an executable plan.

## State contract

- `ready`: sufficient grounded inputs and validated registered/linear structure; solver may be considered.
- `clarification_required`: a material ambiguity or missing data prevents a defensible solve.
- `extension_proposal`: a requested primitive or formulation is outside the reviewed component catalog; explain the proposed semantics and validation needed.
- `rejected`: non-MILP structure is requested and no valid registered linearization applies.

Keep `status` truthful. The validator intentionally accepts only `ready` for solver dispatch.

## Non-negotiable boundary

ModelSpec expressions use only `constant + sum(coefficient × declared_variable)`, where each coefficient is a finite constant or a known, fixed data parameter. Decision-variable products, decision-dependent coefficients or denominators, arbitrary nonlinear functions, and unbounded big-M formulations are not solver-ready. A valid MILP linearization may be used only if it is a reviewed template with explicit finite bounds and its assumptions are recorded. See [linearity boundary](references/linear-milp-boundary.md).

## Evaluation cases

Before changing this skill, check `tests/scenarios.json` against the workflow and validator; record outcomes in `TEST_REPORT.md`. For a new ready golden case, run the validator on its ModelSpec. These cases test behavioral routing and boundaries, not a live LLM's quality.
