# 小一修 · 设计宪法

海上风电检修排程的**降級版**建模通道。与大一修（`dsl_core/`）并列，共用同一套求解内核，
但把大模型的职权从「写程序」降级为「填表」。

---

## 一、一句话定位

> **模型的骨架和约束族预先写死并注册；大模型唯一能做的是往已注册的槽位里填一个数字。**

对应到 MILP 上，就是：**约束的条数与形式固定，只有常数（右端项、系数、开关）可变。**

|  | 大模型产出 | 校验器要验什么 | 完备性怎么保证 |
|---|---|---|---|
| 大一修 | 任意线性表达式（组合 15 种原语） | 线性性、量纲、实体存在、原语合法 | 靠人工补对账规则，补漏了就出事故 |
| 小一修 | `槽位 + 索引 + 数字` 三元组 | 槽位在册、索引存在、数值在区间 | 族固定则对账规则天然闭合 |

**两种「受控」的区别要讲准：**

- 大一修的受控是**控制构造过程**——原语是积木，大模型每轮现场拼出新形状。
  「高危人工费 ≤ 50 万」这条约束在模型里本不存在，是大模型当场造的。
- 小一修的受控是**没有构造**——形状清单冻结。同一句话，预算族那条约束早就预写在清单里
  （右端项默认 ∞，不生效），大模型只是把 ∞ 改成 500000。

实现细节（不改变形状封闭）：默认不生效的约束**激活了才写进模型**，省求解时间；
但「能写哪条」的清单是冻结的，懒加载不改变封闭性。

**三种可写动作**（不是只有系数）：

1. 改数字（右端项、系数）
2. 开/关一条预写约束
3. 把一部分选择**钉死**（如「018 只上 2 号船」）——约束本身预写，默认关着

## 二、为什么族清单是这样推出来的（完备性的来源）

族清单不是拍脑袋列的，是从**候选行的数据结构**投影出来的。

一条候选行（`product_planner.candidates` 的产物）携带的字段是封闭枚举的：

```
任务编号、风机编号、部件编号、部件名称、严重等级、窗口编号、
开始、完成、下项最早开始、作业段、（+ build_model 补的）作业线
```

计划员的每个需求都是「对某个字段投影提出问题并给出要求」。**字段封闭 → 疑问封闭 → 族封闭**：

| 投影 | 能问的问题 | 预写族 |
|---|---|---|
| 任务身份 | 修几个 | `count_min` / `count_max` |
| 开始/完成时间 | 何时修 | `bucket_min/max`、`earliest`、`deadline_delta` |
| 作业线 | 用哪条船 | `line_fixed`、`cap_max` |
| 任务对 / 集合 | 谁先谁后、同异 | `before_seq`、`same_bucket`、`all_diff`、`sev_*` |
| 成本项 | 花多少钱 | `budget_max` |
| 全部字段 | 只修哪些 | `scope_only` |
| 输入行本身 | 改数据 | `part_hours` 等 5 个 |

**组合封闭（最硬的一层）**：每条补丁只是给可行域再交一个预写集合。
约束条数固定、形式固定，补丁只改常数——交集运算做多少次都造不出清单外的新形状。
大一修的问题恰恰是「加约束」：**项数**可变，项数一变形状就变。这就是「改系数」与
「加约束」在数学上的真正区别。

### 完备性声明（不许说满）

| 那一半 | 靠什么 | 硬不硬 |
|---|---|---|
| 单个格子的要求（修多少、何时修、用哪条船、先后同异、只修哪些、改原始数据） | 从候选行字段投影推导 | **硬，有保证** |
| 钱与目标（花多少钱、怎么权衡） | 内核预先算好的 14 个量，人列的 | 软，凭经验 |
| 已知需求集之外的将来问法 | 拒绝时留记录，攒批评审 | 防漏，不防新 |

**只保证覆盖已知需求集，不保证覆盖将来冒出来的新问法。** 拒绝时必须明说「这个不支持」。

## 三、槽位总表（宪法正文）

38 个可写槽位 = 16 个标量参数 + 22 个约束族。

「索引怎么填」列标了两种性质，它直接决定提示词怎么写、校验代码怎么写：

- **离散**：能从固定清单里挑，写错当场拒；还能在提示词里附上当前快照的真实数字当护栏
- **开放**：要模型自己填内容（任务清单、日期区间），只能事后查，且要单独写解析代码

### A 组 · 标量参数（16 项，走 `overrides`）

| 槽位 | 默认 | 用户提问例子 |
|---|---|---|
| 船租（元每艘每天） | 基座值 | 船租涨两成 / 按 8 万一天算 |
| 人工单价（元每人时） | 基座值 | 人工涨价，一小时 300 |
| 最多作业线数 | 基座值 | 最多开两条船 |
| 人员总上限 | 基座值 | 明天只有 5 个人 |
| 每天最多维修小时数 | 基座值 | 一天最多干 10 小时 |
| 风机间转移小时数 | 基座值 | 转场按 3 小时算 |
| 每天维修开始时间 / 结束时间 | 基座值 | 早上 7 点开工、下午 5 点收工 |
| 常态/安全最大风速、常态/安全最大浪高 | 基座值 | 风速 12 米以上不许出海 / 浪高 2 米直接停 |
| 候选开工粒度（分钟） | 60 | 开工时间按半小时一档试 |
| 跨天暂停 | 是 | 一个活儿不许跨天干 |
| 允许夜间转移 | 是 | 晚上不许转场 |
| 允许少修几个 | 否 | 排不下就少修几个吧 |

### B 组 · 目标（走 `strategy` / `weights`）

| 槽位 | 索引 | 默认 | 用户提问例子 |
|---|---|---|---|
| `strategy` | 离散四选一 | 成本最低优先 | 按成本最低排 / 先保高危 / 越早干完越好 / 尽量多修几个 |
| `weight[量]` | 离散 14 个量名 | 0 | 高危优先 / 省钱比赶时间重要 / 尽量压租船天数 |

14 个目标量 = 原有 11 个（总经济成本、现金支出、完成任务数、最后完工时间、完工时间和、
高/中/低严重完成数、高/中/低严重完工时间和）+ **人工费 / 备件费 / 船舶艘天**
（后三个需内核 `metrics` 加三行，已批准）。

### C 组 · 修多少（走注入口）

| 槽位 | 索引 | 默认 | 用户提问例子 |
|---|---|---|---|
| `count_min[组]` | 离散：全部 / 高·中·低严重 / 部件名 / 风机号 / 任务编号；开放：任务清单 | 0 | 至少修 10 个 / 高危全都要修 / 齿轮箱至少修 2 个 / 风机001 必须全修完 / 任务018 一定得排进去 / 这三个里至少挑一个 |
| `count_max[组]` | 同上 | 任务总数 | 最多修 8 个 / 风机003 最多排 2 个 / 任务022 这轮先不修 / 这三个里最多挑一个 |

### D 组 · 何时修（走注入口）

| 槽位 | 索引 | 默认 | 用户提问例子 |
|---|---|---|---|
| `bucket_min[桶,组]` | 桶：离散窗口号/某日、开放日期区间；组：离散部件名/风机号/严重度/任务编号/作业线号 | 0 | **11月第二周必须修叶片** / 窗口03 里高危至少修 3 个 / 这周风机003 的活全干完 / 8号到10号必须开工两个齿轮箱 |
| `bucket_max[桶,组]` | 同上 | 不设上限 | 窗口01 不修齿轮箱 / 11月5号不安排新开工 / 2号船周三别排 / 这周叶片最多修 1 个 |

**判定口径统一：某段时间修了几个，按开工时间计。**

### E 组 · 时间界

| 槽位 | 索引 | 默认 | 用户提问例子 | 落点 |
|---|---|---|---|---|
| `earliest[组]` | 离散：任务编号/严重度/部件名/全部 | 0 | 任务018 最早 11月5号开工 / 高危的也要等下周才能动 | 注入口 |
| `deadline_delta[组]` | 同上 | 0（用任务自带期限） | 高危一周内干完 / 期限整体放宽 3 天 / 齿轮箱提前到 20 号前完成 | 数据补丁 |

> `deadline` 只走数据补丁，不走注入口。原因：独立复算 `verify_schedule` 用的是
> `task['截止分钟']`，若走注入口压候选变量，复算会按老期限验，两边口径不一致（R2）。

### F 组 · 用哪条船（走注入口）

| 槽位 | 索引 | 默认 | 用户提问例子 |
|---|---|---|---|
| `line_fixed[任务]` | 离散任务编号 | 自由 | 任务018 只上 2 号船 |
| `cap_max[维度,桶]` | 维度离散：作业线/风机/部件；桶离散：某日/窗口号 | 不设上限 | 11月8号最多开两条船 / 这周每天最多动 3 台风机 |

### G 组 · 花多少

| 槽位 | 索引 | 默认 | 用户提问例子 | 落点 |
|---|---|---|---|---|
| `budget_max[口径,组]` | 口径离散：现金/总成本/人工/备件/租船天；组：可选严重度或部件 | 不设上限 | 现金不超 80 万 / 总成本压到 200 万内 / 人工费单列不超 50 万 / 高危备件费不超 30 万 / 租船最多 5 天 | limits（前两个）+ 注入口（其余） |

### H 组 · 先后同异（N 元，不局限于两个）

| 槽位 | 索引 | 默认 | 用户提问例子 |
|---|---|---|---|
| `before_seq[有序序列]` + 间隔 | 开放，长度 ≥ 2 的任务编号序列 | 不设 | 先修 018 再修 022 / 按 018→022→025 的顺序做，中间隔 2 小时 |
| `same_bucket[集合]` | 开放，长度 ≥ 2 的任务编号集合 | 不设 | 018 和 022 同一天 / 这三个放同一个窗口 |
| `all_diff[集合]` | 开放，长度 ≥ 2 的任务编号集合 | 不设 | 018 和 022 不许同一天 / 这三台风机分在不同天 |
| `sev_before[层,层]` | 离散，只有 高→中、中→低 | 关 | 高危没干完不许开中危 |
| `sev_gap[层,层]` | 离散，同上 | 不设 | 高危干完隔半天再开中危 |

`before_seq` / `same_bucket` 扩到 N 元是**零新形态**（链式展开，条数变多而已）。
`all_diff` 是新形态（CP-SAT 原生 AllDifferent），已过加族评审，理由是形态固定、
参数只有变量集合、实现十行以内；它和「均衡/摊匀」不是一类——均衡要新造辅助量
（max−min），互异是现成的离散域分配原语。二元时 `diff_bucket` 与 `all_diff` 等价，
前者被吃掉，不再单列。

### I 组 · 只修哪些（走注入口）

| 槽位 | 索引 | 默认 | 用户提问例子 |
|---|---|---|---|
| `scope_only[桶或组]` | 桶离散/开放；组离散部件/风机/严重度、开放任务清单 | 全部 | 这轮只修叶片 / 只在窗口03 里干 / 只修风机001 / 只修这五个任务 |

### J 组 · 改数据（走 `data_patches` / `timeline_patches`）

| 槽位 | 索引 | 默认 | 用户提问例子 |
|---|---|---|---|
| `part_hours[部件,严重度,海况]` | 全离散 | 部件库原值 | 齿轮箱高危按 20 小时算 / 恶劣海况工时翻倍 |
| `part_arrival[部件]` | 离散部件名 | 库存流水原值 | 叶片备件 12 号才能到 |
| `weather[日]` | 离散快照有的日期 | 快照原值 | 11月8号风速按 15 米算 / 那天浪高 2.5 米 |
| `hourly[时刻]` | 开放任意时刻 | 快照原值 | 明天上午电价按 1.2 元算 |
| `window[窗口]` | 离散窗口号 | 快照原值 | 窗口03 推迟两天开始 |

## 四、边界清单（明确做不到，不许拿近似槽位硬凑）

硬凑出来的东西对不上用户的话，比明确拒绝更危险。

| 做不到 | 典型话术 |
|---|---|
| 格子之间比一比（均衡） | 摊匀一点 / 别让某条船累死 / 出海别一天挤一天松 / 几台风机分得差不多 |
| 条件约束 | 如果 018 排进去，019 必须 4 小时内开工 |
| 组内自动两两 | 风机001 所有任务两两间隔 2 小时 |
| 跨量加权组合 | 中严重完工时间和 + 2 倍低严重完工时间和 ≤ 30 天 |
| 过滤后复合量取极值/比值 | 高危里最晚完工的那个不晚于 X |
| 凭经验列的那批之外的目标轴 | 出现第 15 个权衡对象 → 走加族评审，不能直接填 |
| 安全库存下限 | 缺业务依据，不做 |
| 已知需求集之外的将来问法 | 拒绝时留记录 |

「用权重去近似均衡」也在禁止之列——拿近似冒充做到了，就是糊弄。

## 五、校验规则（6 条，全部查表与计数，不解析表达式）

1. **槽位在册**：不在册就明确告知「没有这个旋钮」，并给出最近的替代旋钮
2. **索引值在册**：实体存在性，复用 `dsl_core/registry/entities.py` + `dsl_core/part_catalog.py`
3. **数值类型 / 单位 / 区间**
4. **静态不可行预检**（不用跑求解器，只报算得出来的）：
   - min 大于该桶内该类别的在册任务数
   - min > max
   - 界落在规划范围外
   - 点了不存在的任务
   - `same_bucket` 的任务候选窗口/日期集合无交集（N 元新增）
   - `all_diff` 的候选能取到的不同日期数 < n（N 元新增）
   - `before_seq` 序列里有重复或绕圈（N 元新增）
5. **槽位冲突**：同一任务既必修又排除等
6. **同一格子被写两次**：直接报错，让大模型自己合并（见决策 D2）

第 4 条是小一修相对大一修的**新增能力**：因为族固定，可以在跑求解器之前就把一批
「必然做不到」拦下来，而且理由带数字。

**索引不许猜**：`窗口03` / `11月8日` / `叶片` 按枚举精确匹配，匹配不上就报错，
不做模糊匹配（沿用 `part_catalog` 的纪律）。特别是「叶片」不能顺手匹配掉「叶片备件」。

## 六、硬 / 软消歧（不靠关键词规则，也不靠置信度）

「高危优先」这类话有两条路：硬钉死（`count_min` / `sev_before`）与软偏好（`weight`）。
两条路都在表上，选错代价不对称：

- 该软的做成硬 → 报不可行，用户看到「做不到」会自己改口 → 坏体验但诚实
- 该硬的做成软 → 出了方案但没真满足，用户以为做到了 → **这是欺骗**

规则：

1. **大模型只报强度类别**（硬 / 软 / 拿不准）三选一，**不给数字**。
   自报置信度不是概率、没校准过，拿它当阈值是伪精度，而且同句两次跑会给不同数字，
   直接破坏复现性。
2. **报了硬或软就照做，在结果里回显**——「这句话我按『必须全部排进去』处理了」。
3. **报「拿不准」就问用户一句**，不猜默认值。
4. 若判硬而结果不可行，诊断层接着给退路：「改成『尽量』的话能给你一份 11 个里排 9 个的方案」。

## 七、决策记录

| 编号 | 决策 | 结论 |
|---|---|---|
| D1 | 目录 | 根目录 `小一修/`，内部包 `yxcore` |
| D2 | 同一格子被写两次（**同一轮内**） | **报错**，`*` / `+` / `-` 一律按基线值换算成绝对值 |
| D3 | 硬软同现 | 不报错；回显 + 拿不准就问人 |
| D4 | 安全库存下限 | **不做**（缺业务依据） |
| D5 | 目标表达力 | 只给「四选一策略 + 14 维权重的加权和」，不放回自定义分层顺序 |
| D6 | 时序补丁 | 保留（`weather` / `hourly` / `window` 等） |
| D7 | 数据 | 继续用现有 `data/` 的基座，不另造 |
| D8 | 预算口径 | 现金 / 总成本（内核原生）+ 人工 / 备件 / 租船天（内核 metrics 加三行） |
| D9 | 硬约束默认 | 默认全硬，只对天生软的需求提供罚分系数 |
| D10 | 部分排程判据 | 只有一份，收在 `apply.py`，执行器与对账共用（照抄大一修 `compiler.needs_partial` 的纪律） |
| D11 | H 组 N 元 | 顺序与共现扩到 N 元（零新形态）；互异用 `all_diff`（新形态，已评审） |
| D12 | 均衡族 | **不做**，登记进边界清单 |
| D13 | 同一格子**跨轮**又被写一次 | 不报错，按**修订**处理（后一句覆盖前一句），回执说「从几改成几」 |
| D14 | 相对量（`+2` / `*1.2`）落在哪 | 落在该格**当前生效值**上，不落基线值；没生效值才落基线 |
| D15 | `reset` 撤销什么 | 只撤销点名的那几格，回到基线；不带索引 = 整组撤销 |
| D16 | 状态怎么进提示词 | 用**补丁原格式 JSON** 印生效表，不印人话——人话抄回去会变成另一个 kind |

## 八、目录结构与分期

```
小一修/
  README.md          ← 本文件（宪法）
  yxcore/
    slots.py         ← 槽位注册表（唯一事实来源）
    patch.py         ← 补丁结构、归一化、排序、指纹
    validate.py      ← 6 条校验规则
    apply.py         ← 补丁 → 内核入参（overrides/limits/weights/注入口）
    closure.py       ← 注入口闭包：槽位 → CP-SAT 约束
    prompt.py        ← 从 slots.py 反向生成提示词（改注册表，提示词自动跟着变）
    parse.py         ← 自然语言 → 补丁（调大模型，复用 DEEPSEEK_* 环境变量）
    pipeline.py      ← 编排（抄 dsl_core/runner.py 骨架）+ 意图对账接入
    reconcile.py     ← 槽位对账（注册即承诺，21 个核对函数）
    diagnose.py      ← 不可行逐条归因（理由带数字）
```

### 实现时的三处落地修正（与上文设计的差异，以此为准）

1. **`deadline_delta` 只能提前，不能放宽**。内核的期限补丁（`_apply_task_patches`）
   只做收紧，放宽在内核层就不存在。编译层对「没有让任何任务提前」的期限给出明确拒绝。
2. **`strategy` 没有索引维度**，值就是四选一的策略名；`weight` 的索引是「量」。
3. **开关型槽位**（`scope_only` / `same_bucket` / `all_diff` / `sev_before`）的值可省略，
   点亮即生效。`same_bucket` / `all_diff` 带可选索引「粒度」（天 / 窗口，默认天）。

### 评测还测出来的三件事（如实记录）

- **模型输出有随机性**：同一 temperature=0，不同轮的写法会变（同一条曾出现

  94/95~95/95，117 条重跑后一次跑到 **117/117**。这不代表「调好了就不会错」——
  应对始终是**让错翻的那一类在校验层被拦下**（如 cap_max 拧到 0 会提示「这等于那天
  一条船都不派」），而不是把通过率当稳定性承诺。
- **复现性承诺必须跟最优性绑定**：求解器在时限内未证最优时（本次是「最后完工时间」
  「完工时间和」两阶段），同一批旋钮两次跑出的方案内容可能不同。产物里新增
  `已证最优` / `未证最优目标` 两个字段并进告警；评测只在两次都证到最优时才要求内容一致。
- **在线层先跑不了、后补跑了，过程如实记在这里**：本轮开始时 DeepSeek key 返回
  `402 Insufficient Balance`，E2 在线与 E7 在线两层的结论一度是「未跑」。充值后重跑，
  第一轮 E2 在线直接**整层报错**（我那条索引校验过严，把 `{"量":"…"}` 也拦了），

  按 D3 记为「过慎」，不算错）。
  **记这一段的意思是**：一个只在离线层全绿的评测集，上线第一天就能掉出两层的问题；
  「没跑」和「跑绿了」之间的差距，比「95 分」和「100 分」大得多。

## 十、多轮会话：状态就是一张表

多轮不是「把历史对话全塞进提示词」。那样做有两个后果：提示词越来越长，
而且模型要在散文里自己推断「现在到底按什么在排」——这是让它做状态管理，不是让它做翻译。

**状态收成一张表**：键是 `(槽位, 规范化索引)`，值是补丁。除此之外没有别的状态。

| 用户说 | 表上发生什么 | 为什么这么定 |
|---|---|---|
| 「最多修 8 个」 | 写入 `count_max[全部]=8` | 首次出现 = 新增 |
| 「算了，最多修 6 个」 | 同格覆盖成 6 | 同格=同一件事，后说的算（D13）；回执说「从 8 改成 6」，不是「加了第二条」 |
| 「再多修两个」 | 6 → 8（**不是** 8+2） | 相对量叠在**当前生效值**上（D14）。叠基线的话，改主意就会互相打架 |
| 「修多少个这事先不管了」 | 删掉这一格，回到基线 | `reset` 只撤销点名的那几格（D15）；**不带索引就是整族撤掉** |
| 「刚才那句我再说一遍」 | 表不变 | 值相同就是 `无变化`，不该报成修订 |

**为什么索引必须原样照抄进提示词**：生效表进提示词时用的是**补丁原格式 JSON**，
不是人话版。人话版写「叶片的任务」，模型抄回去会变成另一个 `kind`，落到别的格子上——
用户说「改主意」，结果变成「加了一条新要求」。这是实测踩到的（缺陷 #14 的同族）。

**整轮原子落地**：一轮里模型翻出三条补丁，只要有一条过不了校验或编译，
**整轮全部回滚**，并清掉这一轮的 Turn 记录。理由：半句话生效比整句话不生效更危险——
用户看到「已按你说的改」，实际只改了一半，剩下一半会在几轮之后以「方案怎么不对」的形式冒出来。

**两个指纹，别混用**：`Session.fingerprint()` 算的是「生效补丁 + 轮数」，用于**审计**——
「改了三遍才对」和「一次说对」必须能区分开。而喂给求解器的那个指纹只算**生效补丁**，
用于**复现**——不管用户怎么绕过来的，只要表一样，方案就该一样，指纹也该一样。
